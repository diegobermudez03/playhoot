# Identity - Current State

Status: CURRENT IMPLEMENTATION

## Capability Status

| Area | Status | Notes |
| --- | --- | --- |
| Operation authentication levels | IMPLEMENTED | 2026-10-27: the catalog `Authorize` decides with (`identity/internal/business/operationlevel`, `anonymous < guest < account`; an uncataloged operation is forbidden and alerts), published by `GET /v1/identity/operations`. |
| Guest Users | IMPLEMENTED | 2026-10-27: `POST /v1/guests` (`identity/usecases/createguest`) persists a distinct guest per idempotency key with the normalized display name and opens its credential session; a reused key with another name is `identity.ErrIdempotencyConflict`; a key answers again only within 5 minutes (`idempotency_key_spent` after). |
| Credentials | IMPLEMENTED | 2026-10-27 (IDENTITY-ADR-0003 as amended the same day): access tokens are HS256 JWTs (`identity/internal/business/accesstoken`, 15 minutes, claims: subject UserUUID, expiry, level, display name) verified by `Authorize` with the key alone, reading nothing; refresh tokens are opaque (`phr_` + 32 random bytes) stored as-is in `identity_sessions`. |
| Refresh | IMPLEMENTED | 2026-10-27: `POST /v1/identity/refresh` (`identity/usecases/refreshcredentials`) takes only the refresh token. An active, unexpired session gets a new access token and keeps its refresh token, unless it was issued over 5 hours ago: then a new session row replaces it (`replaced_by_id`) and the old one is deactivated, never updated in place. The immediate predecessor deactivated less than 5 minutes ago answers with a new access token and the current refresh token; anything else is `refresh_invalid` (401). Guests never expire; account sessions expire after 30 days unused and 90 days from sign-in (`identity/internal/business/refreshtoken`). |
| Logout | IMPLEMENTED | 2026-10-27: `POST /v1/identity/logout` (`identity/usecases/endsession`) deactivates the refresh token's session; idempotent, always 204. Access tokens already issued stay valid until they expire. |
| Own identity | IMPLEMENTED | 2026-10-27: `GET /v1/identity/me` returns the caller's User from its access token (`VIEW_OWN_IDENTITY`, guest). |
| Accounts | IMPLEMENTED (local provider) | 2026-10-27, reworked 2026-10-29: the account login workflow (`identity/workflows/accountlogin`: a `Manager` with `StartLogin`, `HandleCallback`, `CompleteLogin`, one file per step). `POST /v1/identity/login/start` records an attempt (state, nonce, the client's S256 code challenge; 5 minutes) and answers the provider's authorization URL (`identity/loginproviders`); the provider's answer reaches `GET /v1/identity/login/{provider}/callback` through the browser, which answers the attempt once, exchanges the provider's code outside any transaction, resolves the external identity (issuer + subject) to its User; one bound to nobody becomes an account of the guest who started the login, when there is one (their `UserUUID`, name and history kept, their guest sessions ended; the guest's access token is optional on `login/start` and recorded on the attempt as `guest_user_id`), or of a new User without a display name, together with its binding (a concurrent first sign-in that binds first wins, the other rolls back and finds it), and redirects to `WEB_SIGN_IN_COMPLETE_URL` with a one-time code (60 seconds) or `?error=cancelled|failed|unavailable`; `POST /v1/identity/login/complete` checks the verifier, uses the code up (a wrong verifier too), opens the account's session (expiring) and ends the session of `replaces_refresh_token` (the guest it replaces) in the same transaction. Every step of an attempt is an event in `identity_login_attempt_events` (started, answered, cancelled, failed, unavailable, code_issued with how the account was resolved (`existing`, `linked_guest`, `created`) and what the provider said about the person at that login, completed, rejected with its reason), written in the same transaction as the change it records. Only the fictitious local provider exists (`IDENTITY_LOCAL_PROVIDER=true`, only in development/local/test): its page `GET /v1/identity/login/local/authorize` lets the person pick a name, the same name being the same subject. Google is WORK-0060. |
| Display names | IMPLEMENTED | 2026-10-29 (decided by the human): an account starts without a display name and its person chooses one through `PUT /v1/identity/me/display-name` (`identity/usecases/setdisplayname`, operation `SET_OWN_DISPLAY_NAME`, guest level); clients ask for it whenever an account has none. Every name a User had is kept in `identity_display_name_changes` (a guest's creation name included), written with the change. The access token carries the name it was issued with until renewed. |

## Persistence

Migration `identity/internal/migrations/20261029000000_identity_core.go`, registered by `migrations.go` through `identity/migration`: `identity_users`, `identity_accounts`, `identity_sessions` (one row per issued refresh token; a partial unique index keeps one active row per `session_uuid`), `identity_guest_requests` (idempotency claims); and `20261029010000_identity_logins.go`: `identity_external_identities` (unique issuer + subject, the User it is bound to, and the email and name seen when it was bound, never overwritten) and `identity_login_attempts` (unique state and one-time code; its current state); and `20261029020000_identity_trails.go`: `identity_login_attempt_events`, `identity_display_name_changes`, `identity_users.display_name` nullable. Only keys, unique constraints and indexes, per the database-constraints standard.

## Placeholders (wired, but not real behavior)

- The local provider (`identity/loginproviders/local.go`) stands in for Google in development and tests; everything around it is the production implementation. The former fixed test tokens (`test-user-1`, `test-user-2`, `test-guest`) no longer exist.
- `IDENTITY_ACCESS_TOKEN_KEY` (at least 32 bytes) is required in production; elsewhere an unset key is replaced by a random one per process, so access tokens die with the process and clients renew them with their refresh token.

## Current Gaps

- Google sign-in (WORK-0060) and identity reconciliation are not implemented: a guest signing in to an account that already exists switches to it, and the two Users are not merged.
- Login attempts are never deleted (no cleanup job yet).
- Revocation does not reach access tokens already issued nor open WebSockets (out of scope of identity-v1).
