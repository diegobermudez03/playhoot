# Identity - Current State

Status: CURRENT IMPLEMENTATION

## Capability Status

| Area | Status | Notes |
| --- | --- | --- |
| Operation authentication levels | IMPLEMENTED | 2026-10-27: the catalog `Authorize` decides with (`identity/internal/business/operationlevel`, `anonymous < guest < account`; an uncataloged operation is forbidden and alerts), published by `GET /v1/identity/operations`. 2026-11-01 (game creation project): `CREATE_GAME` and `EDIT_GAME` (reading and changing a game's version being built), both `account`; whether the caller may edit a given game is Game Management's decision. |
| Guest Users | IMPLEMENTED | 2026-10-27 (capped at 200 per client address per hour since 2026-10-31): `POST /v1/guests` (`identity/usecases/createguest`) persists a distinct guest per idempotency key with the normalized display name and opens its credential session; a reused key with another name is `identity.ErrIdempotencyConflict`; a key answers again only within 5 minutes (`idempotency_key_spent` after). |
| Credentials | IMPLEMENTED | 2026-10-27 (IDENTITY-ADR-0003 as amended the same day): access tokens are HS256 JWTs (`identity/internal/business/accesstoken`, 15 minutes, claims: subject UserUUID, expiry, level, display name) verified by `Authorize` with the key alone, reading nothing; refresh tokens are opaque (`phr_` + 32 random bytes) stored as-is in `identity_sessions`. |
| Refresh | IMPLEMENTED | 2026-10-27: `POST /v1/identity/refresh` (`identity/usecases/refreshcredentials`) takes only the refresh token. An active, unexpired session gets a new access token and keeps its refresh token, unless it was issued over 5 hours ago: then a new session row replaces it (`replaced_by_id`) and the old one is deactivated, never updated in place. The immediate predecessor deactivated less than 5 minutes ago answers with a new access token and the current refresh token; anything else is `refresh_invalid` (401). Guests never expire; account sessions expire after 30 days unused and 90 days from sign-in (`identity/internal/business/refreshtoken`). |
| Logout | IMPLEMENTED | 2026-10-27: `POST /v1/identity/logout` (`identity/usecases/endsession`) deactivates the refresh token's session; idempotent, always 204. Access tokens already issued stay valid until they expire. |
| Own identity | IMPLEMENTED | 2026-10-27: `GET /v1/identity/me` returns the caller's User from its access token (`VIEW_OWN_IDENTITY`, guest). |
| Accounts | IMPLEMENTED | 2026-10-27, reworked 2026-10-29: the account login workflow (`identity/workflows/accountlogin`: a `Manager` with `StartLogin`, `HandleCallback`, `CompleteLogin`, one file per step). `POST /v1/identity/login/start` records an attempt (state, nonce, the client's S256 code challenge; 5 minutes) and answers the provider's authorization URL (`identity/loginproviders`); the provider's answer reaches `GET /v1/identity/login/{provider}/callback` through the browser, which answers the attempt once, exchanges the provider's code outside any transaction, resolves the external identity (issuer + subject) to its User; one bound to nobody becomes an account of the guest who started the login, when there is one (their `UserUUID`, name and history kept, their guest sessions ended; the guest's access token is optional on `login/start` and recorded on the attempt as `guest_user_id`), or of a new User without a display name, together with its binding (a concurrent first sign-in that binds first wins, the other rolls back and finds it), and redirects to `WEB_SIGN_IN_COMPLETE_URL` with a one-time code (60 seconds) or `?error=cancelled|failed|unavailable`; `POST /v1/identity/login/complete` checks the verifier, uses the code up (a wrong verifier too), opens the account's session (expiring) and ends the session of `replaces_refresh_token` (the guest it replaces) in the same transaction. Every step of an attempt is an event in `identity_login_attempt_events` (started, answered, cancelled, failed, unavailable, code_issued with how the account was resolved (`existing`, `linked_guest`, `created`) and what the provider said about the person at that login, completed, rejected with its reason), written in the same transaction as the change it records. Two providers: Google (below) and the fictitious local provider (`IDENTITY_LOCAL_PROVIDER=true`, only in development/local/test), whose page `GET /v1/identity/login/local/authorize` lets the person pick a name, the same name being the same subject. Google (`identity/loginproviders/google.go`, 2026-10-31, WORK-0060): enabled by `GOOGLE_OAUTH_CLIENT_ID`/`SECRET`/`REDIRECT_URL`; PKCE S256 toward Google with a verifier only the server keeps (on the attempt), the ID token verified against Google's keys (RS256, issuer, audience, expiry, nonce), email kept only when verified; not yet verified against the real Google: that integration (an OAuth client, the manual check) is a planned follow-up deferred by the human to the end; until then no environment configures it. `GET /v1/identity/login/providers` lists the enabled providers. |
| Display names | IMPLEMENTED | 2026-10-29 (decided by the human): an account starts without a display name and its person chooses one through `PUT /v1/identity/me/display-name` (`identity/usecases/setdisplayname`, operation `SET_OWN_DISPLAY_NAME`, guest level); clients ask for it whenever an account has none. Every name a User had is kept in `identity_display_name_changes` (a guest's creation name included), written with the change. The access token carries the name it was issued with until renewed. |
| Resource links | IMPLEMENTED | 2026-11-02 (game creation project, decided by the human): `identity/usecases/resourcelinks`. A secret link lets whoever holds it act for its User on one resource only, named by an opaque kind and id (Identity never knows what the resource is; today Game Management's `game`). Tokens are `phl_` + 32 random bytes (base64url); only their SHA-256 is stored. One open link per User and resource: `CreateResourceLink` revokes the open one and makes a new one (7 days, `identity/internal/business/resourcelink`; renewing is creating); `RevokeResourceLink` revokes it (nothing when there is none); `ResourceLinkStatus` says whether a live one exists; `ResolveResourceLink` answers `valid` (with the User, kind, id and expiry), `unknown`, `expired` or `revoked`, and never logs the token. Revocation is written once (`revoked_at`). The API uses it for the links an AI gets to a game (`api/README.md`, games group). Metric `identity_resource_links_total{operation}`. |
| AI authorization | IMPLEMENTED | 2026-11-03 (game creation project, CHECKLIST I, decided by the human): `identity/usecases/aiauthorization`, the OAuth 2.1 authorization server of the MCP server, on tables apart from user sessions. Dynamic client registration (RFC 7591) of public clients only (`none`, authorization code + refresh token, redirect URIs `https` or loopback `http`); authorization code with PKCE `S256` only, the resource indicator must be the MCP resource, a single scope `games` (read, create and change the User's games; never publish); the browser goes to the web consent page `<PUBLIC_WEB_BASE_URL>/connect-ai?request=<id>` (request valid 10 min, decided once by a signed-in account, operation `CONNECT_AI`); codes `phc_` (2 min, single use: a replay revokes the connection), access tokens HS256 JWTs `typ at+jwt` signed with a key derived from `IDENTITY_ACCESS_TOKEN_KEY` (a user token and an AI token are never interchangeable; 1 h; audience the MCP resource; `sid` the connection) checked against the connection on every call, refresh tokens `phr_` (30 days, rotated on every use: a reused one revokes the connection), RFC 7009 revocation. The User lists their live connections (`last_used_at` is the last token grant) and revokes any. Only SHA-256 hashes of codes and refresh tokens are stored. Metric `identity_ai_authorization_total{operation}`. |

## Placeholders (wired, but not real behavior)

- The local provider (`identity/loginproviders/local.go`) stands in for Google in development and tests; everything around it is the production implementation. The former fixed test tokens (`test-user-1`, `test-user-2`, `test-guest`) no longer exist.
- `IDENTITY_ACCESS_TOKEN_KEY` (at least 32 bytes) is required in production; elsewhere an unset key is replaced by a random one per process, so access tokens die with the process and clients renew them with their refresh token.

## Current Gaps

- Identity reconciliation is not implemented: a guest signing in to an account that already exists switches to it, and the two Users are not merged. Google sign-in is implemented; its check against the real Google is the planned follow-up (Identity phase 2).
- Login attempts and their events are kept for good, by design (closure decision, IDENTITY-ADR-0003): they are the history of what people did.
- Revocation does not reach access tokens already issued nor open WebSockets (out of scope of identity-v1).

## Identity Phase 2 (planned, after the game creation flow)

Decided by the human on 2026-10-31: identity-v1 was phase 1, only what was needed to test ownership with real people (guests, accounts, credentials). Identity as a component continues after the game creation flow (plans 03 and 04) with:

- The account screen: account management and data, including changing the display name after the first one (`PUT /v1/identity/me/display-name` already exists).
- The account's active sessions: listing them with the device each one was opened on (storing device data per session then) and letting the person end any of them.
- The real Google integration: an OAuth client and the manual check against Google (planned follow-up of WORK-0060).
- Retention of abandoned guests: guest sessions never expire for now, so every guest stays.
- Rotation of the access-token signing key (several keys at once).
- Signing out as a guest (not offered: a guest who signs out loses their identity for good).
