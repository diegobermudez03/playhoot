# Project: Game Creation v1

Status: ACTIVE
Created: 2026-11-01
Last updated: 2026-11-05

## Goal

Deliver the game creation flow: a creator (with an external AI that only reads links, with an AI agent through API/MCP, or alone) edits a persisted draft, uploads its assets, builds it with the Playhoot SDK, tests it in a human preview and in automated scenarios, and publishes a validated build that other people can play. Started from `../docs/04_Playhoot_Plan_del_Flujo_de_Creacion.docx` (the "plan"; `§N` points to its chapters), deliveries 0 to 3 (§13), with the SDK contract in `../docs/03_Playhoot_Plan_del_SDK.docx`.

**Realignment (the human, 2026-11-05).** The product direction changed (`../docs/06_Playhoot_Product_Strategy_Couples_Handoff.docx`: Playhoot + Education vertical; `../docs/07_Playhoot_Propuesta_Costos_IA_Teacher.docx`: integrated AI economics). The creation flow must now satisfy `../docs/08_Playhoot_Checklist_Flujo_de_Creacion.md` (the "checklist"; letters point to its sections), which wins over the plan and over earlier conversation decisions where they conflict. The goal of the creation operations is to be cheap and efficient for an AI agent: small context, patches instead of whole files, templates from published games, compact verifiable tests. The teacher product layer (classes, students, material ingestion, gradebook) and the integrated Playhoot AI runner are NOT part of this project; this project builds the creation operations they will use.

The frontend counterpart is the frontend repository's Project `game-creation-web-v1` (SDK packages, build tools, authoring UI, AI guide). As in `session-runtime-v1`, the human directs each step in conversation; `CHECKLIST.md` tracks what is required and done.

## Explicitly Out Of Scope

- Plan deliveries 4-7 (cards/boards, didactic simulation, 2D world, launch closure): SDK projects. They gate the template families of checklist AM and the composable modules of E3.
- Playhoot's own AI agent runner and everything that only exists inside it (checklist Z, AA, AB, AC, AD, AG repeated-failure detection, P raster generation, R automatic repair loop, L teacher material ingestion), billing, Teacher product layer: later projects that reuse these operations.
- Automatic screenshots (checklist V, P2).
- Template marking, featuring and the real discovery search (second step of the templates work, decided by the human 2026-11-05): this project only builds the consumption side against a catalog port.
- Infrastructure and real integrations (deployed storage, isolated build worker, global quotas, real MCP clients): done before the first deploy, tracked in `docs/engineering/LAUNCH_READINESS.md`.

## Decisions Taken In Conversation (2026-11-01 to 2026-11-03)

Kept unless marked superseded.

- Assets use the final flow from the start behind the storage port; the existing GCS adapter runs against the local emulator until launch. No code is written that integration would have to replace. Redesigned by the human on 2026-11-02: asset bytes are uploaded through the backend, which validates them anyway; a signed URL is issued only when the backend never touches the bytes (`docs/engineering/standards/object-storage.md`).
- MCP is implemented for real in this binary. Its authorization is per user account (OAuth); the project travels in each call. Identity reuses the normal sign-in but keeps AI authorization attempts and AI sessions in their own tables.
- One MCP operation = one API endpoint = one creation service method. Services know nothing about actors: authorization lives in the upper layers (API, MCP, Identity), sharing one authorization component. MCP calls the service method directly; if split out later it calls the endpoint.
- The project link given to an AI grants read and write; an AI that cannot write tells the user what to paste. A GET never mutates.
- Real AI clients are tested by the human on a throwaway GCP VM with an ephemeral database; no tunnels.
- Backend scripts built by the SDK use a new versioned scriptcheck profile `sdk-v1` (CHECKLIST B): top-level module state is forbidden statically and top-level constants are frozen once at load; the author may mutate the state it receives (each call gets freshly parsed JSON). No per-call re-initialization. Code that still mutates something top-level breaks the protocol and is a bug of that game, accepted.
- The human preview goes before automated scenarios.
- Domain model (the human, 2026-11-01): Game Management owns the game ENTITY (created unpublished, card, thumbnails, published or not) and its editions; Play owns everything playable, including the version being built. A Play version is DRAFT (mutable: sources edited in place, each change a new revision of the same version with optimistic locking on `baseRevision`, idempotency key, every attempt recorded) until it becomes EXECUTABLE ("ready", immutable forever); `play_games.current_version_id` only points at a ready version. A game has at most one DRAFT. A GM edition (`game_editions`, EDITING/PUBLISHED) references its Play version by uuid. No direct calls between domains: the orchestrator coordinates. Cross-domain writes: create game (GM game + edition, then Play game + DRAFT version) and publish (GM rules + Play readiness, Play freezes and points to the version, GM marks published; idempotent steps completed on retry, no compensations). Every Play write is authorized by GM first (owner / creation access, open edition) through the orchestrator. Assets are declared in `game.project.json` and the build derives the pending list.
- Preview (the human, 2026-11-02): it runs on the live controller pinned to a SUCCEEDED build of a draft revision, with synthetic participants the owner plays one at a time from one connection; pause is included (Session time stands still, the game never sees it); one preview per game; it ends after 10 minutes without activity. Previews are recorded apart from Sessions and keep no checkpoints, replays or recovery.
- Editing a published game (a new edition and a new DRAFT not pointed to until published) is in this project's backend scope (the human, 2026-11-01).
- The change envelope (`playhoot.project-change.v1`) uses snake_case field names (`base_revision`, `files`, `delete`, `idempotency_key`), like every API body; the plan's `baseRevision` example is superseded. The idempotency key is required on every draft write. Extended 2026-11-05 with `edits` (CHECKLIST M).
- Builds (the human, 2026-11-02): every applied revision is built automatically in the background, coalesced so only a version's newest waiting revision is built; the answer never waits for the build, and a person or an AI reads its result on the draft or through a long poll. A simulation or a preview requires a succeeded build. The build runs behind a port (`gamebuild.Builder`) so it can become its own service.
- AI links (the human, 2026-11-02): the link is a credential Identity keeps, scoped to one game; its token goes in the path for reads and writes; one active link per game, valid 7 days; renewing creates a new link and revokes the old one; the context page is Markdown served by the backend, with the sources inline when they weigh under 150 KiB, otherwise linked per file pinned to the observed revision. Kept for the Markdown page (a read-only chat reads everything in one fetch, on its own tokens); **superseded 2026-11-05 for MCP and the JSON context**, which return metadata only (CHECKLIST L).
- Simulation for the AI (the human, 2026-11-02): a separate loop on a virtual clock that reuses the sandbox and the live admission, limits and boundary planning, advancing 100 ms ticks; a command runs its own boundary at its arrival. **Superseded 2026-11-05 in part** (CHECKLIST O): expectations are now in scope, results are summarized by default and kept for a short time so the AI can inspect state on demand, scenarios saved in the project run by path, and hold segments exist. The shared-semantics part stays.
- MCP (the human, 2026-11-03): the official Go SDK (`github.com/modelcontextprotocol/go-sdk`, a released version pinned); the AI may create games (`create_game`) and list the User's games (`list_my_games`); there is no publish tool. One OAuth scope, `games`, which never includes publishing. `upload_asset` takes the content in base64: **superseded 2026-11-05** for anything but small files (CHECKLIST S).
- Publishing (the human, 2026-11-02): a card needs only a name to be published (description, logo and discovery photos optional); visibility is chosen at publish, public (anyone creates Sessions) or private (only the owner creates Sessions, anyone with a code joins); only the CURRENT revision is published (earlier revisions exist to restore); the name is given when the game is created and may be confirmed or replaced at publish.
- Templates and remix as the plan defined them ("Usar como plantilla" chosen by the user, no AI search, a small fixed catalog): **superseded 2026-11-05**, see below.

## Decisions Taken In Conversation (2026-11-05, realignment)

- The checklist (`../docs/08_...md`) is the criterion; earlier decisions that conflict with it are reverted (the human: "prioricemos el plan actual"). The agent proposes the concrete shape; the human agreed in advance to proposals that fit the checklist.
- Templates (the human): a template is any PUBLISHED game whose owner marked it as usable as a template (default off: creators keep the rights to their games). Playhoot can additionally mark some of them as featured for AI: the first list an AI sees, by kind of game. Nothing about templates is hardcoded in the MCP or the guide: it comes from the backend. The AI discovers templates like the user's search (categories, keywords), receives the metadata the database already has (nothing AI-generated), inspects one candidate in detail (brief, configuration, file list) and reads only the files it needs before choosing; it may decide that none fits and start from the minimal project. Instantiating copies the template's published sources and assets into a draft, recording the provenance; the template never changes. Two steps: (1, this project) the whole consumption side against a template catalog port whose first implementation answers empty lists; (2, a later project) marking, featuring, categories and the real discovery service. Remix of a published game is the same mechanism.
- Composable modules (checklist E3) are realized as SDK capabilities plus small glue code, not as file merging; they wait for the SDK deliveries that provide those capabilities.
- Context diet: MCP and JSON reads return metadata (paths, hashes, sizes, build summary, assets, notes, brief); sources are read per file. Every write answers the new revision's file hashes.
- Patches: the change envelope accepts exact search/replace edits applied by the service on the base revision; an edit that does not match exactly once rejects the whole change.
- Asset bytes keep going through the backend (object-storage standard); for an agent they must not go through the model's context: an upload URL to the backend replaces base64 for anything beyond small files.
