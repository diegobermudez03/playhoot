# WORK-0005 — Host Connection Design Revision (2026-09-20)

Process: design reconciliation of `WORK-0005-thin-live-coordinator.md` (`docs/projects/active/session-runtime-v1/works/`), following the material architecture inconsistency discovered during the same-day Project/WORK migration (see `LEGACY_HUMAN_REVIEW_2026-09-20.md`, question 2). No production Session code was implemented by this session.

## What changed

- `WORK-0005`'s `Status:` was returned from `IMPLEMENTING` to `DRAFT`, per `docs/work/README.md`'s Material Change / Reapproval rule - this WORK's already-implemented Create/Join/Start/AnswerInteraction/Deliver path is unaffected and remains the accepted foundation; only the host live-connection-establishment path needs (and now has) a design correction.
- A new "Host Connection Design Revision (2026-09-20, DRAFT PROPOSAL)" section was added to WORK-0005, giving Blocker 8 a concrete proposed resolution. Summary:
  - A **host** obtains a live connection through a distinct connect handshake (`session_uuid` + `user_uuid`, no `join_code`/`display_name`/`idempotency_key`) that never calls `Join` and never creates a `session_participants` row.
  - Before upgrading, that handshake calls a new read-only `SessionRuntime.ResolveHost` capability (implemented in `play/sessionruntime`, alongside the existing post-commit event-translation reads) that resolves `sessions.host_actor_id` and compares it to the `SessionActor` for `(SessionUUID, UserUUID)` - the same check `sessionlifecycle.Manager.Start` already performs internally, restated read-only rather than duplicated as a new rule. No change to `Manager`'s signatures/business logic/persistence model.
  - `play.Coordinator` gains a second, structurally separate connection registry for host connections (alongside the existing per-Session participant registry), so a host connection can never be mistaken for, or receive, participant-addressed fan-out, and so future host-targeted delivery (WORK-0006/WORK-0008) has a natural place to target later without a registry redesign.
  - A host connection only ever accepts `START` (not `ANSWER_INTERACTION`, which stays tied to a bound Participant connection).
  - **Layered authorization**: `sessionlifecycle.Manager` already independently re-validates host/participant identity on every command regardless of transport path (`Start`'s existing `NOT_HOST` outcome, `AnswerInteraction`'s existing recipient check) - the new connect-time check protects the *connection slot* (so an arbitrary caller cannot occupy/hijack it or later receive host-targeted fan-out), it is not the sole security boundary.
  - A host may still separately also become a Participant through the ordinary Join+connect flow - two independent connections, never fused - structurally unaffected, not exercised by this WORK.
- `docs/projects/active/session-runtime-v1/PROJECT.md` was updated: WORK-0005's Current Work bullet, Work table status (IMPLEMENTING -> DRAFT), WORK-total tally, Capability Coverage row, and Material Decisions list (new item 5) all now reflect the DRAFT proposal awaiting approval.
- `internal/AI_CONTEXT.md`'s resume header was updated to point at this checkpoint.

## Please confirm or correct

1. **The overall model**: two independent connection kinds (host, participant), bound into two structurally separate `play.Coordinator` registries, with a host-connect handshake gated by a new read-only `SessionRuntime.ResolveHost` check mirroring `Start`'s existing host-authorization logic. If this shape is wrong, say what should replace it - alternatives considered and not proposed include: (a) issuing the host a one-time "host token" at Create time instead of re-checking `UserUUID` per connect attempt (rejected as a new identity mechanism beyond Blocker 2's already-accepted trusted-`UserUUID` stance, not clearly needed since `host_actor_id` is immutable in V1); (b) a single `GET /ws` endpoint with a `role` parameter instead of a distinct route (left as Implementation Freedom, not a material question).
2. **Where `ResolveHost` lives**: proposed as a new file in `play/sessionruntime` (the same package that already reads `sessions`/`session_interactions` directly for post-commit event translation), not a new `sessionlifecycle.Manager` method. This keeps `Manager`'s public surface/signatures untouched (this WORK's existing Out-of-Scope constraint) and matches GAME-ADR-0005's "Session Runtime decides whether this User is represented by a SessionActor in this Session, whether that actor is the host." If a new `Manager` method is preferred instead (e.g. for symmetry with `Start`'s own check, or to avoid a second place implementing the same comparison), say so.
3. **No idempotency key for host connect**: proposed because connecting mutates no durable state (unlike Join, which persists a Participant row) - there is nothing to deduplicate. Confirm this asymmetry is acceptable.
4. **Known, not-newly-introduced gap left unresolved**: a participant's `Join` can still complete (persisting an active Participant) immediately before a same-request WebSocket upgrade failure leaves it with no bound connection - this already exists in the currently-implemented Blocker-7 design and is not fixed by this revision; recovery is an already-available retry, full resolution belongs to WORK-0015 (Disconnect/Reconnect/Full Resync). Confirm this is acceptable to continue deferring rather than folding into WORK-0005's own scope now.
