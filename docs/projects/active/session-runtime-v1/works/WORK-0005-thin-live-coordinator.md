## Outcome

A real client can connect over a live transport and exercise Create -> Join -> Start -> answer-one-interaction against a real `sessionlifecycle.Manager`, with the interaction Session Runtime opens delivered to the connected client and the client's answer delivered back to Session Runtime - proving the actual live path works, not just the Go-API surface Slices 1-3 already validated.

This is deliberately the thinnest transport slice that proves that path. It must not grow to include disconnect grace/debounce, semantic presence, timer scheduling/reconciliation, an inactivity reaper, full process-loss recovery, or advanced reconnect semantics - all explicitly deferred to Slices 5-8 per `PLAN.md`.

## Context

Slices 1-3 (WORK-0001, WORK-0003, WORK-0004) are DONE: `sessionlifecycle.Manager` exposes `Create`/`Join`/`Leave`/`Start`/`AnswerInteraction`, all Go-API-level (typed parameters, typed `engine.Value` answers, no wire/DTO decoding, no transport). No HTTP or WebSocket server exists anywhere in the repository yet - `main.go` only opens Postgres and runs migrations. `api/` exists as a package with only a README describing the general external-transport-edge convention; it contains no Go code. `play/` exists as a directory with no files at all, not even a README - `PLAN.md`'s own drift notes flagged it as "the most plausible future home" for a Coordinator, without an accepted decision committing to that.

GAME-ADR-0002 already accepts the Live Session Coordinator as a responsibility boundary (ephemeral connection binding, delivery/fan-out, physical disconnect detection, physical timer scheduling - owning no authoritative truth), and that V1 may keep it in the same Go process using local maps/channels/goroutines, never Redis or distributed routing. GAME-ADR-0020 already accepts that delivery is best-effort against already-durable Session Runtime truth: a RuntimeTurn commits first, live delivery happens only after, a delivery failure never reopens or rolls back anything, and V1 introduces no durable delivery outbox/ACK mechanism. Resync (GAME-ADR-0010) - reconstructing a player-facing projection for a client that missed live delivery - is explicitly Slice 7 scope, not this slice's.

Identity has no implementation (`identity/CURRENT_STATE.md`): there is no capability anywhere in the repository that resolves a real credential into an authenticated `UserUUID`. Slice 1 already faced the same gap for its plain Go-API callers and settled it by having trusted callers supply `UserUUID` directly, explicitly avoiding any temporary fake-auth mechanism that would later need removal. This slice introduces the first actual external-facing connection boundary in the repository and needs its own explicit answer to the same question for a live connection specifically (see Blocker 2).

## Scope

### In Scope

- Three components, split by responsibility and dependency direction (resolved, see Blockers):
  - **`api/` - WebSocket transport (stateless/dumb).** Owns the HTTP upgrade handshake and one read-pump/write-pump goroutine pair per connection. Decodes/encodes wire JSON, forwards decoded client commands to `play`, forwards outbound messages from `play` back to the socket. Holds no Session/connection registry and no business state. Depends only on `play`'s exported API (never on any `game/...` package), consistent with `api/README.md`'s existing "user-facing transport endpoints"/"transport-level concerns" charter.
  - **`play` - Live Session Coordinator (stateful), a new top-level package.** The conceptual GAME-ADR-0002 Coordinator - itself already framed as a boundary "outside Session Runtime" - lives as a top-level package, a sibling of `game/`, `api/`, `identity/`, not nested inside any of them. Its exported API - the methods and struct types other packages call/reference - declares a `SessionRuntime` interface and uses only primitive/`play`-owned types (`string`/`time.Time`/`play`'s own result structs) for everything crossing that boundary, never a `game`-package type. `play`'s own package (the `play` import path itself) imports no other domain package. It owns an in-process, per-Session registry of bound connections (channel-based, per GAME-ADR-0002's accepted local-maps/channels stance), binds a **participant** connection to `(SessionUUID, UserUUID)` per Blocker 2, binds a **host** connection to `SessionUUID` alone in a structurally separate registry slot per the 2026-09-20 Host Connection Design Revision (Blocker 8), and translates a decoded client command into a call against the `SessionRuntime` interface.
  - **An implementation of `play`'s `SessionRuntime` interface** that actually calls the existing, unmodified `sessionlifecycle.Manager` and translates between `play`'s primitive types and `Manager`'s semantic types (`SessionUUID`, `UserUUID`, `JoinResult`, `engine.Output`, etc.) in both directions - including translating a committed `Manager` call's resulting `OpenQuestionOutput`/`CloseQuestionOutput` (scope per Blocker 4) into the primitive event values `play` fans out. This implementation is expected to import `game` - that is normal and required, since it is the piece whose whole job is bridging to `game`'s real types. Where it physically lives (a subpackage under `play/`, e.g. `play/sessionruntime`, or elsewhere) is Implementation Freedom; what matters is that it is not the `play` package itself, so `play`'s own imports/exported API stay clean.

### Dependency Direction (Why This Split Matters)

The rule is about `play`'s own package and its exported API, not about every file anywhere under the `play/` directory: the `play` package itself imports no other domain package, and every type its exported methods/structs expose is `play`-owned or a primitive - never a `game` type. The concrete implementation of `SessionRuntime` is expected to import `game` (it has to, to call `sessionlifecycle.Manager` and translate its real types) - that is normal and does not violate the rule, as long as it isn't part of `play`'s own exported surface. `game` itself imports nothing from `play` or `api`, and `api` imports only `play`'s exported API. This is what avoids a circular dependency between `play` and `game`, and is what makes them swappable to separate deployment units later: moving from an in-process call to a network call means replacing the `SessionRuntime` implementation with an HTTP/gRPC client - no change to `play`'s own exported API, hub/registry/fan-out logic, or to `game` at all.

### Out of Scope

- Disconnect grace/debounce, semantic presence tracking/recovery, reconnect handling, and the resync read capability (Slice 7, GAME-ADR-0010/0015/0016).
- Physical timer scheduling/reconciliation (Slice 5, GAME-ADR-0008/0013).
- An inactivity reaper (Slice 8, GAME-ADR-0014).
- Any change to `sessionlifecycle.Manager`'s existing business logic, method signatures, or persistence model - this slice adds a transport layer in front of it, nothing inside it changes.
- Real credential verification / Identity implementation - this slice extends the same trusted-caller stance Slice 1 already established (see Blocker 2), it does not build Identity/Auth.
- A client that connects to a Session already `RUNNING` with a pre-existing open interaction seeing that interaction live - with no resync capability until Slice 7, such a client simply receives no further messages until it exists, per `PLAN.md`'s own explicit framing of this slice's exclusions ("a client that disconnects simply stops receiving further messages until Slice 7 exists").
- Multi-instance/distributed delivery, Redis, sticky routing (already excluded from all of V1 by GAME-ADR-0002, not specific to this slice).

## Approved Design

Beyond canonical context, this WORK settles:

- **`play` owns the port; a separate implementation owns the bridge to `game`.** `play`'s own package declares the `SessionRuntime` interface (or equivalent name) it depends on, and every type in `play`'s exported API (interface methods, exported structs) is primitive or `play`-owned - no `game` package (`sessionlifecycle`, `engine`, etc.) is ever referenced by anything `play` exports. The concrete implementation of that interface is expected to import `game` and call `sessionlifecycle.Manager` in-process - that is normal, not a violation, as long as the implementation itself isn't part of `play`'s own package/exported surface. This is a deliberate dependency-inversion boundary to avoid a `play`<->`game` circular dependency, not incidental structure: it is what lets `play` and `game` later become separate deployment units by swapping only the `SessionRuntime` implementation.
- **No shared database transaction, or database handle at all, between `play` and `game`.** `play` never receives, stores, or passes through a `*gorm.DB`/transaction handle; every mutation it triggers happens by calling the `SessionRuntime` interface, and the implementation's own call into `sessionlifecycle.Manager` owns that call's entire transaction scope exactly as it already does today, entirely on the `game` side of the boundary.
- **Durable commit remains the correctness boundary.** A `Manager` call's transaction must fully commit (inside the `SessionRuntime` implementation, on the `game` side of the interface) before any Output resulting from it is translated into a `play`-owned event and delivered live; a delivery failure afterward never rolls back, reopens, or otherwise reinterprets the committed Session state (GAME-ADR-0020). This slice adds no compensating/retry logic for a failed delivery.
- **No new persistence.** This slice adds no migration, no connection-presence column, no delivery outbox, and no ACK table. Connection state is ephemeral, in-process Go state, not Session Runtime persistence.
- **`sessionlifecycle.Manager` is called, never reimplemented.** The `SessionRuntime` implementation is a caller of the Manager's existing public methods, exactly as a future HTTP handler would be; it owns no lifecycle/admission/execution policy itself, and neither does `play`.
- **The Host obtains a live connection independent of Participant status (2026-09-20 revision, resolves Blocker 8).** A distinct host-connect handshake and a structurally separate `play.Coordinator` registry slot let the Session host obtain a bound live connection and issue `Start` without ever calling `Join` or being represented by a `session_participants` row. See "Host Connection Design Revision (2026-09-20, DRAFT PROPOSAL)" below for the full design; this does not alter Blockers 1-7's already-approved design for Create/Join/Start/AnswerInteraction/delivery.

## Constraints and Invariants

- `game` imports nothing from `play` or `api`. `api` imports only `play`'s exported API, never `game`. `play`'s own package imports no other domain package, and nothing `play` exports (interface methods, exported struct fields) references a `game` type. The concrete `SessionRuntime` implementation may and normally does import `game` - that dependency direction (implementation -> game, never `play`'s own package -> game) is what avoids a `play`<->`game` cycle, not an absolute ban on `game` appearing anywhere under the `play/` directory.
- `play` never holds a `*gorm.DB`, a transaction handle, or any other Session Runtime persistence reference of any kind.
- No Coordinator/client-visible output is ever delivered before its causing transaction has durably committed (GAME-ADR-0020, already-established Start/AnswerInteraction behavior).
- A delivery failure, a disconnected client, or a Coordinator/process crash immediately after commit must never be treated as a reason to reverse, retry against, or reinterpret the already-committed Session state.
- No authoritative connection-presence field (`is_connected`, `connection_id`, `websocket_id`, or equivalent) is added to any Session Runtime persistence (GAME-ADR-0003) - this slice does not yet implement `semantic_presence` at all (that is Slice 7).
- This slice must not implicitly grow into disconnect grace/debounce, timer scheduling, an inactivity reaper, or reconnect/resync handling - if implementation discovers one of these is unavoidable to make the thin path work, that is new information routed back through this WORK rather than silently implemented.
- **A bound host connection and a bound participant connection are structurally distinct registry entries**, even for the same `UserUUID` on the same Session; the participant-addressed `Deliver`/`Event.Recipient` fan-out path never reaches a host-connection entry, and vice versa. No host-targeted fan-out exists in this WORK's own scope (see Out of Scope) - the separation exists so a future one (WORK-0006/WORK-0008) has a place to target without a registry redesign, not because this WORK delivers anything to it yet.
- **No connection-role claim made by a client at connect time is trusted as command authorization.** `sessionlifecycle.Manager`'s own per-command checks (`host_actor_id` for `Start`, recipient identity for `AnswerInteraction`) remain the sole authoritative enforcement, unchanged by the 2026-09-20 revision. The host-connect handshake's own validation (`ResolveHost`) protects the connection slot itself (so an arbitrary caller cannot occupy or hijack it, or later receive host-targeted fan-out) - it is a defense-in-depth/UX boundary, not a replacement for Manager's authority.

## Acceptance Criteria

- A client can connect, create a Session, join it, start it, and receive the interaction opened by Start's first RuntimeTurn, entirely over the live transport.
- Submitting a valid answer over the live transport results in a new RuntimeTurn committing (exactly as `AnswerInteraction` already guarantees at the Go-API level) and the connected client(s) receiving whatever further `Output`s that Turn produces, per Blocker 4's resolved scope.
- No Output is ever observed by a client before its causing transaction has committed - provable by a test that fails a delivery attempt (or observes ordering directly) and confirms the durable Session state is already correct regardless.
- Disconnecting a client mid-Session does not affect Session Runtime's durable state in any way (no Participant deactivation, no termination, no error) - it simply stops receiving further messages, per this slice's explicit exclusion of disconnect handling.
- `go list -deps ./play` (the root `play` package only, not its subpackages) contains no `game/...` package, and `go list -deps ./game/...` contains neither `play` nor `api` - the dependency-inversion boundary is real, not merely described in comments. A subpackage implementing `SessionRuntime` (if that is where Implementation Freedom places it) is expected to depend on `game` and is not part of this check.
- `go build ./...`, `go vet ./...`, and `go test ./... -count=1` pass, with no new failure introduced beyond the already-recorded out-of-scope `getgame` JSONB-comparison test defect.
- **(2026-09-20 addition, resolves Blocker 8)** A host can obtain a bound live connection (`session_uuid` + `user_uuid`, no `join_code`) and issue `Start` without becoming a Participant - provable by connecting as host, sending `START`, and confirming no `session_participants` row was created for that `UserUUID`.
- A `UserUUID` that is not the Session's host is declined (`NOT_HOST`) when attempting the host-connect handshake, with no upgrade.
- A host connection that sends `ANSWER_INTERACTION` receives an `ERROR` reply and causes no `Coordinator`/`SessionRuntime`/`Manager` call.
- The existing Create -> Join -> Start -> receive-interaction -> answer -> receive-resolution end-to-end proof is re-demonstrated with the host connecting via the host handshake (never joining) and a separately-joined Participant receiving/answering the opened interaction.

## Implementation Freedom

- Exact name/shape of `play`'s `SessionRuntime` (or equivalently named) port interface and its request/response DTOs, and exactly where its concrete implementation lives - a subpackage under `play/` (e.g. `play/sessionruntime`), a package elsewhere, or directly in `main.go`'s wiring - as long as it is not part of `play`'s own package/exported surface and the dependency direction in this WORK's Constraints holds.
- Exact shape of the in-process per-Session connection registry (a map guarded by a mutex, one goroutine per Session, or another concurrency-safe structure), subject to `docs/engineering/standards/`.
- Exact Go type/package/file names for the new transport/coordinator code, subject to `repositories.md`/`domain-logic-placement.md`/`function-signatures.md`.
- Test structure/fixtures, following `testing.md` and the existing Slice 1-3 test layout; a live-transport test may use an in-process test client/server rather than a real network socket where that is sufficient to prove the required behavior. `play`'s own hub/registry/fan-out tests should mock the `SessionRuntime` interface rather than exercising a real `sessionlifecycle.Manager`, since `play` itself never depends on it.
- **(2026-09-20 addition)** Exact route shape for the host handshake (`GET /ws/host`, or a single `GET /ws` branching on an explicit `role` query parameter, or another shape) - the requirement is only that Session performs the semantic host check before upgrading, not any particular URL structure. Exact Go naming/shape of the new `SessionRuntime.ResolveHost` capability, `Coordinator.ConnectHost`/`BindHost`, `HostConnectOutcome`, and the host registry's data structure, subject to the Constraints above (structurally distinct from the participant registry). Whether the host connection receives its own outbound acknowledgment message type (recommended, mirroring `JOIN_RESULT`) is likewise Implementation Freedom.

## Blockers

Status: Blockers 1-7 are **RESOLVED, HUMAN-APPROVED** and unaffected by this revision. Blocker 8 is **PROPOSED, AWAITING HUMAN APPROVAL** as of the 2026-09-20 revision below - WORK-0005 cannot return to READY until a human approves (or redirects) Blocker 8's proposed resolution. Each item below shaped a pattern later slices inherit (Slice 5's timer scheduling and Slice 7's disconnect/reconnect both explicitly extend this same Coordinator rather than inventing a new one), so none was silently decided here.

1. **Where does the Coordinator/live-transport code live, and what is the exact dependency rule between `play` and `game`?** **Resolution: RESOLVED, HUMAN-APPROVED (revised twice on 2026-09-20, superseding this WORK's own first two passes).** Pass one proposed nesting the stateful Coordinator inside `game/` (`game/play/`); the human corrected this to a top-level `play` package instead, so `play` and `game` could later become separate deployment units by swapping an in-process call for a network call - which requires `play` not to depend on `game` types, and no shared database transaction between them. Pass two initially over-specified this as "no `game` import anywhere under `play/`'s directory tree, adapter must live outside it entirely"; the human refined this to the precise rule actually needed: **`play`'s own package and its exported API (interface methods, exported struct types) must depend only on primitives/`play`-owned types and must never import or reference `game`** - but the concrete implementation of the `SessionRuntime` interface `play` declares is expected to import `game` (it has to, to call `sessionlifecycle.Manager` and translate its real types), and that implementation may live anywhere, including a subpackage under `play/` - it is simply not part of `play`'s own package or exported surface. This is the precise rule that breaks the circular-dependency risk without over-constraining where implementation code physically lives. **Final resolution**: `play` is a new **top-level** package, a sibling of `game/`, `api/`, `identity/`. The WebSocket transport adapter stays in `api/` as before, depending only on `play`'s exported API. See this WORK's Approved Design/Constraints and Scope's "Dependency Direction" subsection for the precise rule. This choice also decides where Slice 5's timer-scheduling extension and Slice 7's disconnect/reconnect extension both land (inside `play`, behind the same `SessionRuntime` boundary), since both explicitly extend this same Coordinator rather than building a second one.
2. **V1 connection authentication / `(SessionUUID, UserUUID)` binding with no Identity implementation.** `game/README.md` requires an already-trusted `UserUUID` before Session Runtime ever sees a caller ("the external client is not the trusted source of `UserUUID`"), but Identity has no implementation anywhere. Slice 1 already resolved the analogous problem for its plain Go-API method calls: trusted callers supply `UserUUID` directly, no temporary fake-auth mechanism. **Resolution: APPROVED as proposed.** This slice extends that exact same stance to the live connection handshake - the client supplies `UserUUID` directly at connection time (for example a query parameter or an initial handshake message), with real credential verification explicitly deferred to a future Identity/Auth slice, exactly as every Go-API caller already does today. This sets no new identity precedent; it is a live-transport-shaped instance of the one precedent Slice 1 already established.
3. **Which operations ride the live connection itself, versus ordinary request/response?** `PLAN.md`'s Slice 4 scope describes "translating Slice 1-3's existing Session application operations into transport requests" without specifying the transport shape per operation. **Resolution: APPROVED as proposed, later revised for `Join` by Blocker 7 below.** `Create` and `Join` happen before any live connection exists (a host creates a Session, a player scans a join code) and stay ordinary HTTP request/response; only `Start`, `AnswerInteraction`, and the resulting `Output` fan-out - the operations that need to be correlated with an open connection expecting live delivery - ride the WebSocket. **Superseded for `Join` (see Blocker 7)**: `Join` turned out to also need to be correlated with an open connection - a client that only called HTTP Join was a persisted Participant with no bound connection, silently missing any Event addressed to it - so `Join` moved to being the WebSocket handshake itself rather than staying independent HTTP. `Create` is unaffected by that revision.
4. **Which engine `Output` variants are translated into client-facing fan-out messages, and their wire shape.** The engine currently produces nine committed `Output` variants (`OpenQuestionOutput`, `CloseQuestionOutput`, `ScheduleTimerOutput`, `CancelTimerOutput`, `EmitEffectOutput`, `ActivatePresentationOutput`, `UpdatePresentationOutput`, `RemovePresentationOutput`, `WorkflowCompletedOutput`). `PLAN.md`'s own Slice 4 Delivers line says only "at minimum whatever is needed to see an opened interaction and its resolution," leaving the rest ambiguous. **Resolution: APPROVED as proposed.** This slice translates and fans out exactly `OpenQuestionOutput`/`CloseQuestionOutput` - the minimum needed to prove the live path end-to-end - and silently ignores every other variant for now (no error, no partial translation): `ScheduleTimerOutput`/`CancelTimerOutput` have no consumer until Slice 5 exists, `EmitEffectOutput`/the presentation-shaped Outputs are explicitly best-effort/droppable presentation effects under GAME-ADR-0020, and `WorkflowCompletedOutput` has no accepted client-facing meaning defined anywhere yet. The fan-out DTO itself must not leak internal engine identities (`engine_path`, `Slot`, `SessionActorID`) - a recipient (`engine.UserID`) must be translated back through Session Runtime to the caller-facing identity the client already supplied (its own `UserUUID`), mirroring the same non-leakage principle already accepted for `game/README.md`'s (not-yet-built) resync projection, even though resync itself remains Slice 7's.

5. **Who constructs the fully-wired `play.Coordinator` (`sessionlifecycle.Manager` + `play/sessionruntime.SessionRuntime` + `play.NewCoordinator`) - `main.go`, or `api` itself?** Raised after this WORK's own implementation report, during a follow-up review of `api`'s internal organization. The original implementation had `main.go` build every layer (Manager, `SessionRuntime`, `Coordinator`) and hand `api.NewServer` the finished `*play.Coordinator`, so `api`'s own import graph never touched `game`, not even transitively - matching Blocker 1's rule as originally written above ("`api` imports only `play`'s exported API, never `game`"). **Resolution: HUMAN-APPROVED, revising that rule.** `api` is the external transport/application edge for the whole system, reasoned about as if it were eventually its own deployed service; under that framing it should own knowing how to construct/reach every capability it talks to, receiving only genuinely shared infrastructure (today, the database handle) from its caller - the same way a real gateway service would own its own downstream-client bootstrap rather than have that handed to it fully assembled. `api.NewServer` now takes `db *gorm.DB` and calls a new `play/sessionruntime.NewCoordinator(db)` constructor internally, so `api`'s build graph now transitively includes `game` packages (verifiable via `go list -deps ./api`). This does **not** reopen Blocker 1's actual dependency-inversion boundary: `play`'s own root package still imports no `game` package (`go list -deps ./play` unchanged), `game` still imports nothing from `play` or `api`, and `play`'s exported API still references no `game` type - the swappability the boundary exists to protect (replacing the in-process `SessionRuntime` implementation with a network client without touching `play`'s own package) is untouched, since that swap still only ever means changing what `sessionruntime.NewCoordinator` (or its future network-client equivalent) does internally, not `play` itself. What changed is narrower: `api` may now depend on `game` transitively through its own composition/wiring code, though `api`'s actual handler/business logic still never references a `game` type directly - it only ever calls through `play.Coordinator`.

6. **No layer in this WORK's implementation ever actually started a request log.** `game/session/workflows/sessionlifecycle.Manager` (from earlier slices) already called `logging.Step`/`logging.LogFields` at every exported method, correctly assuming its caller's context already carried a started log - but nothing in this WORK's own new code (`play.Coordinator`, `play/sessionruntime.SessionRuntime`, or `api`'s handlers) ever called `logging.Start`, and `logging.Step`/`LogFields` silently do nothing without one. The result: every request through the entire live-transport path produced zero log output, with no error or signal that anything was missing. **Resolution: HUMAN-APPROVED**, raised directly against the implemented code rather than during design. `docs/engineering/standards/logging.md` (new) now states the rule this WORK's implementation should already have followed: only an entry-point package - today, only `api` - calls `logging.Start`/`defer logging.FinishRequestLog`; every other package (domain workflow, coordination layer, adapter) assumes its context already carries one and only ever calls `logging.Step`/`LogFields`/`LogError`. Fixed by adding `logging.Start`/`defer logging.FinishRequestLog` to `api/session`'s HTTP handlers, WebSocket connect/disconnect events, and - since a long-lived WebSocket connection carries many independent exchanges, not one - each individual inbound WS message; and by adding the same `logging.Step`/`LogFields` pattern `sessionlifecycle.Manager` already used to `play.Coordinator`'s and `play/sessionruntime.SessionRuntime`'s own exported methods, so the resulting log nests all the way from the HTTP/WS entry point down through Coordinator, SessionRuntime, and Manager in one flushed structured line per request. Verified against real Postgres: every Create/Join/WS-connect/WS-message/WS-disconnect now produces a fully nested `slog` line (confirmed by inspecting actual test output, not merely by code inspection).

7. **Should Join stay ordinary HTTP request/response, independent of the live connection?** Raised directly against Blocker 3's own resolution above, after reviewing the implemented code: a client that called HTTP Join successfully but never separately opened `GET /ws` was a persisted, active Participant the Coordinator had never bound a connection for - `Coordinator.Deliver` silently drops an Event addressed to a recipient with no bound connection (this package's own accepted best-effort/no-resync stance), so such a player could miss the very first interaction Start opens, with nothing anywhere signaling that the two required calls were never both made. **Resolution: HUMAN-APPROVED, revising Blocker 3.** The frontend should not need to know that "join a session" is actually two independently-failable network operations it must both remember to perform in order - a single logical client action should be a single call with a single outcome. `Join` no longer has an HTTP endpoint. `GET /ws` now takes `join_code` (not `session_uuid`) plus `user_uuid`/`display_name`/`idempotency_key`, calls `Join` first, and only upgrades and binds the connection when the outcome means an active Participant (`JOINED`, or the idempotent-replay-shaped `ALREADY_JOINED` - the same path a client reconnecting with a fresh idempotency token after a drop takes); a genuine decline or error is reported over plain HTTP with no upgrade at all, since nothing worth connecting for happened. `Create` is unaffected - it has no connection to pair with, since no Participant/connection exists to bind until Join. This does not fuse Join and Bind into one `play.Coordinator` method: `Bind` requires an actual live socket, which only exists after `Coordinator.Join` has already returned successfully and the HTTP connection has been upgraded, so the two Coordinator calls are still sequenced by `api/session`'s own handler - what changed is that this sequencing now happens behind one client-facing endpoint instead of being the client's own responsibility to perform correctly across two separate calls. Reconnection after `RUNNING` starts (once the JoinCode is revoked) remains unsolved by this mechanism and stays Slice 7's resync scope, exactly as already accepted - this only closes the LOBBY-phase join/connect consistency gap, not the broader reconnect story.

Local implementation choices (exact WebSocket library, connection-registry data structure, package/file naming) remain Implementation Freedom and are not blockers.

## Host Connection Design Revision (2026-09-20, DRAFT PROPOSAL - historical; ownership transferred to WORK-0020)

It does not re-open Blockers 1-7, all still HUMAN-APPROVED and structurally unaffected - Create, participant Join+connect, `AnswerInteraction`, and the existing participant-addressed `Deliver` fan-out are unchanged by everything below.

### Problem Recap

The implemented `GET /ws` unconditionally calls `Join` before upgrading, so a host who has not otherwise joined must go through `Join` (consuming a `playersMax` slot, creating a `session_participants` row) purely to obtain a connection through which to send `Start` - contradicting `game/README.md`'s accepted "Host and Participant are independent concepts" invariant. `sessionlifecycle.Manager`'s own domain logic already keeps Host and Participant correctly independent (`CreateSessionWithHost` creates no Participant for the host; `Start`'s authorization checks `sessions.host_actor_id` via `FindActor`, never Participant status) - the drift is transport-layer only.

### Revised Model

- **Two independent live-connection kinds** bind against the same `play.Coordinator`, distinguished by role, never conflated: a **host connection** and a **participant connection**. The same person (`UserUUID`) may hold both simultaneously as two separate connections/registry entries - never one connection wearing two hats.
- **Host connect handshake.** A new connect path (`GET /ws/host` recommended; exact route shape is Implementation Freedom) takes only `session_uuid` and `user_uuid` - no `join_code`, `display_name`, or `idempotency_key`, since connecting a host mutates no durable state and creates no Participant row. Before upgrading, the handshake calls a new `play.Coordinator.ConnectHost(ctx, sessionUUID, userUUID)`, which calls a new `play.SessionRuntime.ResolveHost(ctx, sessionUUID, userUUID)` port method. `ResolveHost`'s concrete implementation lives in `play/sessionruntime` (same package/pattern as the existing post-commit `eventsForCommittedTurn` read in `query.go` - proposed as a new sibling file, e.g. `host.go`): a pure read that resolves `sessions.host_actor_id` for the given Session and compares it against the `SessionActor` matching `(SessionUUID, UserUUID)` - the same check `sessionlifecycle.Manager.Start` already performs internally (`FindActor` + compare to `HostActorID`), restated read-only rather than duplicated as a new authorization rule. No change to `sessionlifecycle.Manager`'s method signatures, business logic, or persistence model - consistent with this WORK's existing Out-of-Scope constraint. This placement is also consistent with GAME-ADR-0005: "Session Runtime decides whether this User is represented by a SessionActor in this Session, whether that actor is the host" - the check stays on the `game` side of the `play`/`game` boundary, never reimplemented in `play`, `api`, or the transport layer.
  - Outcome: `HOST_CONFIRMED` (upgrade proceeds, connection is bound) or `NOT_HOST` (declined over plain HTTP, no upgrade - symmetric with the existing participant-Join-decline pattern: "nothing worth connecting for happened"). An unknown `session_uuid` declines with the existing `play.ErrSessionNotFound`.
  - No idempotency key is needed: unlike Join, connecting the host performs no mutation and creates no durable row, so there is nothing to deduplicate against a retried connect attempt.
  - An unlocked read is sufficient (no transaction/row lock): `host_actor_id` is set once at Create and never reassigned in V1 (`game/README.md`: "V1 does not introduce separate mutable creator and host concepts... Host transfer is not currently designed") - there is no window in which this read can observe a stale value that later matters, and `Start` re-validates authoritatively regardless.
- **Participant connect handshake.** Entirely unchanged from Blocker 7's already-approved resolution (`GET /ws` with `join_code`/`user_uuid`/`display_name`/`idempotency_key`, Join-then-bind as one operation). This revision touches nothing about it.
- **Connection registry / binding.** `play.Coordinator` gains a second registry alongside the existing per-Session participant map (`sessions map[SessionUUID]map[UserUUID]Conn`): a per-Session single host-connection slot (e.g. `hosts map[SessionUUID]Conn`), bound via a new `Coordinator.BindHost(sessionUUID, conn) (unbind func())` mirroring the existing `Bind`'s replace-outright/no-grace-period semantics (a Session has exactly one live host connection at a time; a second host-connect attempt for the same Session simply replaces the first, exactly like a participant reconnect does today). Keeping this a **structurally separate** registry - not a role-tagged entry inside the existing participant map - is what makes it mechanically impossible for a bound host connection to be mistaken for, or accidentally receive, participant-addressed fan-out (`Deliver`'s existing `Event.Recipient`-keyed lookup is untouched and continues to only ever reach the participant registry), and gives future host-targeted delivery (WORK-0006's Presentations/Effects, WORK-0008's live lobby) a natural, already-separated place to target without a registry redesign then.
- **Command boundary.** A host connection's read pump only ever dispatches `START` (today; WORK-0011's future `CANCEL` would join it) to `Coordinator.Start`. `ANSWER_INTERACTION` received on a host connection is rejected transport-side with an `ERROR` message (no participant identity exists on that connection to attribute an answer to), never forwarded to Coordinator. A participant connection's read pump is unchanged (still dispatches both `START` and `ANSWER_INTERACTION` exactly as today).
- **Layered authorization, not transport-trust.** The connection-role split is a routing/UX/future-delivery-targeting boundary, not the sole security boundary: `sessionlifecycle.Manager.Start` already independently re-validates `userUUID` against `sessions.host_actor_id` on every call regardless of which connection or route it arrived through (`step_start.go`'s existing `NOT_HOST` outcome), and `Manager.AnswerInteraction` already independently validates the interaction's actual recipient. So even in a hypothetical bug/race where a non-host connection reached `Coordinator.Start`, Manager would still authoritatively decline it with `NOT_HOST`. The host-connect handshake's own validation protects the *connection slot itself* (so an arbitrary caller cannot occupy/hijack the host's live-view connection or later receive host-targeted fan-out merely by claiming the role) - it is defense-in-depth, not a replacement for Manager's authority. This directly answers the requirement that "the transport must not accidentally allow an arbitrary user to claim a Host connection merely by providing a Session UUID and User UUID."
- **Host becoming a Participant.** Structurally unaffected and already possible without further design work: the same person's `UserUUID` can also complete the ordinary participant `GET /ws` handshake (with a `join_code`), producing a second, independent `Bind` entry in the participant registry alongside their separate host-connection entry - two connections, two lifecycles, never fused into one. Not exercised by this WORK's own Acceptance Criteria; recorded here only to confirm the model does not block it, since a future product decision might want it.

### Failure Semantics

- Host connect declined (`NOT_HOST`) or Session not found: reported over plain HTTP, no upgrade - symmetric with the existing participant-Join-decline pattern. Nothing is left dangling, since no row is ever created for a host-connect attempt, successful or not.
- Host connect passes validation but the WebSocket upgrade itself then fails (rare - a malformed/dropped upgrade handshake): strictly safer than the equivalent participant case, since no durable state was created to leave orphaned - the caller simply retries the same host-connect handshake, no cleanup concern.
- Participant Join-then-upgrade-fails (pre-existing, **not** introduced or fixed by this revision): a Join can still complete (persisting an active Participant) immediately before a same-request upgrade failure leaves it with no bound connection. This gap already exists in the currently-implemented Blocker-7 design and is out of this revision's scope to fix; recovery is an already-available retry (a fresh `GET /ws` attempt with the same `idempotency_key` returns `ALREADY_JOINED` and binds). Full resolution belongs to WORK-0015 (Disconnect/Reconnect/Full Resync). Named explicitly here so it is not mistaken for a new gap this revision introduces.

### Blocker 9 (found and resolved during independent review, 2026-09-21): standalone logging bypassed the project's own logging package

**Discovery**: while reading this WORK's implemented code for its still-pending independent review, `api/session/ws.go`'s `writePump` (a WS write failure) and `play/coordinator.go`'s `Coordinator.Deliver` (a best-effort delivery failure to one recipient) were both found calling the standard library's `log.Printf` directly instead of this repository's own `logging` package - the exact "server-initiated push... this standard does not yet resolve" gap `docs/engineering/standards/logging.md` already flagged as open. Neither call site has a request-scoped `context.Context` available to log under: `writePump` runs in a goroutine with no owning request (it drains sends caused by other connections' `Deliver` calls, not only its own connection's read pump), and `Coordinator.Deliver` fans out to potentially many recipient connections at once, so no single request could correctly own the log. The `logging` package had no non-request-scoped logging capability at all, so `log.Printf` was the only option available at implementation time - not an oversight of an existing capability, a genuine missing one.

**Resolution: HUMAN-APPROVED, resolved same-session.** Added `logging.LogStandalone(logger, tags, message, fields...)` to the `logging` package - the one function in that package that may be called without a request-scoped `ctx`. It requires at least one tag (a fixed, low-cardinality field such as `"websocket"`/`"session"`/`"delivery"` identifying where in the system the log came from), defaulting to `"untagged"` rather than silently permitting an untagged standalone log, per the human's explicit direction that a standalone log path is inherently risky and must stay filterable. See `docs/engineering/standards/logging.md`'s new "Standalone Logs (No Request Context)" section for the full rule. Both call sites now use it: `writePump` tags `{"websocket", "session"}`, `Coordinator.Deliver` tags `{"delivery", "session"}` (not `"websocket"` - `play` is deliberately transport-agnostic per this WORK's own dependency-inversion boundary, and tagging it with a specific transport would leak that assumption into it). Added `TestLogStandaloneWritesTaggedStructuredLog`/`TestLogStandaloneDefaultsMissingTags`/`TestLogStandaloneNoopWhenLoggerNil` to `logging/request_log_test.go`.

**Scope note**: a repository-wide check found two other `log.Printf`/`fmt.Println` call sites (`main.go`'s process-bootstrap logging; `monitoring/alerts.go`'s already-TODO-flagged alert-forwarding stand-in) and one in `game/language/v1/example.go` (an explicitly-marked, non-compiling draft/scratch file, not production code). None were changed: `main.go`'s calls happen before any request or `logging` machinery exists (reading env vars, opening Postgres, starting the HTTP listener) and are process-lifecycle diagnostics, not application/request logging - a different category this fix does not claim to cover. `monitoring/alerts.go` already logs through `logging.LogFields` and only additionally `fmt.Println`s pending a real alerting integration it already documents as a TODO - unrelated to this gap.

**Verification**: `go build ./...`, `go vet ./...`, `gofmt -l` (changed files) all clean; `go test ./logging/... ./api/... ./play/... -count=1` passes, including the three new `LogStandalone` tests.
