# ADR-0014: Game Management / Session Runtime Domain Split, Game Language Internalized Into Session Runtime

Status: ACCEPTED
Created: 2026-09-27
Last status change: 2026-09-27
Supersedes: None
Superseded by: None

## Context

`GAME-ADR-0001` accepted one Game bounded context containing Game Management and Session Runtime as internal capabilities, with Game Language as a shared supporting technical subsystem used by both. Session Runtime was accepted to depend on Game Management only through a narrow read capability (`gameCurrentVersionReader`/`gamePinnedDefinitionReader`), never on Game Management's repository directly.

A review of the implemented `sessionlifecycle` package (`game/session/workflows/sessionlifecycle`) found that this narrow-contract rule was satisfied at the interface-declaration level but not at the return-type level: `management.GetPlayableGameWithCurrentVersion`/`GetGameDefinition` return `*management.Game` (`game/management/models.go`), which itself embeds `program.Definition` (Game Language). Every one of Session Runtime's seven RuntimeTurn-capable operations (`Create`, `Join`, `Start`, `AnswerInteraction`, `SubmitUserIntent`, `CancelSession`, `ExpireTimer`) declares its own narrow consumer interface against this producer type, per `docs/engineering/standards/domain-logic-placement.md`'s consumer-driven-interface pattern — that part is correct. But the producer's own exported type is itself composed from a third package (Game Language) that Game Management does not conceptually own, so every one of those seven consumers transitively depends on Game Language merely to declare an interface against Game Management's contract.

Examining why revealed the deeper issue is not the return-type shape but which domain actually owns the compiled Game Language definition at runtime. Every one of those seven operations calls into Game Management at runtime — not once at Session creation, but on every single lifecycle/runtime operation for the Session's entire lifetime — solely to re-read the same immutable, already-pinned definition/version (`sessions.game_definition_uuid`) that never changes after `Create`. Game Management's actual business responsibility (authored-game lifecycle: visibility, publication state, images, ownership, authored history) never requires reading this data back once a Session exists; Session Runtime is the sole real consumer of the compiled definition at runtime, for the Session's entire lifetime.

`GAME-ADR-0001` itself already flagged, and explicitly deferred, "Persist a complete definition snapshot into every session immediately," reasoning that an immutable referenced execution version was sufficient and that a compiled-program cache was a valid *future* optimization "if runtime traffic or independent-deployment latency requirements make synchronous definition lookups costly." That framing treated per-runtime-call coupling as a performance/latency question. Re-examined now, it is instead a domain-ownership question: Game Language's compiled definition is not something Game Management incidentally stores and Session Runtime incidentally reads often — it is Session Runtime's own execution input, and Game Management's involvement with it (validating/decoding an authored script) is itself only in service of what Session Runtime will later execute.

## Decision

The "Game" bounded-context grouping (`ARCHITECTURE.md -> Accepted Business Boundaries`, `game/README.md`) is dissolved. Game Management and Session Runtime become independent business bounded contexts, siblings to Identity and to the other top-level domains already scaffolded at the repository root (`composer/`, `orchestrator/`, `identity/`, ...) — not internal capabilities of a shared "Game" context.

Game Language (`program`, `engine`, and their supporting packages, currently `game/language/v1/...`) is reclassified from a shared supporting subsystem of "Game" into Session Runtime's own internal implementation detail. It moves under Session Runtime's own package tree and is no longer a dependency Game Management may use.

Session Runtime gains its own persisted entity representing the executable Game Language artifact — the compiled/authored script content Session Runtime actually executes — owned entirely within Session Runtime's own persistence boundary, independent of Game Management's own `games`/`game_definitions` tables. This entity is keyed by the same immutable definition/version identity Session Runtime already pins to at `Create` (`sessions.game_definition_uuid`), not by the mutable Game UUID: a Game has many authored versions over its lifetime, each independently immutable once a Session is pinned to it (`GAME-ADR-0001`'s version-immutability invariant), so Session Runtime's own copy must be one row per immutable version, the same granularity Game Management itself already versions at, not one row per Game.

Game Management keeps its own `Game` entity — visibility, publication/status, name, description, ownership, images, authored-version history — with no dependency on Game Language and no column/type carrying compiled script content Session Runtime is the one to execute. Game Management and Session Runtime's respective entities correlate one-to-one per authored version through the same public Game/definition-version UUID identity already accepted as Game Management's cross-domain-referenceable identity (`ARCHITECTURE.md -> Cross-Domain Public Entity References`); this is intentional, accepted coupling to a published logical identity, not coupling to either domain's storage representation.

Direct domain-to-domain calls between Game Management and Session Runtime are removed entirely — no `sessionlifecycle` step calls into Game Management, and Game Management never calls into Session Runtime. Cross-domain composition uses the coordination layers `ARCHITECTURE.md` already accepts:

- **Create-time visibility composition** (a Session may only be created for a currently-playable/visible Game): moves to Composer (`composer/`), which reads Game Management's visibility first and only then calls Session Runtime's `Create`. Session Runtime's `Create` no longer reads Game Management at all; it assumes the caller (Composer) already authorized creation, and no longer requires a `gameCurrentVersionReader`-shaped dependency.
- **Publishing/authoring a Game** (writing a new authored version so both domains' representations of it agree — Game Management's visibility/metadata row and Session Runtime's own executable-definition row): becomes a cross-domain write workflow through Orchestrator (`orchestrator/`), validating the authored definition against Session Runtime's own Game Language before either domain persists it.

Neither cross-domain composition flow above is designed or implemented by this record. `Create`'s Composer-mediated visibility check and the Orchestrator-mediated publish/authoring workflow are each tracked as their own required future WORK (see Implementation Impact) — deliberately deferred, since neither Game-authoring/publishing nor Session Runtime's live-transport/application-edge layer exists yet in this codebase (`game/management` currently exposes only two read use cases, `getgame`/`getgamedefinition`; no create/publish use case exists to compose with yet).

## Rationale

The narrow-interface pattern (`docs/engineering/standards/domain-logic-placement.md -> A Workflow's Public Contract Lives At The Domain Root`) already correctly requires a *consumer* to declare its own interface against a *producer's* root-level types, importing only that producer's root package. That part of the existing pattern was correctly applied here (`gameCurrentVersionReader`/`gamePinnedDefinitionReader`) and required no fix. What was missing is the symmetric rule on the producer side: a producer's own exported type must not itself be composed from a type owned by a third domain/subsystem it does not conceptually own, or every one of its consumers transitively imports that third package regardless of how narrow their own interface is. `docs/engineering/standards/domain-logic-placement.md`'s Enforcement section and `ARCHITECTURE.md -> Dependency Principles` are updated by this record to state that rule explicitly, independent of this specific migration, since it is a reusable pattern gap, not only a Game-specific fact.

Fixing only the return-type shape (Game Management mapping `program.Definition` into some Game-Management-owned mirror type before returning it, the same translation shape `WORK-0029` already applied to `engine.Output`/`engine.Value` at the `sessionlifecycle`/Game-Language boundary) would satisfy that narrower rule but leaves the actual problem untouched: Session Runtime would still call into Game Management on every single runtime operation for the Session's entire lifetime, to re-read data that never changes after `Create` and that Game Management does not conceptually need back once authored. A translation-only fix treats the symptom; owning the data where it is actually and repeatedly consumed treats the cause, and is the more accurate application of `ARCHITECTURE.md -> Domain Boundaries`: "A Playhoot business domain must not directly invoke another Playhoot business domain's capabilities" already discourages exactly this per-operation direct-call shape, even when mediated through a narrow interface.

This also directly resolves `GAME-ADR-0001`'s own deferred question about a "compiled-program cache keyed by an immutable definition UUID," which correctly anticipated the mechanism (a Session-Runtime-owned copy keyed by immutable version identity) but framed it as a latency optimization rather than the correct resting place for data Session Runtime, not Game Management, actually owns the runtime meaning of.

## Alternatives Considered

### Keep `management.Game` returning `program.Definition`, have `sessionlifecycle` map it into a `session`-owned type at the boundary

Rejected as insufficient on its own (see Rationale) — it fixes the type-composition violation but not the deeper per-operation cross-domain runtime dependency, which is the more material problem. `WORK-0029`'s precedent for `engine.Output`/`engine.Value` remains correct there because `engineservice`/`engine` is a technical execution library Session Runtime is expected to depend on for its own implementation; Game Management is a distinct business domain Session Runtime should not depend on repeatedly at runtime at all.

### Compiled-definition cache in Session Runtime, keyed by definition UUID, populated lazily by calling Game Management on miss

This was this reviewer's own first recommendation before the human decision below, and is materially the same shape `GAME-ADR-0001` already named as a future optimization. Rejected by explicit human decision: it still leaves a live runtime dependency/coupling from Session Runtime to Game Management (now merely optimized, not removed), and does not resolve that Game Language execution semantics conceptually belong to Session Runtime's own responsibility rather than Game Management's authoring responsibility. A cache is the right shape for data genuinely owned elsewhere and read often; it is the wrong shape when the data is more accurately owned by the reader.

### Keep "Game" as one bounded context (status quo)

Rejected; superseded by this decision for the reasons above.

### Move Game Language entirely out of both domains into a repository-root-level shared package, unowned by either

Not materially considered as a serious alternative — `ARCHITECTURE.md`'s Component Model already treats a "Technical / Supporting Library" as a valid category distinct from a business domain, but Game Language's actual only consumer becomes Session Runtime once this decision lands (Game Management no longer needs to decode/validate scripts against it directly — see Consequences), so leaving it as a nominally-shared top-level package with one real consumer would be organizational indirection without benefit.

## Consequences

- Game Management's own package (`game/management`, target location `management/`) no longer imports `program`/`gameservice`/`engine` at all. Its current `getgame`/`getgamedefinition` use cases, which today call `gameservice.DecodeJSON` to validate/decode the stored script, lose that capability under this decision — Game Management no longer decodes or validates Game Language content itself. How Game Management validates an authored script before persisting it (today there is no create/publish use case yet, so this is not a regression of working functionality) becomes part of the future Orchestrator-mediated publish workflow's design, where Session Runtime's own Game Language performs the actual validation before either domain's write commits. This record does not resolve that design; it is out of scope and tracked separately (see Implementation Impact).
- Session Runtime (`game/session`, target location `session/`) gains a new persisted entity for the executable Game Language artifact, keyed by immutable definition/version UUID, and every one of its seven RuntimeTurn-capable operations that today calls Game Management (`Create`, `Join`, `Start`, `AnswerInteraction`, `SubmitUserIntent`, `CancelSession`, `ExpireTimer`) instead reads its own table. `gameCurrentVersionReader`/`gamePinnedDefinitionReader` and the interfaces/mocks built against them are removed from `sessionlifecycle`.
- This is a substantial migration: a new table/migration, package moves (`game/language` becoming Session-Runtime-internal; `game/management` and `game/session` becoming independent top-level packages; retiring the `game/` bounded-context root and its `README.md`/`CURRENT_STATE.md`/`docs/`), and updating every one of the seven call sites above plus their tests/mocks. It is significant enough that no implementation is authorized by this record (see Implementation Impact) — it is routed to a dedicated Project.
- Create-time visibility enforcement (today performed inline by `sessionlifecycle.Create` calling Game Management directly) has no owner until the Composer-mediated flow is built. Until that follow-up WORK lands, a gap exists where nothing prevents creating a Session for a non-visible/unpublished Game if `Create`'s direct call is removed before the Composer replacement exists — the migration WORK must not remove the direct call without first landing (or explicitly sequencing before) its replacement, or must otherwise explicitly accept and record that temporary gap.
- Publishing/authoring a Game (writing to both domains' representations consistently) becomes a genuine two-domain write-consistency problem the future Orchestrator workflow must handle (partial-failure/compensation, per `ARCHITECTURE.md -> State and Transaction Boundaries`), rather than something a single shared transaction could ever have legitimately done (`GAME-ADR-0001` already rejected shared transactions between these capabilities).
- `game/docs/decisions/GAME-ADR-0001-game-capability-persistence-transaction-boundary.md`'s bounded-context framing ("Game remains one bounded context... Game Management and Session Runtime remain internal capabilities of Game") and its "Session Runtime directly depends on a narrow Game Management definition/read capability contract" consequence are superseded by this record; its independent-persistence/transaction-boundary rationale (no shared transactions between the two capabilities) is restated and preserved by this record, not overturned.

## Implementation Impact

Not authorized by this record. Routed to a new Project, `docs/projects/active/management-session-domain-split/`:

- `WORK-0031` (DRAFT) — the migration itself: new Session-Runtime-owned executable-definition table/migration, package moves, and updating all seven call sites away from Game Management.
- `WORK-0032` (PLANNED) — Composer-mediated Create-time visibility composition, replacing the direct call `WORK-0031` removes; must be sequenced so the visibility-enforcement gap in Consequences above is never actually exposed in a deployed state.
- `WORK-0033` (PLANNED) — the future Orchestrator-mediated cross-domain Game-publish/authoring write composition; genuinely required per this record's Decision, design not yet started.
