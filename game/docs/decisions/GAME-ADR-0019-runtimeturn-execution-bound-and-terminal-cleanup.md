# GAME-ADR-0019: RuntimeTurn Execution Bound and Terminal Cleanup

Status: ACCEPTED
Created: 2026-09-08
Last status change: 2026-09-08
Supersedes: None
Superseded by: None

## Context

`engine.Limits`/`engine.DefaultLimits()` (see `game/language/v1/engine/README.md`) already bound the work done inside *one* `Step` call - guarding against an unbounded loop or unbounded recursive spawn within a single transition. GAME-ADR-0007 accepts that one `RuntimeTurn` may execute 1..N internal `engine.Step` calls in the same transaction, draining `Commit.InternalSignals` until quiescence, but no accepted decision bounds *how many* chained `Step` calls one RuntimeTurn may make. Left unbounded, a pathological or buggy authored chain of internal signals (each `Step` producing another `InternalSignals` entry) could make Session Runtime loop indefinitely inside one transaction - a distinct hazard from anything `engine.Limits` already guards against, since it operates one level above a single `Step` call.

Separately, GAME-ADR-0017 accepts a four-class runtime-failure taxonomy and an atomic fatal-materialization pattern for class B/C failures, but left "the concrete configured execution-budget/loop-limit/workflow-depth values" and "interaction/timer closure semantics at inactivity or fatal termination" as explicitly deferred topics; GAME-ADR-0014 (inactivity expiration) similarly left "the persistence-state transitions/closure reasons for still-open `session_interactions`/`session_timer_obligations` at inactivity termination" deferred. Without an accepted invariant, an implementation could plausibly leave a `TERMINAL` Session with interactions/timers still logically `ACTIVE` and executable, an operational hazard regardless of *which* terminal reason produced it (authored completion, lobby expiration, inactivity expiration, runtime execution failure, runtime state invalidity, or any future terminal reason).

Finally, GAME-ADR-0017 stated `base_turn_id` "is required (a fatal attempt always executes from some last-valid committed Turn, even if that Turn is only the Start-produced initial Turn)" - but did not consider whether a fatal failure could occur *before* any RuntimeTurn, including the Start-produced initial Turn, ever commits. GAME-ADR-0004's Start contract already requires that "if initialization or first authoritative execution fails, the transaction must not partially expose a `RUNNING` Session," but does not say what durable state results from a *deterministic* initialization failure specifically, as opposed to ordinary infrastructure failure - and whether Start's own initial signal/internal-signal chain is itself subject to any Step bound.

## Decision

### `MAX_STEPS_PER_RUNTIME_TURN = 20`

Session Runtime imposes a V1 Session-level limit on the internal engine `Step` chain belonging to one RuntimeTurn: at most 20 total `engine.Step` invocations per RuntimeTurn. This is distinct from, and layered above, `engine.Limits` (which bounds work inside one `Step` call). The value starts at 20; is defined/configurable through code (a constant or configuration value, not a durable per-Session persisted setting, and not authored by individual games in V1); and is intentionally easy to adjust after observing real games' actual internal-signal chain depth. `MAX_STEPS_PER_RUNTIME_TURN` applies uniformly to every Session and every game in V1 - it is Session Runtime platform policy, not Game Language surface.

**Counting semantics.** Every actual `engine.Step` invocation belonging to the same RuntimeTurn counts, including the initial externally-caused `Step` and every subsequent `Step` caused by draining an `InternalSignals` entry from a prior `Step`'s `Commit` within the same Turn. A RuntimeTurn may therefore execute at most 20 such `Step` calls before it must have reached quiescence (no remaining `InternalSignals`). This is specifically the Session-owned chain of `Step` calls for one RuntimeTurn - not 20 RuntimeTurns, not 20 operations inside one `Step` call (that remains `engine.Limits`' concern), and not 20 user interactions.

**Start is subject to the same bound.** Start's initial signal/internal-signal chain, which produces the Session's first RuntimeTurn, is also bounded by `MAX_STEPS_PER_RUNTIME_TURN`. If reaching quiescence for that initial chain would require more than 20 `Step` calls, Start does not commit Turn 1 (see Pre-First-Turn Fatal Start Failure below).

### Exceeding the limit is fatal deterministic execution failure

If processing a RuntimeTurn would require more `Step` invocations than `MAX_STEPS_PER_RUNTIME_TURN` allows before reaching quiescence, Session Runtime stops execution: no partial RuntimeTurn is persisted, no partial gameplay consequence is persisted, and the last committed `current_turn_id` remains authoritative. The whole attempted RuntimeTurn fails atomically - this is not expected-input rejection (GAME-ADR-0017 class A), not an infrastructure-retry situation (class D), and not a reason to simply continue processing the remaining internal signals later. It is classified as the same deterministic runtime/game execution failure family already accepted in GAME-ADR-0017 (class B, `RUNTIME_EXECUTION_FAILED`), using the same atomic fatal-materialization transaction pattern that record already accepts: attempt execution, encounter the fatal Step-limit condition, persist no attempted Turn/Steps, persist a `SessionRuntimeFailure`, set `phase = TERMINAL` + `terminal_reason = RUNTIME_EXECUTION_FAILED` + `terminal_at`, commit.

### Diagnostic observability: a stable, queryable error code

This specific failure must carry a clear, stable technical diagnostic classification distinguishable from every other `RUNTIME_EXECUTION_FAILED` cause, using a repository-conventional stable code equivalent to `runtime_turn_step_limit_exceeded`, persisted as (or alongside) `session_runtime_failures.error_code`. Operators/developers must be able to query and identify Sessions that terminalized specifically because the RuntimeTurn Step-chain limit was exceeded, distinct from an invariant violation, division by zero, or another `RUNTIME_EXECUTION` cause. The already-accepted `SessionRuntimeFailure` fields (GAME-ADR-0017: `session_id`, `failure_kind`, `error_code`, `base_turn_id`, `attempted_sequence`, `failed_step_index`, `source_kind`, `source_interaction_id`/`source_timer_obligation_id`, `actor_id`, `diagnostic_payload`) are sufficient to capture this - `failed_step_index`/`diagnostic_payload` may record the attempted sequence of internal signals that would have exceeded the bound. This technical code is never exposed to normal players, consistent with GAME-ADR-0017's existing internal/public terminal-reason separation (`RUNTIME_EXECUTION_FAILED` still projects publicly only as the generic `INTERNAL_ERROR` category).

### No ACTIVE runtime obligations after terminalization

Once a Session becomes semantically `TERMINAL`, it must not retain executable runtime obligations in `ACTIVE` state, regardless of terminal cause - authored root workflow completion, lobby expiration (GAME-ADR-0004), inactivity expiration (GAME-ADR-0014), runtime execution failure or runtime-state invalidity (GAME-ADR-0017, including the Step-limit-exceeded case above), or any other future terminal reason. Any still-open `session_interactions`/`session_timer_obligations` must be closed/cancelled as part of terminal-state materialization, in the same transaction that materializes `TERMINAL`: Session -> `TERMINAL`; ACTIVE interactions -> terminally closed/cancelled; ACTIVE timer obligations -> `CANCELLED`; terminal metadata (and failure metadata, where applicable) persisted; commit. A durable state where `Session.phase = TERMINAL` while an `ACTIVE` `session_interactions`/`session_timer_obligations` row still exists must never occur.

This terminal cleanup is explicit Session lifecycle cleanup, not gameplay: it does not execute Game Language, does not create a RuntimeTurn, does not fabricate an interaction response or a timer expiration, and does not mutate the last authoritative Snapshot. It is conceptually adjacent to, but distinct from, an authored gameplay consequence - the Session ending is what closes these obligations, not any engine `Step`.

**Closure provenance.** The existing `closed_by_turn_id` field represents gameplay/runtime closure produced by a committed RuntimeTurn (GAME-ADR-0007). When closure instead happens because the Session itself terminalized, `closed_by_turn_id = NULL` is valid, paired with a persisted closure reason/state capable of distinguishing this case from runtime-produced closure - conceptually `SESSION_TERMINATED` or a repository-conventional equivalent. This closure-reason field only explains "this obligation stopped being active because the Session terminated," not *why* the Session terminated; that remains discoverable through Session lifecycle/failure metadata (`terminal_reason`, and `session_runtime_failures` where applicable), and is deliberately not duplicated onto every closed interaction/timer.

**State vocabulary.** Existing state vocabularies are reused where possible: interactions transition `ACTIVE -> (terminally closed/cancelled)`; timer obligations transition `ACTIVE -> CANCELLED`. This record does not invent an exhaustive new enum taxonomy; the invariant - a `TERMINAL` Session has no executable `ACTIVE` interaction/timer obligation - matters more than exact enum naming, which remains an implementation-planning detail.

### Fatal failure before the first RuntimeTurn

The already-accepted `SessionRuntimeFailure.base_turn_id` concept (GAME-ADR-0017) is refined to explicitly support a fatal failure occurring before any authoritative RuntimeTurn has ever committed for a Session. `base_turn_id` is nullable: non-null means a last valid authoritative Turn existed before the fatal attempt (GAME-ADR-0017's original description of this field); null means the fatal execution/state failure occurred before any RuntimeTurn ever committed for this Session. This narrows GAME-ADR-0017's original "always required" description of `base_turn_id` to the specific pre-first-Turn case identified here; the rest of GAME-ADR-0017's accepted taxonomy, entity, and atomic-materialization model is unchanged.

### Start can fail fatally before Turn 1

Start (GAME-ADR-0004) validates lifecycle/host/roster/definition/constraints, then begins initialization/runtime execution - itself a RuntimeTurn-shaped chain subject to `MAX_STEPS_PER_RUNTIME_TURN` above. If deterministic engine execution fails before the first RuntimeTurn can commit (including a Step-limit overflow during initialization), the durable outcome is: `Session.phase = TERMINAL`, `terminal_reason = RUNTIME_EXECUTION_FAILED`; `started_at` follows the existing canonical semantics for a Session that never successfully entered `RUNNING` (it remains null - no value is invented for a Session that was never actually running); a corresponding `SessionRuntimeFailure` is persisted with `base_turn_id = NULL`, `attempted_sequence = 1` (diagnostic only - see below), appropriate source context identifying Start/initialization as the origin, failed-Step information, and the applicable error code/diagnostics. No Turn 1 exists. No fake Turn 0 exists. No dummy Snapshot is persisted. The Session may terminalize directly from `LOBBY` to `TERMINAL` without ever having been `RUNNING`.

`attempted_sequence = 1` may still be recorded diagnostically in this pre-first-Turn case, exactly as GAME-ADR-0017 already treats `attempted_sequence` generally: it does not consume authoritative sequence 1, since no RuntimeTurn exists, and the Session being terminal means no subsequent Turn sequence will ever be produced.

### RUNNING only exists after a successful first RuntimeTurn commit

GAME-ADR-0004's existing Start atomicity rule is strengthened to be explicit: a Session transitions durably from `LOBBY` to `RUNNING` only if Start successfully creates and persists the initial authoritative runtime state, including its first RuntimeTurn/current runtime pointer and every other required durable Start consequence, in one transaction - validate Start; build the Start-time roster; initialize the engine; execute the initial RuntimeTurn chain within the `MAX_STEPS_PER_RUNTIME_TURN` bound; persist Turn 1 and its RuntimeSteps/consequences; set `session_runtime_state.current_turn_id -> Turn 1`; set `phase = RUNNING`; set `started_at`; revoke JoinCode; apply other already-accepted Start consequences; commit. Coordinator/client-visible outputs occur only after this commit succeeds.

**Infrastructure failure during Start** (transient Postgres unavailability, deadlock/serialization retry, network/dependency failure, process crash before commit) does not itself produce a fatal `SessionRuntimeFailure`, and does not durably move the Session out of `LOBBY`: if the transaction did not commit, the Session remains durably `LOBBY` and is retryable under normal idempotent-retry semantics (GAME-ADR-0004), consistent with GAME-ADR-0017's class D and GAME-ADR-0013's crash-rollback model.

**Deterministic Start failure is different from infrastructure failure.** If Start reaches engine/runtime initialization and encounters a deterministic fatal execution failure (including exceeding `MAX_STEPS_PER_RUNTIME_TURN`), Session Runtime must not return the Session to `LOBBY` and invite endless retries of a definition that deterministically fails the same way every time; terminalization according to the runtime-failure semantics above is the accepted outcome instead. The distinction is: infrastructure failed -> no commit -> `LOBBY` remains retryable; game/runtime deterministic initialization failed -> `TERMINAL` with an internal runtime-error reason.

## Rationale

Bounding the internal-signal `Step` chain at the RuntimeTurn level closes a gap `engine.Limits` cannot close by itself: `engine.Limits` deliberately bounds only the work of *one* `Step` call (an unbounded loop/recursive spawn inside one transition), while nothing previously bounded how many times Session Runtime itself would keep calling `Step` again to drain `InternalSignals` produced by the *previous* `Step`. A buggy or adversarial authored chain that keeps producing further internal signals could otherwise make one RuntimeTurn's transaction run indefinitely, holding the per-Session serialization lock (GAME-ADR-0018) far longer than any legitimate turn-based interaction ever needs - a starvation risk to every other operation against that Session, not merely a performance nuisance for the one caller.

Treating a Step-limit overflow as the same `RUNTIME_EXECUTION_FAILED` class GAME-ADR-0017 already accepts - rather than inventing a fifth failure category - keeps the accepted four-class taxonomy exhaustive and avoids special-casing "the platform gave up" as somehow different from "the engine reported it couldn't safely continue"; both mean the attempted execution cannot be trusted to have reached a correct terminal state, and both get the same atomic-materialization treatment for the same reason GAME-ADR-0017 already gives (no window where a known-fatal condition leaves the Session durably `RUNNING`). A distinct, stable diagnostic `error_code` is still required specifically because collapsing every `RUNTIME_EXECUTION_FAILED` cause into one undifferentiated bucket would make it operationally impossible to tell "this game's authored logic has a runaway internal-signal chain" (actionable by whoever owns that game definition) from "this game hit a genuine invariant violation" (a different actionable signal) - the same operational-triage reasoning GAME-ADR-0017 already applied to justify distinguishing `RUNTIME_EXECUTION_FAILED` from `RUNTIME_STATE_INVALID` in the first place.

Requiring no `ACTIVE` obligations after terminalization, regardless of terminal cause, follows from treating `TERMINAL` as an actual end state rather than a label applied to a Session that could still, in principle, be operated on: an `ACTIVE` interaction/timer left dangling on a `TERMINAL` Session is either dead weight (nothing will ever answer/expire it) or, worse, a latent bug surface if any future code path forgets to check `phase` before acting on it. Making this cleanup atomic with terminalization - rather than a best-effort follow-up job - removes any window where those two facts could diverge. Explicitly stating this is *not* gameplay (no RuntimeTurn, no engine `Step`, no fabricated response) prevents an implementation from rationalizing this cleanup as "just another kind of Turn," which would incorrectly consume a sequence number and pollute RuntimeTurn history with entries that never touched engine execution at all.

Distinguishing termination-caused closure (`closed_by_turn_id = NULL` + `SESSION_TERMINATED`) from Turn-caused closure preserves the meaning GAME-ADR-0007 already gives `closed_by_turn_id` - "the RuntimeTurn that closed this" - without forcing every terminal-cleanup closure to either fabricate a Turn reference that doesn't exist or silently reuse the field with a different, undocumented meaning. Not duplicating the full Session terminal reason onto every closed obligation avoids "one fact, one owner" duplication risk (a future terminal-reason correction would otherwise need to fan out across every interaction/timer row it ever closed) in favor of a single closure-reason value whose entire job is "why did this specific row stop being active," leaving "why did the Session terminate" to the Session's own already-accepted lifecycle/failure fields.

Making `base_turn_id` nullable, rather than leaving GAME-ADR-0017's original "always required" framing standing, is necessary because that framing implicitly assumed at least one RuntimeTurn (even just Start's initial Turn) always exists before a fatal failure can occur - an assumption this record shows is false once Start's own initialization chain is itself subject to `MAX_STEPS_PER_RUNTIME_TURN` and can fail before ever committing. Refusing to fabricate a placeholder Turn 0/Turn 1 to give `base_turn_id` a non-null value follows the same reasoning GAME-ADR-0017 already used to reject fabricating a Turn for a failed attempt: inventing a Turn that never actually executed to a valid state would corrupt the "one committed Turn = one authoritative sequence + Snapshot" invariant (GAME-ADR-0007) for the sake of satisfying a column's non-nullability, which is exactly backwards.

Making `RUNNING` conditional on a successfully committed first RuntimeTurn, and distinguishing that from ordinary infrastructure failure, follows the same class-D reasoning GAME-ADR-0017 and GAME-ADR-0013 already establish: an uncommitted transaction is, from the Session domain's perspective, equivalent to nothing having happened, so infrastructure failure must leave `LOBBY` retryable exactly as any other uncommitted Session mutation would. But a *deterministic* initialization failure is not transient - retrying the identical Start against the identical pinned Game definition would deterministically fail again, so leaving the Session in an endlessly-retryable `LOBBY` state would be actively misleading (implying the operation might eventually succeed) rather than honestly reporting a permanent, definition-level problem via terminalization.

## Alternatives Considered

### No RuntimeTurn-level Step bound; rely solely on `engine.Limits` per-`Step` bounds

Rejected. `engine.Limits` cannot see across `Step` calls - a chain of many individually-cheap `Step` calls, each well within `engine.Limits`, could still make one RuntimeTurn's transaction (and its held serialization lock, GAME-ADR-0018) run arbitrarily long, which is precisely the hazard this record closes.

### Make the RuntimeTurn Step limit an authored, per-game Game Language setting

Rejected for V1. Letting individual game definitions author their own execution-safety bound would make the limit part of the Game Language surface/public contract rather than platform operational policy, complicate validating a game definition against a limit that could itself vary per game, and remove the platform's ability to adjust one operational safety value in response to real observed behavior across all games at once - directly contradicting the intent that this value "starts at 20... is intentionally easy to adjust after observing real games."

### Treat Step-limit overflow as a distinct fifth failure class instead of `RUNTIME_EXECUTION_FAILED`

Rejected. A fifth top-level class would duplicate machinery (atomic materialization, public projection, archival/queryability treatment) that GAME-ADR-0017's class B already provides for exactly this shape of problem ("the attempted execution cannot be trusted to reach a correct state, so it must not commit and the Session must terminalize"); a stable `error_code` inside the existing `session_runtime_failures` entity already gives operators the specific diagnostic distinction they need without widening the taxonomy.

### Best-effort/asynchronous cleanup of interactions/timers after terminalization, rather than atomic same-transaction cleanup

Rejected. A best-effort follow-up job reintroduces exactly the window this record closes: a period, however brief, where `Session.phase = TERMINAL` while an `ACTIVE` interaction/timer obligation still exists and could in principle still be acted upon by code that only checks obligation state, not Session phase. Atomic same-transaction cleanup removes that window entirely at negligible additional transactional cost, since the Session row is already being written in the same transaction regardless.

### Fabricate a placeholder Turn 0/Turn 1 so `base_turn_id` never needs to be nullable

Rejected. This is the same rejected idea GAME-ADR-0007/GAME-ADR-0017 already considered and rejected in a different guise (a synthetic Turn representing "nothing happened"): it would corrupt the RuntimeTurn sequence/Snapshot invariant and force every future reader of Turn history to special-case a Turn that never executed anything, purely to avoid a nullable column.

### Allow `LOBBY` retry after any Start failure, including deterministic ones

Rejected. Retrying a Start that will deterministically fail again against the same pinned, immutable Game definition wastes host/player time and gives a false impression that the failure might be transient; terminalizing directly communicates a permanent, actionable problem instead (a game-definition/runtime problem, not a "try again" situation), consistent with how GAME-ADR-0017 already treats deterministic execution failure during ordinary RUNNING-phase execution.

## Consequences

- Session Runtime must count every `engine.Step` invocation within one RuntimeTurn (initial cause plus every internal-signal-triggered `Step`) against `MAX_STEPS_PER_RUNTIME_TURN = 20`, defined in code and adjustable without a schema/architecture change.
- Exceeding the bound must be treated as an atomic `RUNTIME_EXECUTION_FAILED` fatal materialization (GAME-ADR-0017), with a stable, queryable diagnostic code equivalent to `runtime_turn_step_limit_exceeded` distinguishing it from every other `RUNTIME_EXECUTION_FAILED` cause, never exposed to players.
- Every terminalization path (authored completion, lobby expiration, inactivity expiration, runtime execution/state failure, any future terminal reason) must, in the same transaction that sets `phase = TERMINAL`, also close/cancel every still-`ACTIVE` `session_interactions`/`session_timer_obligations` row for that Session, using `closed_by_turn_id = NULL` plus a closure reason equivalent to `SESSION_TERMINATED` when the closure is not itself produced by a committed RuntimeTurn.
- `session_runtime_failures.base_turn_id` must be nullable; a null value means the fatal failure occurred before any RuntimeTurn ever committed for that Session, refining (not superseding) GAME-ADR-0017's original description of this field.
- Start must apply the same `MAX_STEPS_PER_RUNTIME_TURN` bound to its own initialization/internal-signal chain, and a deterministic failure of that chain must terminalize the Session directly from `LOBBY` with `base_turn_id = NULL`, `attempted_sequence = 1`, no fabricated Turn 0/Turn 1, and `started_at` left at its canonical null-for-never-ran value.
- A Session must never be observed as durably `RUNNING` without a correspondingly committed first RuntimeTurn/`current_turn_id`; infrastructure failure before that commit must leave the Session retryable in `LOBBY`, while deterministic initialization failure must not.
- Future implementation planning must design the concrete constant/configuration surface for `MAX_STEPS_PER_RUNTIME_TURN`, the exact closure-reason enum value(s), and the exact `runtime_turn_step_limit_exceeded`-equivalent error code, none of which is frozen syntax by this record.

## Implementation Impact

None. No constant/configuration value, migration, terminal-cleanup transaction code, Start implementation, or diagnostic error-code implementation is authorized by this record. The exact constant name/location, closure-reason enum values, and stable error-code string remain implementation-planning decisions.
