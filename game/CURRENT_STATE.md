| JavaScript Execution Runtime | PARTIAL | Sandboxed JavaScript execution is now a separately deployed service, `game/session/jsexecutor` (its own binary - `jsexecutor/main.go` is `package main`, built/run/scaled independently of Session Runtime's own server process; it communicates with Session Runtime only over gRPC, never in-process). It is placed inside `game/session/`, not at the repository root alongside `identity/`/`composer/`/`orchestrator/`, specifically to signal that it exists solely to serve Session Runtime and is not a shared/general-purpose service any other domain may call - see `game/session/jsexecutor/README.md`. It exposes one gRPC RPC, `Executor.Execute`, wrapping the sandbox mechanics: `wazero`-hosted QuickJS, a fresh worker process re-exec'd per call (`internal/sandbox`), a fresh empty scratch working directory per invocation (so the sandbox's mounted filesystem root never contains real host files), an empty worker-process environment, and a prelude that replaces the language's own ambient `Date`/`Math.random` and removes `performance`/`os` entirely, so a script cannot observe real wall-clock time, OS randomness, or elapsed real time even by calling those directly. A client-supplied gRPC deadline propagates to killing the whole worker process, verified against a script that never yields, over the real gRPC boundary. A business-level script rejection is returned as `ExecuteResponse.Rejected` with an OK gRPC status; an infrastructure-level failure (worker crash, deadline exceeded) is a non-OK gRPC status. The service also exposes the standard `grpc.health.v1` health check. Resource-limit tuning/hardening and worker pooling are not yet implemented (a fresh process is spawned per call). Session Runtime now has its own caller-side port onto this service, `game/session/internal/executor` (the `Executor` interface plus `GRPCClient`, its production gRPC implementation, and `Fake`, an in-memory test double) - `GRPCClient` retries only a connection-level `Unavailable` failure (execution is a pure function, so a request that never reached a worker is always safe to retry), never a deadline-exceeded or reported failure, and maps outcomes onto `*ScriptRejectedError`/`*ExecutorError` the same way `jsexecutor` itself distinguishes them. No `sessionlifecycle` call site invokes this port yet - the prior same-host-subprocess design (`game/session/internal/jsengine`, dispatched via `game/session/bootstrap`) has been retired entirely, both packages are deleted, and `main.go`'s corresponding worker-dispatch hook was removed since nothing called it in production. |

## Current Gaps

- Game Management lifecycle operations beyond retrieving a playable game (by current version or by a pinned Definition/Version UUID) were not found implemented.
- Session Runtime returns Question (persisted), Effect, and Presentation Outputs (in memory only) from `Start`/`AnswerInteraction`, terminalizes the Session on a game-completion Output (`TerminalReasonGame*`), and now durably persists/expires timer obligations (WORK-0012, DONE). Nothing yet consumes the returned Effect/Presentation Outputs, the game-completion fact, or physically schedules a timer obligation's expiration: no live-transport Coordinator exists to fan any of them out to a connected client or call `Manager.ExpireTimer` from a real wall-clock event - `docs/projects/active/session-runtime-v1/works/WORK-0020-role-aware-live-connections.md` owns rebuilding that Coordinator.
- `api`'s HTTP/WebSocket transport exists as a skeleton (real routes, a real connection upgrade) but calls no domain package - see the Session Runtime row above and `docs/projects/active/session-runtime-v1/works/WORK-0005-thin-live-coordinator.md`'s Blocker 11.
- Session Runtime's disconnect/reconnect/resync do not yet exist. `activity_expires_at` schema/renewal/lazy-materialization are now implemented (WORK-0016, DONE); the background Reaper described in `game/README.md`'s Durable Inactivity Expiration section is not - a Session past its deadline only actually terminalizes the next time some RUNNING-phase operation reaches it, not proactively.
- The new sandboxed JavaScript execution runtime (`jsexecutor`, a separately deployed gRPC service) exists and is tested standalone, and Session Runtime now has a real `Executor` port/client (`game/session/internal/executor`) to reach it, but no lifecycle step in `sessionlifecycle` calls that port yet - every step still executes the Game Language engine directly. Real resource-limit enforcement/tuning and worker-process pooling (a fresh process is spawned per call today) are not yet implemented, and `jsexecutor` has no deployment manifest (Dockerfile/compose entry) yet - it currently only runs via `go run`.
