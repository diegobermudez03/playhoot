Every deterministic-execution/state-invalidity fatal path (`Start`/`AnswerInteraction`/`SubmitUserIntent`/`CancelSession`/`ExpireTimer`) now persists a `session_runtime_failures` diagnostic row (GAME-ADR-0017) through one shared `(*Manager).materializeRuntimeFailure` helper (`runtime_failure.go`), which also performs the already-existing terminal-cleanup invariant (GAME-ADR-0019) atomically alongside it; `error_code` is a Session-Runtime-owned stable string catalog decoupled from the engine's own `ExecutionErrorCode` (WORK-0014, DONE). `sessions.activity_expires_at`, the RUNNING-phase inactivity deadline, is now implemented (WORK-0016, DONE): `Start` sets the initial deadline; `AnswerInteraction`/`SubmitUserIntent`/`ExpireTimer` renew it whenever they actually commit a Turn; all four of those plus `CancelSession` lazily materialize `TERMINAL`/`RUNTIME_INACTIVITY_EXPIRED` (closing every still-`ACTIVE` interaction/timer obligation, no `session_runtime_failures` row) if a call discovers the deadline already passed. No background Reaper exists yet - a stale Session only actually terminalizes the next time some RUNNING-phase operation reaches it. Disconnect/reconnect and resync still do not exist. |
| Game Language | IMPLEMENTED | Current v1 source model, JSON codec/validation, compiler, runtime step/evaluate behavior, snapshot codec, and tests exist. Session Runtime's lifecycle steps still call this engine directly; it has not yet been retired from the live call path. |
| JavaScript Execution Runtime | PARTIAL | `game/session/internal/jsengine` implements the sandboxed execution boundary: `Execute(ctx, previousState, event, context) -> (newState, requestedCommands)`, running author-written JavaScript inside a QuickJS-on-WebAssembly sandbox hosted in a separate OS process (a re-exec of the same binary in a hidden worker mode, dispatched via `game/session/bootstrap` before `main.go`'s normal startup). Each invocation gets a fresh, empty scratch working directory (so the sandbox's mounted filesystem root never contains real host files) and a prelude that replaces the language's own ambient `Date`/`Math.random` with values derived from the supplied logical time/random seed, so a script cannot observe real wall-clock time or OS randomness even by calling those directly. A caller-supplied deadline is enforced by killing the whole worker process, verified against a script that never yields. Resource-limit tuning/hardening and worker pooling are not yet implemented (a fresh process is spawned per call); no Session Runtime call site invokes this yet - it exists as a standalone, tested package, not yet wired into the lifecycle steps that still call the Game Language engine above. |

## Current Gaps

- Game Management lifecycle operations beyond retrieving a playable game (by current version or by a pinned Definition/Version UUID) were not found implemented.
- Session Runtime returns Question (persisted), Effect, and Presentation Outputs (in memory only) from `Start`/`AnswerInteraction`, terminalizes the Session on a game-completion Output (`TerminalReasonGame*`), and now durably persists/expires timer obligations (WORK-0012, DONE). Nothing yet consumes the returned Effect/Presentation Outputs, the game-completion fact, or physically schedules a timer obligation's expiration: no live-transport Coordinator exists to fan any of them out to a connected client or call `Manager.ExpireTimer` from a real wall-clock event - `docs/projects/active/session-runtime-v1/works/WORK-0020-role-aware-live-connections.md` owns rebuilding that Coordinator.
- `api`'s HTTP/WebSocket transport exists as a skeleton (real routes, a real connection upgrade) but calls no domain package - see the Session Runtime row above and `docs/projects/active/session-runtime-v1/works/WORK-0005-thin-live-coordinator.md`'s Blocker 11.
- Session Runtime's disconnect/reconnect/resync do not yet exist. `activity_expires_at` schema/renewal/lazy-materialization are now implemented (WORK-0016, DONE); the background Reaper described in `game/README.md`'s Durable Inactivity Expiration section is not - a Session past its deadline only actually terminalizes the next time some RUNNING-phase operation reaches it, not proactively.
- The new sandboxed JavaScript execution runtime (`game/session/internal/jsengine`) exists and is tested standalone, but nothing in `sessionlifecycle` calls it yet - every lifecycle step still executes the Game Language engine. Real resource-limit enforcement/tuning and worker-process pooling (a fresh process is spawned per call today) are not yet implemented.
