# Session Runtime

Status: CANONICAL DOMAIN MODEL

## Responsibility

Session Runtime owns the runtime execution of Playhoot game sessions.

## Owns

- Live game sessions.
- Session runtime state and participation.
- Execution lifecycle of a game session.
- Its own persisted copy of the executable Game Version Artifact for each immutable Game version it has ever pinned a Session to.

## Does Not Own

- Transport/network connections.
- Identity/profile ownership.
- Public discovery/search experience.
- Authored games and their definitions/versions, or Game metadata/visibility/publication state (owned by Game Management, `game/README.md`).

## Internal Structure

Session Runtime is an independent top-level package/business bounded context, a sibling to Game Management (`game/`), `identity/`, `composer/`, and `orchestrator/` - not a capability nested under a shared "Game" bounded context (`docs/decisions/architecture/ADR-0014-management-session-domain-split.md`, ACCEPTED and implemented for the package/domain split itself by `docs/projects/active/js-runtime-migration/works/WORK-0034-session-owned-executable-script-artifact-and-package-restructuring.md`).

Game Language is fully retired from Session Runtime's live execution path. Every operation that resolves a pinned Game version (`Join`/`Start`/`SubmitPlayerEvent`/`CancelSession`/`ExpireTimer`) reads it entirely from Session Runtime's own `session_games`/`session_game_version_artifacts` tables (see Capability Persistence and Transaction Boundary below) - no cross-domain read to Game Management exists anywhere in the live path. Every RuntimeTurn-producing operation (`Start`/`SubmitPlayerEvent`/`CancelSession`/`ExpireTimer`) executes the pinned `backend_script` through `session/internal/executor`'s port onto the separately deployed JavaScript Executor (`session/jsexecutor`), never a local/in-process execution mechanism.

## Capability Persistence and Transaction Boundary

Session Runtime owns its own persisted state: sessions, session state, participants, join codes, its own copy of the executable Game Version Artifact (`session_games`/`session_game_version_artifacts`), and other live-runtime persistence. No database transaction spans Session-Runtime-owned and Game-Management-owned state, and a transaction handle must not be propagated from one into the other (`ARCHITECTURE.md -> State and Transaction Boundaries`).

`Create` resolves and pins a Session's Game definition/version entirely from Session Runtime's own tables, never from Game Management. The remaining six RuntimeTurn-capable operations still depend on a narrow Game Management pinned-definition read capability, unchanged by this migration. A session must be pinned to a concrete execution definition/version, and the definition observed by an existing session must remain semantically stable for that session's lifetime; version immutability for existing sessions is the preferred model. Changing a game's current definition affects only newly created sessions.

Rationale and alternatives for the original shared-context/transaction-boundary decision are recorded in `game/docs/decisions/GAME-ADR-0001-game-capability-persistence-transaction-boundary.md`; the domain-split decision itself is recorded in `docs/decisions/architecture/ADR-0014-management-session-domain-split.md`.

## Session Runtime Durable Boundary

Session Runtime owns all durable authoritative state that determines the meaning of a session and must be reconstructible after loss or restart of the process.

"Stateless" for Session Runtime means process-stateless/reconstructible. It does not mean the capability has no durable domain state.

`Live Session Coordinator` is the accepted conceptual responsibility boundary outside Session Runtime for ephemeral/runtime mechanisms:

- live connection bindings;
- delivery/fan-out to connected clients;
- detection of physical disconnects;
- physical timer/scheduling mechanisms.

The Coordinator does not own authoritative session/game truth or business consequences. This boundary does not require another deployed service; V1 may keep the Coordinator in the same Go process. Coordinator/client delivery is best-effort against already-durable Session Runtime truth, never the other way around - see Session Runtime Post-Commit Client Delivery Semantics below.

V1 does not introduce sticky-session correctness requirements, Redis, distributed session routing, distributed locks, or other multi-instance mechanisms. The initial single-process modular-monolith deployment may use local maps, channels, and Go timers for ephemeral mechanisms, but session correctness must not depend exclusively on those ephemeral objects.

Timer obligations that can affect game semantics are durable Session Runtime state. The Coordinator owns the physical timer and detects elapsed wall-clock time; Session Runtime owns the durable timer obligation and decides the semantic consequence, normally through its authoritative runtime/engine flow. A process crash may destroy physical timers but must not silently erase timer obligations or change game semantics. Pending or overdue obligations must be reconstructible/recoverable from durable state - recoverable means the obligation and its configured delay survive, not that the exact original overdue/elapsed wall-clock position is reconstructed. V1 persists only the obligation and its `delay_ms`, not an absolute deadline; on recovery, active obligations may be rescheduled using their full configured delay from the new scheduling moment, per the accepted `session/docs/decisions/SESSION-ADR-0007-session-runtime-v1-timer-recovery-simplification.md` tradeoff.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0001-session-runtime-durable-boundary.md`.

## Session Runtime Actor and Lifecycle Model

Host and Participant are independent concepts. Creating a Session establishes a host but does not automatically make that host a gameplay participant. The same Session-owned actor may be both host and Participant, but those are separate relationships.

V1 does not introduce separate mutable `creator` and `host` concepts unless another accepted decision requires them. Host transfer is not currently designed.

Participant is session-scoped. Session Runtime does not own a cross-session Player/Profile master entity. A Participant belongs to one Session and contains Session-owned participation/lifecycle state plus a display-name snapshot.

V1 does not include a generic persisted `role` field merely to anticipate spectators, judges, controllers, or gameplay roles. Gameplay roles belong primarily to game definition/runtime state unless Session Runtime later has a concrete cross-game reason to own such a distinction.

Session-local uniqueness is the accepted invariant: an actor may occupy at most one active logical participation for the same Session. Game does not establish a platform-wide invariant that one User may belong to only one active Session.

Session Runtime conceptually owns a session-scoped identity such as `SessionActorID`. Host and Participant relationships refer to this local identity. Runtime/domain operations should primarily operate using Session-owned identity rather than propagating `UserUUID` throughout engine/runtime behavior.

A SessionActor may persist `user_uuid` as a cross-domain reference to `Identity.User`. This is a logical domain reference, not ownership of User/Profile, not permission to read Identity persistence, not dependency on Identity table layout, and not a cross-domain database foreign key.

Session Runtime owns its participation-time display-name snapshot associated with SessionActor/Participant representation. Mutable global display/profile ownership remains unresolved outside Game.

User-originated operations crossing the public/application boundary of Session Runtime identify the caller through authenticated `UserUUID`. The external client is not the trusted source of `UserUUID`; a trusted authentication/application layer resolves credentials into an authenticated `UserUUID`.

Session Runtime owns the translation from `(Session UUID, UserUUID)` to `SessionActorID`. `SessionActorID` is internal Session-owned identity, not part of Session Runtime's public/application-facing contract. Coordinator, Orchestrator, HTTP/WebSocket adapters, and clients do not own or maintain the mapping from `UserUUID` to `SessionActorID`.

Game Language / engine user identity represents the Session-local actor and must not receive `Identity.UserUUID`. When engine/runtime behavior targets a Session-local actor, Session Runtime resolves that internal actor back to `SessionActor.user_uuid` / `UserUUID` before crossing the Session Runtime boundary. Identity/Auth proves who the caller is; Session Runtime decides whether that User may act as host, active Participant, or another Session-owned relationship in the current lifecycle/runtime state.

Use the conceptual Session lifecycle:

```text
LOBBY -> RUNNING -> TERMINAL
```

`TERMINAL` is irreversible. Terminal cause/reason is modeled separately from lifecycle phase; the exhaustive terminal-reason enum is not yet accepted.

`LOBBY` has its own durable expiration concern, `lobby_expires_at`; Join/Start correctness must enforce this durable deadline even if no asynchronous cleanup/sweeper has materialized the Session as terminal yet. `RUNNING` has its own separate durable inactivity deadline, `activity_expires_at` (see Session Runtime Durable Inactivity Expiration below); neither deadline is a generic whole-session lifetime, and a later max-runtime/runaway-session abuse policy remains a different, still-deferred concern.

Physical connection presence belongs to the Live Session Coordinator and must not be persisted as authoritative state through fields such as `is_connected`, `connection_id`, or `websocket_id`. Session Runtime does durably persist a coarser, already-debounced platform fact on the SessionActor itself: `semantic_presence` (`CONNECTED | DISCONNECTED`), answering only "has this SessionActor crossed the Coordinator -> Session semantic connected/disconnected boundary?" This is distinct from `session_participants.active`, which answers "does this actor currently occupy/admit a participant position?" - a phase-dependent question (see Session Runtime Lobby Lifecycle Contract and Session Runtime Disconnect, Reconnect, and Resynchronization Boundary below). The two may legitimately diverge, for example a reconnecting actor that is semantically `CONNECTED` but locked out of a full lobby.

The disconnect/reconnect transport-and-platform boundary, the authored Game Language disconnect/reconnect contract, and the phase-dependent LOBBY-vs-RUNNING participation consequence are all now accepted; see Session Runtime Disconnect, Reconnect, and Resynchronization Boundary below. What remains authored (not a Session Runtime invariant) is how a game behaves while an actor is offline - waiting, timers, forfeiture - beyond the platform lifecycle signals themselves.

The live transport distinguishes two independent connection roles, `ADMIN` and `PARTICIPANT`, mechanically enforcing the Host/Participant independence stated above rather than only stating it as a domain invariant: a host obtains an `ADMIN` connection without `Join`, and may separately also hold an independent `PARTICIPANT` connection if they choose to also play. See `session/docs/decisions/SESSION-ADR-0024-role-aware-live-connections.md`.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0002-session-runtime-actor-and-lifecycle-foundations.md`.

The public/internal identity boundary is refined by `session/docs/decisions/SESSION-ADR-0004-session-public-and-internal-identity-boundary.md`.

## Session Runtime Lobby Lifecycle Contract

All mutations that can alter lobby membership or cross the lobby/start boundary for one Session must serialize against that Session. This includes Join, Leave, Start, and materialization of lobby expiration when performed by one of these operations or housekeeping. The accepted architecture is the per-Session serialization guarantee, not one specific SQL syntax. This same per-Session serialization guarantee is extended to RUNNING - see Session Runtime RUNNING Mutation Serialization below; a Session is a single-writer-at-a-time domain object for its entire authoritative-mutation lifetime, not only during LOBBY.

CreateSession/CreateRoom receives conceptually a Game public UUID, authenticated host `UserUUID`, and opaque idempotency key. Session Runtime resolves the currently playable immutable Game definition/version entirely from its own `session_games`/`session_game_version_artifacts` tables - no Game Management call (`docs/projects/active/js-runtime-migration/works/WORK-0034-session-owned-executable-script-artifact-and-package-restructuring.md`) - pins the Session to that immutable definition/version, and does not accept an externally-precompiled `engine.Program`.

Within one Session-owned transaction, Create creates a Session in `LOBBY`, a host SessionActor correlated through `user_uuid`, the Session host relationship pointing to that SessionActor, an active JoinCode, and `lobby_expires_at`. Creating the Session does not automatically make the host a gameplay Participant. `lobby_expires_at` is V1 Session Runtime policy unless another accepted product decision says otherwise. Public responses do not expose `SessionActorID`; QR codes and join URLs are projection/application concerns derived from JoinCode.

JoinCode is authoritative Session Runtime state, not cache-owned truth. V1 has one active JoinCode for a lobby unless a future accepted feature requires rotation/multiple codes. A JoinCode is valid only while its Session remains admissible for joining, is revoked when the Session exits `LOBBY`, and may retain historical records for traceability. A textual code value need not be permanently reserved forever after revocation.

Join receives conceptually a JoinCode, authenticated `UserUUID`, display-name snapshot supplied by the trusted application/integration layer, and opaque idempotency key. Session Runtime resolves the JoinCode to its Session, obtains the pinned Game version artifact's own structural `ParticipantConstraints` needed for lobby constraints, enters the Session-serialized mutation, and revalidates JoinCode admissibility, `LOBBY` phase, and `lobby_expires_at`.

Join finds or creates the SessionActor for `(Session, UserUUID)`. A Join carrying the same idempotency token as a previously completed Join, with the same semantically meaningful fields (JoinCode, UserUUID, display-name snapshot), replays that completed outcome rather than re-evaluating current state. A Join carrying a *different* idempotency token is always evaluated as a new logical command against current state: if the caller is already an active Participant, this new command is rejected with the already-active-participant outcome (`AlreadyJoined` or an equivalent value) rather than silently treated as success merely because the desired end state already holds. Otherwise Join counts active Participants, enforces `ParticipantConstraints.Max` from the pinned artifact, activates Participant membership, and commits atomically. The pinned artifact remains the source of truth for the structural `participant_min`/`participant_max` range; Session does not copy those values as a second correctness source. `JOINED`, `LOBBY_EXPIRED`, `LOBBY_FULL`, and `ALREADY_JOINED` are all expected, correctly-evaluated Join outcomes returned as a result value rather than as an application error - only an invalid command/protocol contract or an execution/infrastructure failure is an error (`docs/engineering/standards/error-handling.md`). See `session/docs/decisions/SESSION-ADR-0020-session-lobby-command-idempotency-token-semantics.md` for the full token-replay-vs-new-command rule and its rationale, and `session/docs/decisions/SESSION-ADR-0021-session-lobby-business-declines-as-workflow-outcomes.md` for the outcome-vs-error representation.

Leave is a `LOBBY` participation operation. Public/application caller identity is `UserUUID`; Session Runtime resolves `(Session, UserUUID)` to its internal SessionActor. Leaving deactivates logical Participant membership, releases a lobby slot, does not delete the SessionActor, does not remove host authority, and does not automatically cancel the Session. A host who is also participating may leave gameplay participation while remaining host. Rejoining the same admissible lobby reuses the same SessionActor.

A `LOBBY` semantic disconnect (see Session Runtime Disconnect, Reconnect, and Resynchronization Boundary below) has the same participation effect as Leave: the SessionActor's `semantic_presence` becomes `DISCONNECTED`, its active Participant (if any) is deactivated, and the released slot is immediately available to other joiners. This is intentionally stronger than the RUNNING disconnect rule below - a player still inside Coordinator transport grace never reaches Session Runtime as a disconnect and keeps their active lobby slot. A subsequent `LOBBY` reconnect transitions `semantic_presence` back to `CONNECTED` and reuses the same SessionActor/Participant record, but if the prior disconnect deactivated the Participant, re-admission is revalidated against current lobby constraints (Session still `LOBBY`, not expired, current active-participant count against `participant_max`, and other applicable admission constraints) exactly as a fresh Join would be; admission is not guaranteed to succeed, and reconnect does not guarantee recovery of a previously released slot if another actor has since occupied it.

Join/Start correctness does not depend on a sweeper having already changed stored phase. If an operation discovers `phase == LOBBY && now >= lobby_expires_at`, it may atomically materialize `TERMINAL`, a terminal reason corresponding to lobby expiration, a terminal timestamp equal to the lobby deadline, and JoinCode revocation. A background sweeper is housekeeping/materialization support, not the source of business correctness. The exhaustive terminal-reason enum is not yet accepted.

Start receives conceptually a Session UUID, authenticated `UserUUID`, and opaque idempotency key. Session Runtime resolves `(Session UUID, UserUUID)` to `SessionActorID` and uses that internal identity to verify host authority. Start uses the Session's pinned immutable Game version artifact, not the latest current Game version; validates `LOBBY`, `lobby_expires_at`, host authority, active Participants, `participant_min`, and defensively `participant_max`; drives the authored backend script's own first execution (a `SESSION_STARTED` Event against no prior state); persists the resulting state and durable consequences; transitions Session atomically to `RUNNING`; sets `started_at`; revokes JoinCode; and commits before any Coordinator/client-visible outputs are delivered.

If initialization or first authoritative execution fails, the transaction must not partially expose a `RUNNING` Session. No Coordinator/client-visible output is delivered before successful durable commit.

A Session becomes durably `RUNNING` only after Start successfully commits its first authoritative RuntimeTurn/current runtime pointer together with every other required Start consequence in one transaction. Transient infrastructure failure before that commit leaves the Session durably `LOBBY` and retryable under normal idempotent-retry semantics: Session Runtime does not return the Session to `LOBBY` for endless retry of a script that will deterministically fail again - it terminalizes the Session directly from `LOBBY` to `TERMINAL` with internal `terminal_reason = RUNTIME_EXECUTION_FAILED`, `started_at` left at its canonical null value (the Session never actually ran), and a `SessionRuntimeFailure` recorded with `base_turn_id = NULL` and diagnostic `attempted_sequence = 1` - no Turn 1 and no fabricated Turn 0. See Session Runtime Failure Classification And Diagnostic Persistence below.

Mutating external Session commands in this lobby lifecycle accept an opaque idempotency key, including Create, Join, Leave, and Start, following `docs/engineering/standards/idempotency.md`'s general token semantics. Session Runtime must guarantee that retrying the same logical command does not repeat its effect, and that a differently-tokened command is always evaluated as a new logical command against current state rather than inferred to be a retry merely because the resulting state already holds (see the Join token semantics above and SESSION-ADR-0020). Natural/domain idempotency is useful additional protection but is not a substitute for the explicit idempotency contract. The final idempotency storage algorithm is not yet accepted.

Start's `SESSION_STARTED` Event carries `Players`, the Session-local runtime identity derived from `SessionActorID` for each active Participant; `Identity.UserUUID` is never exposed to the authored backend script.

The roster is built strictly from Participants active at the serialized Start moment. A SessionActor that is `DISCONNECTED` (and therefore inactive from a lobby disconnect) or `CONNECTED` but not currently re-admitted as an active Participant is not included. Whether a concurrent physical disconnect actually excludes a player from Start depends only on which side wins the existing per-Session serialization: if Coordinator grace has not yet expired when Start wins serialization, the Participant is still active and included; if the semantic disconnect was already processed first, it is excluded. This is not special-cased outside Session - the existing lobby serialization already decides it. An actor excluded from the Start-time roster does not join the running game merely by reconnecting afterward. Post-Start late admission is a distinct, separately deferred capability.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0003-session-lobby-lifecycle-contract.md`, `session/docs/decisions/SESSION-ADR-0004-session-public-and-internal-identity-boundary.md`, `session/docs/decisions/SESSION-ADR-0005-game-language-root-player-roster-contract.md`, `session/docs/decisions/SESSION-ADR-0014-session-actor-semantic-presence-and-lobby-membership.md`, `session/docs/decisions/SESSION-ADR-0020-session-lobby-command-idempotency-token-semantics.md` (Join idempotency token-replay-vs-new-command semantics), `session/docs/decisions/SESSION-ADR-0021-session-lobby-business-declines-as-workflow-outcomes.md` (business declines represented as workflow outcomes, not errors), and, for the pre-first-Turn fatal Start behavior above, `session/docs/decisions/SESSION-ADR-0018-runtimeturn-execution-bound-and-terminal-cleanup.md`.

## Session Runtime RUNNING Mutation Serialization

Status: HUMAN-APPROVED and canonically promoted; not yet implemented.

The per-Session serialization guarantee accepted above for LOBBY is extended to RUNNING. For one Session, every mutation capable of changing authoritative RUNNING-phase runtime state executes serially - including, without limitation, interaction responses, timer expirations, `UserDisconnected`/`UserReconnected` semantic-presence processing (see Session Runtime Process-Agnostic Recovery below), and any future platform/runtime signal capable of creating a RuntimeTurn or otherwise mutating authoritative Session runtime state. There must never be two RuntimeTurns concurrently executing against the same authoritative Session state.

V1 imposes this serialization through the same database-backed pessimistic locking strategy already accepted for LOBBY, inside Session Runtime's own transaction boundary: if two causes (for example an interaction response and a timer expiration) concurrently target the same Session, one obtains the Session's serialization boundary first, and only after it commits or rolls back may the other continue against the resulting authoritative state. The exact SQL lock anchor/statement is an implementation-planning detail, not frozen here.

A runtime mutation must not execute against a Snapshot read before serialization was obtained. Once serialization is acquired, execution reloads the current committed `sessions.current_turn_id` (SESSION-ADR-0022) and its corresponding authoritative Snapshot; each RuntimeTurn starts from the latest committed state visible at the moment serialization was actually acquired, not from whatever was visible before the caller began waiting.

Authoritative ordering of concurrent causes is defined purely by which cause wins Session serialization and commits first. Worked example: current authoritative Turn is 40; an interaction response Q5 and a timer expiration T1 concurrently target the same Session. If Q5 wins serialization, it processes from Turn 40 and commits Turn 41; T1 then obtains serialization, processes from Turn 41, and commits Turn 42. Session Runtime must never attempt to reconstruct a different authoritative ordering from wall-clock receive timestamps, Coordinator arrival timestamps, process identity, or socket/transport timing - persisted Turn sequence is the only authoritative execution order.

Correctness does not depend on process ownership, sticky routing, an in-memory actor, Redis or another distributed lock service, or Coordinator ownership of correctness; Coordinator remains the ephemeral delivery/connection-binding layer and must not become a competing source of Session mutation ordering.

Read-only operations such as resync (see Session Runtime Disconnect, Reconnect, and Resynchronization Boundary below) do not themselves create RuntimeTurns and are not required to participate in this mutation-serialization boundary merely to be modeled consistently; a read should observe a coherent committed state, but the exact read-isolation implementation is not frozen here.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0017-session-running-mutation-serialization.md`.

## Session Runtime Turn And Persistence Model

`RuntimeTurn` is the historical/transactional unit for RUNNING-phase execution. One RuntimeTurn begins from one external cause (a submitted player event, a timer expiration, a host cancellation, or Start's own first execution) and drives exactly one Executor `Execute` call within the same transaction; the state that call returns becomes the observable/authoritative Session state, and one committed Turn corresponds to exactly one Session runtime sequence.

Session Runtime persists the current authoritative Runtime state directly, as `session_runtime_turns.new_state` - an opaque value Session Runtime never decodes or interprets, stored exactly as the Executor returned it. The current authoritative Turn is a thin pointer, `sessions.current_turn_id` (not a separate `session_runtime_state` table - SESSION-ADR-0022); every caller that needs current state already holds the locked `sessions` row for per-Session serialization, reads that pointer, and passes the pointed-at row's `new_state` straight to the Executor as the next call's `PreviousState`. No reconstruction step of any kind exists on this path.

Session Runtime does not persist an absolute due-at/deadline for timers; it persists only the timer obligation and its configured delay. The Coordinator remains the time-aware layer and owns physical timers in memory. On recovery, active timer obligations may be rescheduled using their full configured delay from the new scheduling moment; preserving elapsed wall-clock time across a full process restart is not required. This does not affect `lobby_expires_at`, which remains a separate, already-accepted Session lifecycle deadline.

The accepted lobby/lifecycle idempotency table for Create/Join/Leave/Start/SubmitPlayerEvent/CancelSession is `session_requests`, storing the request payload rather than a hash, so a retry with the same idempotency key can be checked for semantic equivalence against the originally stored request.

The durable signal/cause log (`session_runtime_turns`'s own ordered `source_kind`/`source_timer_obligation_id`/`source_cause_event_id` envelope, `session_runtime_starts`, `session_cause_events`, `session_timer_obligations`) is retained purely for a future, not-yet-implemented best-effort reconstruction/audit capability - nothing on the live-correctness path reads it to determine current state. Strict deterministic replay across calls is not relied upon anywhere: each Execute call draws its own fresh random seed.

The full accepted table/column/relationship diagram is recorded in `session/docs/SESSION_RUNTIME_PERSISTENCE_MODEL.md`. Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0025-snapshot-based-session-runtime-persistence.md` (supersedes `SESSION-ADR-0023-replay-first-session-runtime-persistence.md`, retained as historical record).

## Session Runtime Process-Agnostic Recovery

Session Runtime does not model durable ownership of a Session by a particular process, pod, or runtime instance. It has no `owner_process_id`, no runtime instance ownership, no process heartbeat ownership, no fencing/takeover generation for the purpose of process ownership, no sticky Session ownership, and no durable `RECOVERING` process phase. Conceptually, one process calls the Session Runtime API against durable Session state, then disappears; another process later calls the same Session Runtime API against the same durable Session state, and Session Runtime does not need to know the caller changed. A process crash by itself is not a Session-domain event and does not change `Session.phase`.

The accepted RuntimeTurn transactional model (see Session Runtime Turn And Persistence Model above) is preserved unchanged for crash recovery. If a process dies before a RuntimeTurn's transaction commits, the entire Turn rolls back: `current_turn_id` remains at its previous value, no partially authoritative Turn exists, and the external cause may later be retried under its own idempotency semantics. If the transaction committed but the process died before live delivery/response, the Turn did occur: `current_turn_id` points to it, its committed state/timer mutations remain authoritative, reconnect/resync returns the resulting state, and normal idempotency prevents replaying the same accepted external cause - which process happened to execute the Turn is irrelevant.

A process that needs to resume serving a `RUNNING` Session reads current durable authoritative state directly - `sessions` (including `current_turn_id`), that row's own `new_state`, active `session_timer_obligations`, and other current durable Session-owned state - never by replaying anything. Historical Turns remain useful for history, debugging, archive, and separately designed audit/replay tooling, but are not required bootstrapping state. Timer recovery continues to use the same tradeoff unchanged: active durable timer obligations may be physically rescheduled after process loss using their full configured delay; no `due_at` is introduced.

Total loss of ephemeral Coordinator/process state does not itself mutate `session_actors.semantic_presence` (SESSION-ADR-0014): durable `CONNECTED`/`DISCONNECTED` values before the loss remain unchanged merely because sockets, Coordinator maps, timers, or grace state disappeared with the crashed process. `semantic_presence = CONNECTED` means only "Session Runtime has not yet processed a semantic `CONNECTED -> DISCONNECTED` edge for this actor," not that a live socket currently exists - physical connectivity remains entirely Coordinator-owned ephemeral state. When Coordinator reconstructs a still-semantically-active Session and finds a durably `CONNECTED` actor with no current physical binding, it starts a fresh transport/recovery grace for that actor, reusing the same mechanism already accepted for ordinary transient disconnects (SESSION-ADR-0009) rather than a distinct process-crash-disconnect event or API; a durably `DISCONNECTED` actor receives no such grace, since there is no semantic uncertainty to absorb. Recovery grace must never revive a Session whose authoritative `lobby_expires_at`/`activity_expires_at` deadline already passed, and merely reconstructing infrastructure mechanisms after restart (reading current state, discovering timer obligations/durably `CONNECTED` actors, starting recovery graces, rebuilding Coordinator maps) does not by itself renew `activity_expires_at`. Session Runtime does not gain process-specific APIs (for example `RecoverFromProcessCrash`, `ClaimSession`, `CoordinatorRestarted`) - it continues to expose only ordinary domain/runtime operations regardless of which process invokes them.

Disconnect/reconnect's own authored-script processing (translating a semantic presence transition into a platform Event delivered to the backend script) remains `session-runtime-v1`'s own not-yet-implemented capability under this new execution model; this section describes only the persistence/recovery mechanism it will build against.

Rationale and alternatives, including the rejected process-owned-lease/heartbeat/fencing direction, are recorded in `session/docs/decisions/SESSION-ADR-0012-session-runtime-process-agnostic-recovery.md`. The recovery-grace-after-total-process-loss behavior is recorded in `session/docs/decisions/SESSION-ADR-0015-session-semantic-presence-recovery-after-total-coordinator-state-loss.md`.

## Session Runtime Failure Classification And Diagnostic Persistence

Session Runtime distinguishes three conceptually different failure classes, not one undifferentiated "operation failed" outcome:

- **Expected script rejection** - `*executor.ScriptRejectedError`: the authored script itself declined the input (threw, or returned a value not matching its required shape). The current operation is rejected/discarded; current state is not mutated; no RuntimeTurn is created; the Session remains `RUNNING` (except Start, which has no ordinary decline path for its own first execution - see Session Runtime Lobby Lifecycle Contract above).
- **Executor infrastructure failure** - `*executor.ExecutorError`: a failure to run the script at all (the Executor was unreachable, the call failed, or the deadline was exceeded). This is not "bad input, try again": the attempted RuntimeTurn does not commit, no partial effect becomes authoritative, the previous RuntimeTurn's `new_state` remains the last valid state, and the Session becomes `TERMINAL` with internal terminal reason `RUNTIME_EXECUTION_FAILED`.
- **Transient infrastructure failure** - temporary Postgres unavailability, transaction/deadlock/serialization retry, transient network/dependency failure, transaction timeout, or process crash, where the authoritative Session transaction did not commit and durable state remains valid. This does not terminalize the Session merely because infrastructure temporarily failed; the last committed authoritative state is preserved and the operation may fail/retry under normal infrastructure policy, consistent with the existing process-agnostic crash-rollback semantics above.

A fatal attempted execution (the Executor-infrastructure-failure class) does not become a `session_runtime_turns` row. If the current authoritative Turn is 41 and the next attempt fails, `current_turn_id` remains 41, no Turn 42 exists, and no gameplay consequence from the failed attempt persists - Session Runtime does not fabricate a Turn to represent the failure.

`session_runtime_failures` records this fatal class: `id`, `session_id`, `failure_kind` (`RUNTIME_EXECUTION`), `error_code` (the one stable code the Executor-driven fatal path records, operator/debug only, never exposed to players), `error_message` (technical diagnostic text, operator/debug only), `base_turn_id` (nullable - the last successfully committed authoritative RuntimeTurn before the fatal attempt when one exists; `NULL` specifically means the fatal failure occurred before any RuntimeTurn ever committed for this Session, including a fatal failure during Start's own first execution), `attempted_sequence` (diagnostic only), `source_kind`, `source_timer_obligation_id` (nullable), `actor_id` (nullable), `diagnostic_payload` (a minimal forward-compatible envelope), and `created_at`.

For an Executor infrastructure failure, Session Runtime performs atomic fatal materialization in one Session transaction rather than rolling back the attempted Turn and separately terminalizing the Session as two operations: validate/serialize the Session; attempt execution; encounter the fatal failure; persist no attempted RuntimeTurn; persist the `SessionRuntimeFailure`; set `phase = TERMINAL`, `terminal_reason = RUNTIME_EXECUTION_FAILED`, and `terminal_at` to the fatal materialization instant; commit. The durable result is atomic - either the Session remains at its previous valid state because the transaction itself failed, or the Session is `TERMINAL` with its fatal diagnostic record committed together with it. If infrastructure fails before this transaction commits, the previous Session state remains authoritative and no fatal terminalization or `SessionRuntimeFailure` is considered to have happened - an infrastructure retry problem, not a Session-domain event.

`session_runtime_failures` is not created for an expected script rejection, an authored game-completion/failure outcome, or a host `CancelSession` the script itself reacted to, nor for transient infrastructure/database errors; the table represents terminal/internal runtime failure diagnostics, not every failed request.

`RUNTIME_EXECUTION_FAILED` projects to clients as a generic public terminal category equivalent to `INTERNAL_ERROR` (exact enum/DTO naming not frozen); clients must never receive raw technical detail (`error_message`, `diagnostic_payload`, or internal DB/runtime identifiers).

Live clients may be notified of the terminal failure only after `Session TERMINAL` + `SessionRuntimeFailure` commit durably - fatal attempt, then durable terminal commit, then post-commit Coordinator delivery/fanout; correctness must not depend on successful delivery, since a client that misses the live notification still discovers `phase = TERMINAL`/`INTERNAL_ERROR` through the already-accepted resync capability above.

Failed Sessions remain normal terminal Sessions for archival eligibility (see Session Runtime History Archival Direction below). `session_runtime_failures` is not automatically classified as hard-deletable heavy history like the other runtime-history tables; lightweight runtime-failure metadata should remain queryable relationally in PostgreSQL after heavy runtime-history archival. Large diagnostic-payload retention/compaction strategy may be optimized later and is not designed here.

### Terminal Cleanup: No ACTIVE Obligations After Terminalization

Once a Session becomes semantically `TERMINAL`, it must not retain executable runtime obligations in `ACTIVE` state, regardless of terminal cause - authored script completion, lobby expiration, inactivity expiration (`RUNTIME_INACTIVITY_EXPIRED`), runtime execution failure, or any other future terminal reason. Any still-open `session_timer_obligations` are cancelled as part of terminal-state materialization, in the same transaction that materializes `TERMINAL`: Session -> `TERMINAL`; `ACTIVE` timer obligations -> `CANCELLED`; terminal metadata (and failure metadata where applicable) persisted; commit. A durable state where `Session.phase = TERMINAL` while an `ACTIVE` timer obligation still exists must never occur.

This cleanup is Session lifecycle cleanup, not gameplay: it does not execute the authored script, does not create a RuntimeTurn, and does not fabricate a timer expiration - the Session ending is what cancels these obligations, not any script execution.

Closure provenance distinguishes this from ordinary Turn-caused closure. The existing `closed_by_turn_id` represents closure produced by a committed RuntimeTurn; when closure instead happens because the Session itself terminalized, `closed_by_turn_id = NULL` is valid, paired with a closure reason/state equivalent to `SESSION_TERMINATED` distinguishing it from runtime-produced closure. This closure reason only explains "this obligation stopped being active because the Session terminated" - not why the Session terminated, which remains discoverable through the Session's own lifecycle/failure metadata (`terminal_reason`, and `session_runtime_failures` where applicable) rather than duplicated onto every closed obligation. Existing state vocabularies are reused where possible (interactions: `ACTIVE -> terminally closed/cancelled`; timer obligations: `ACTIVE -> CANCELLED`); the invariant matters more than exact enum naming, which remains an implementation-planning detail.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0016-session-runtime-failure-classification-and-diagnostic-persistence.md` and, for the Step-limit fatal case, terminal cleanup invariant, and pre-first-Turn `base_turn_id` refinement, `session/docs/decisions/SESSION-ADR-0018-runtimeturn-execution-bound-and-terminal-cleanup.md`.

## Session Runtime Durable Inactivity Expiration

Status: HUMAN-APPROVED; schema/renewal/lazy-materialization implemented by `WORK-0016-inactivity-expiration-reaper.md` - the background Session Reaper described below remains not implemented, split to a separate not-yet-drafted WORK.

Every `RUNNING` Session has a durable inactivity deadline, `sessions.activity_expires_at`, distinct from `lobby_expires_at`. It is not a process ownership lease; it answers until what instant the platform still considers the Session active absent meaningful activity, so abandoned Sessions and crashed-process Sessions eventually leave hot `RUNNING` state and become eligible for terminalization and archival.

Meaningful Session operations that demonstrate continued active use extend `activity_expires_at = now + inactivity_ttl`. V1 may use a configurable TTL around 10 minutes; the exact duration is configurable operational/product policy, not hard-coded Game Language semantics. Only operations that constitute meaningful evidence of active use may renew the deadline - for example successful RuntimeTurn-producing gameplay operations, accepted interaction processing, timer expiration processing, meaningful lifecycle/runtime events, or justified authenticated reconnection/resume activity (illustrative, not exhaustive) - arbitrary passive reads/polling must not renew it.

`activity_expires_at` is the source of truth: semantic expiration occurs because the deadline passed, not because a Reaper happened to discover the Session, mirroring the already-accepted `lobby_expires_at` -> lobby-expiration-terminal-reason pattern. Any Session Runtime operation that requires the Session still be active must, under the normal per-Session serialization mechanism, load/lock the Session, validate lifecycle, compare current time with `activity_expires_at`, and only if not expired may it process the operation and potentially renew the deadline; an operation arriving after the deadline must not revive the Session merely because persisted `phase` still says `RUNNING`. Such an operation may instead atomically materialize, in the same transaction, `phase = TERMINAL`, `terminal_reason = RUNTIME_INACTIVITY_EXPIRED`, and `terminal_at = activity_expires_at`, then reject the attempted action - without renewing the deadline, reopening the Session, fabricating gameplay, or creating an engine RuntimeTurn merely to represent expiration.

A background Session Reaper proactively finds Sessions where `phase = RUNNING` and `activity_expires_at <= now` but the persisted lifecycle representation has not yet been materialized, and - using the same Session serialization rules as normal mutations - re-validates and materializes `TERMINAL`/`RUNTIME_INACTIVITY_EXPIRED` if still expired; if a legitimate operation already won the serialization race and renewed the deadline, the Reaper rechecks and does nothing. The deadline, not Reaper scheduling latency, decides the outcome. `terminal_at` always equals `activity_expires_at`, never the Reaper's or a lazy operation's current wall-clock time - this matters for historical correctness, retention windows, archival timing, and analytics (for example, a multi-day platform outage does not move the semantic terminal instant forward). `terminal_reason = RUNTIME_INACTIVITY_EXPIRED` means only that the `RUNNING` Session exceeded its allowed inactivity period; it does not assert a process crashed, a pod was killed, the host disconnected, every participant left, or any other specific root cause.

The Archive Worker (see Session Runtime History Archival Direction below) remains completely separate from this mechanism: it consumes already-materialized `TERMINAL` Sessions under archival retention policy and must not inspect process ownership, detect crashes, determine `RUNNING` inactivity, or interpret `activity_expires_at` to mutate lifecycle. Once a Session is semantically `TERMINAL`, future gameplay timer/interactions are no longer executable as active gameplay; still-open `session_interactions`/`session_timer_obligations` are closed/cancelled atomically as part of the same terminal materialization (see Terminal Cleanup: No ACTIVE Obligations After Terminalization above), and materializing expiration must never fabricate engine responses or RuntimeTurns to close gameplay.

Merely reconstructing infrastructure mechanisms after a Coordinator/process restart - scanning `RUNNING` Sessions, loading a current Snapshot, discovering active `session_timer_obligations`, rescheduling physical timers, discovering durably `CONNECTED` actors (see Session Runtime Process-Agnostic Recovery above), starting a Coordinator recovery grace, or rebuilding Coordinator maps - does not by itself renew `activity_expires_at`; otherwise infrastructure restarts could keep an abandoned Session alive indefinitely. A later real operation, such as an authenticated reconnect, may separately qualify as meaningful activity under the renewal policy above. See `session/docs/decisions/SESSION-ADR-0015-session-semantic-presence-recovery-after-total-coordinator-state-loss.md`.

Rationale and alternatives, including the rejected process-ownership/heartbeat cleanup direction, are recorded in `session/docs/decisions/SESSION-ADR-0013-session-runtime-durable-inactivity-expiration.md`.

## Session Runtime History Archival Direction

PostgreSQL remains the hot/runtime store. After a Session reaches an appropriate terminal/archiveable condition, heavy runtime history may eventually be serialized into a versioned JSON artifact written to long-term object storage such as Google Cloud Storage; the exact archive schema and storage implementation are deferred. Archive metadata (`session_history_archives`) tracks this per Session with a provider/key identifier rather than an expiring URL.

Heavy runtime/history tables (`session_runtime_turns`, `session_runtime_steps`, `session_interactions`, `session_timer_obligations`) may become an explicit hard-delete exception, but only after the long-term archive is successfully written and verified. `sessions.current_turn_id` (SESSION-ADR-0022) is not itself hard-deleted - it is a logical reference that keeps identifying the Session's last-current Turn even after that Turn's own row is archived away, resolving against the archive artifact instead of a live row. `session_actors` and `session_participants` are excluded from this deletion policy and remain relationally stored indefinitely, since they support ongoing product queries such as which Sessions a User participated in. `session_runtime_failures` (see Session Runtime Failure Classification And Diagnostic Persistence above) is likewise excluded from automatic hard-delete: lightweight fatal-runtime-failure metadata remains queryable relationally after heavy runtime-history archival, pending a separately designed retention/compaction strategy if diagnostic-payload volume ever warrants one.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0008-session-runtime-history-archival-and-hard-delete.md` and, for `session_runtime_failures` specifically, `session/docs/decisions/SESSION-ADR-0016-session-runtime-failure-classification-and-diagnostic-persistence.md`.

**Superseded in part (2026-09-20):** the archive destination is PostgreSQL (a same-database JSONB `session_archives`-equivalent record, compacted in one transaction with the removable source rows), not GCS/object storage. The archive-metadata-entity concept and the verified-archival-before-hard-delete policy above are otherwise unchanged. See `session/docs/decisions/SESSION-ADR-0023-replay-first-session-runtime-persistence.md`.

## Session Runtime Disconnect, Reconnect, and Resynchronization Boundary

Three responsibilities remain distinct and must not collapse into one owner: the transport fact that a physical connection disappeared or returned (Coordinator); the platform/runtime semantic event that a Session User is now considered disconnected or reconnected (Session Runtime boundary); and the gameplay consequence of that event (Session Runtime + Game Language).

Loss of a physical connection is owned by the Live Session Coordinator and does not by itself deactivate `session_participants`, remove a Participant, free a gameplay slot, delete a SessionActor, or terminate the Session. Session Runtime does not add authoritative connection-state fields such as `is_connected`, `connection_id`, or `websocket_id`.

The Coordinator may apply a short, in-memory transport grace/debounce period when a connection disappears, to absorb transient failures (Wi-Fi loss, browser reconnection, socket replacement). A reconnect within this grace period rebinds the connection and cancels the pending escalation without Session Runtime/Game Language ever observing a semantic disconnect; the grace duration is not decided here and remains configurable/implementation-level. This grace period is not gameplay policy and is not the time a game gives a disconnected player before forfeiting/removing them.

If the grace period expires without reconnection, the Coordinator notifies Session Runtime that the User/SessionActor has semantically disconnected. Session Runtime serializes the resulting SessionActor `semantic_presence` transition (`CONNECTED -> DISCONNECTED`) per Session; a repeated disconnect report while already `DISCONNECTED` is idempotent and must not duplicate any Game Language disconnect effect. The Coordinator does not decide gameplay consequences such as removing, forfeiting, pausing, or terminating - and the consequence of the transition itself is phase-dependent:

- In `LOBBY`, semantic disconnect deactivates the active Participant and releases its slot (see Session Runtime Lobby Lifecycle Contract above); there is no root workflow yet, so no `UserDisconnected` signal exists to deliver.
- In `RUNNING`, semantic disconnect does not deactivate or remove the Participant from the runtime roster; Session Runtime translates the platform event into the accepted `UserDisconnected` Game Language signal (see Authored Game Language Disconnect/Reconnect Contract below), and authored Game Language - not Session Runtime - determines gameplay consequences.

Reconnect is not Join. Session Runtime resolves `(SessionUUID, UserUUID) -> existing SessionActor` and verifies the existing logical participation/session relationship; it must not create another SessionActor or Participant slot, consume another player slot, require a JoinCode, or rerun lobby Join admission. Transport reconnection does not imply gameplay reinstatement: if the game had already reacted to the semantic disconnect (removed, forfeited, disabled), a User may reconnect at the transport level while the current Game state still prevents them from resuming active gameplay. If the semantic disconnect had already been delivered to the game, a corresponding `UserReconnected` signal is delivered to Session Runtime/Game Language - but only for a SessionActor that was part of the current execution's `players` roster; an actor excluded from the roster at Start does not join the running game merely by reconnecting (see Session Runtime Lobby Lifecycle Contract above).

The accepted persistence model (`session/docs/SESSION_RUNTIME_PERSISTENCE_MODEL.md`) does not gain a connection-presence table for disconnect/reconnect. Live connection bindings and transport-grace state remain ephemeral Coordinator state; a full process restart may lose an in-flight grace period, which is acceptable for V1. Existing durable state (SessionActor, Participant, current RuntimeTurn/Snapshot, active SessionInteractions, active TimerObligations) remains sufficient for Session Runtime's authoritative business/runtime state.

After the Coordinator authenticates/rebinds a connection, it may request a Session resynchronization view from Session Runtime using `(SessionUUID, UserUUID)`. Resync is a read/reconstruction capability and does not mutate the game; the exact transport endpoint/DTO is not frozen here. Session Runtime must never return the raw internal `engine.Snapshot` as this contract - it produces a player-facing Session projection for the resolved SessionActor (conceptually: Session lifecycle/phase, current player-visible game state, that User's currently active SessionInteractions, and other accepted player-visible state), without leaking internal engine identities, paths, slots, or SessionActorIDs. The resync representation carries the current RuntimeTurn `sequence` as its monotonic version, so Coordinator/client can reason about stale prior deliveries; no second, independent version counter is introduced.

Reconnect during transport grace creates no RuntimeTurn: the Coordinator rebinds, cancels the pending grace, and resends current resync state, with no semantic disconnect/reconnect and no engine execution. Reconnect after an already-escalated semantic disconnect processes gameplay/runtime semantics first (delivering `UserReconnected`, which may produce a RuntimeTurn if the root workflow handles it) and only then builds resync from the resulting current state - the client is synchronized to what the game currently believes, not blindly restored to its pre-disconnect state.

Total loss of Coordinator/process state (a crash, a redeploy) does not itself mutate `semantic_presence`; durable `CONNECTED`/`DISCONNECTED` values survive unchanged, since `CONNECTED` already means only "no semantic disconnect edge processed yet," not "a live socket exists right now" (see Session Runtime Process-Agnostic Recovery above). When a new Coordinator process reconstructs a still-semantically-active Session and finds a durably `CONNECTED` actor with no current physical binding, it starts a fresh transport/recovery grace for that actor using this same grace mechanism - not a distinct process-crash-disconnect event. If the actor rebinds before that fresh grace expires, the SessionActor remains `CONNECTED`, no `UserDisconnected`/`UserReconnected` is emitted, and Coordinator simply resends normal resync state - this is what prevents an ordinary process restart/deployment from producing artificial disconnect/reconnect pairs for every still-connected player. If the fresh grace expires without a binding, Coordinator invokes this same ordinary semantic-disconnect path described above, and the already-accepted phase-dependent LOBBY/RUNNING rules apply unchanged. A durably `DISCONNECTED` actor receives no recovery grace, since there is no semantic uncertainty to absorb; a later connection uses the ordinary reconnect path above. Recovery grace must never revive a Session whose `lobby_expires_at`/`activity_expires_at` deadline already passed (see Session Runtime Lobby Lifecycle Contract and Session Runtime Durable Inactivity Expiration above), and V1 restarts the full configured grace duration after process loss rather than persisting elapsed/remaining grace time.

For a RUNNING runtime member, the `semantic_presence` transition and the corresponding `UserDisconnected`/`UserReconnected` Game Language processing commit as one Session transaction, so a crash can never durably record the presence edge while losing the corresponding authored lifecycle effect (or the reverse); an unhandled signal still commits the presence transition alone, consistent with the no-op RuntimeTurn rule below.

Different games may reasonably require different disconnect/reconnect behavior (continue, wait, start a timer, forfeit, remove, pause, end); the Game Language contract described below standardizes only the platform lifecycle signals themselves, not any particular game policy.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0009-session-disconnect-reconnect-resync-boundary.md`. The durable `session_actors.semantic_presence` field and the LOBBY-vs-RUNNING phase-dependent participation consequence above are recorded in `session/docs/decisions/SESSION-ADR-0014-session-actor-semantic-presence-and-lobby-membership.md`. The recovery-grace-after-total-process-loss behavior and the RUNNING atomic semantic-presence/Game-Language-processing rule are recorded in `session/docs/decisions/SESSION-ADR-0015-session-semantic-presence-recovery-after-total-coordinator-state-loss.md`.

### Authored Game Language Disconnect/Reconnect Contract

`UserDisconnected` and `UserReconnected` are standard `NamedSignalSource` platform/lifecycle signals - the same closed mechanism already used for `WorkflowStarted`/`SessionCancelled` - not new `SignalKind` variants. Each exposes exactly one authored field, `user: user` (the Session-local runtime identity derived from `SessionActorID`), and never `Identity.UserUUID`, connection/socket IDs, IP address, disconnect timestamp, transport-grace information, or other Coordinator internals. Session Runtime delivers both signals to the one workflow instance a Session runs; ask-group slots within it see the signal the same way any other transition does, since the engine executes a Session's entire game logic as a single flat workflow instance (see `game/docs/decisions/GAME-ADR-0026-flat-workflow-execution-model-and-keyed-interaction-slots.md`), not a tree of separately addressed instances.

Handling either signal is optional. If the root workflow declares no matching transition, this is an ordinary rejected/unmatched signal (`engineservice.ErrSignalRejected`) with no automatic gameplay consequence - Session Runtime must not infer remove/forfeit/pause/skip/end, and a rejected delivery that produces no `Commit` does not create a `RuntimeTurn` merely to record a no-op. "The game ignores disconnect" means only that disconnect itself does not mutate gameplay; it does not mean the platform guarantees continued progress.

An interaction/question targeted at a SessionActor whose transport connection is currently absent is still created as a normal durable `SessionInteraction` - Session Runtime must not suppress, auto-answer, skip, or redirect it, or deactivate the Participant, merely because the actor is offline. The interaction remains logically ACTIVE independent of live delivery; a later reconnect can surface it through the existing resync capability. Whether/how gameplay proceeds while an actor is offline (an authored timer/timeout deciding skip/default/forfeit, or legitimately remaining unresolved if no timeout applies) is ordinary authored Game Language policy, not a Session Runtime inference; a future max-runtime/inactivity/runaway protection may eventually terminate an abandoned Session but must never fabricate gameplay responses.

The compiler's `namedLifecycleSignals` schema for both signals is implemented (`docs/projects/active/session-runtime-v1/works/WORK-0018-game-language-disconnect-reconnect-signal-support.md`); Session Runtime's own delivery of either signal to a running workflow instance is not yet implemented (`docs/projects/active/session-runtime-v1/works/WORK-0015-disconnect-reconnect-full-resync.md`).

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0010-game-language-disconnect-reconnect-authored-semantics.md`.

### Keyed Timer Slots

The ordinary `TimerSlotDeclaration` holds at most one pending timer per statically named slot per workflow instance, which makes an authored policy such as an independent disconnect timeout per player awkward with a single static slot. Game Language implements a general `KeyedTimerSlotDeclaration` capability - distinct pending timers addressed by `(slot, key)`, so different keys (for example `disconnect_timeout[P1]` and `disconnect_timeout[P2]`) may have independent timers pending simultaneously, while at most one timer may be pending per exact tuple. Scheduling into an already-occupied `(slot, key)` is an execution error with no implicit reset/replace/coalesce, mirroring the ordinary `TimerSlot` rule; cancellation affects only the selected key and is idempotent; expiration exposes the authored key (`KeyedTimerExpiredSignalSource` binding `key: KeyType`) without exposing internal timer-obligation UUIDs or wall-clock scheduling data. This is a general language primitive - not a disconnect-specific `DisconnectTimer` - also usable for player cooldowns, team timers, per-object timers, and similar keyed processes. The Session Runtime persistence consequence (`session_timer_obligations.engine_key`) is implemented (`docs/projects/active/session-runtime-v1/works/WORK-0012-timer-obligations.md`): `Manager.ExpireTimer` durably schedules, cancels, and expires both the ordinary `TimerSlot` shape and independent `KeyedTimerSlot` occurrences.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0011-game-language-keyed-timer-slots.md`.

## Session Runtime Post-Commit Client Delivery Semantics

Status: HUMAN-APPROVED and canonically promoted; not yet implemented.

Once a Session Runtime transaction commits successfully, the resulting Session state is authoritative. A later failure to deliver Coordinator/WebSocket/client outputs must never roll back the RuntimeTurn, undo the Snapshot, reopen a closed interaction, undo a timer obligation, undo terminalization, or otherwise reinterpret the committed Session state. Conceptually: `runtime execution -> durable Session commit -> best-effort live delivery`. The commit is the correctness boundary; everything after it is delivery, not truth.

V1 does not introduce a generic durable outbox solely for WebSocket messages, Coordinator fan-out, client delivery, per-client acknowledgements, replay of every emitted live message, or replay of every intermediate presentation transition. No `session_delivery_outbox`, `delivery_attempts`, persistent connection delivery offset, or per-client ACK table is part of the accepted persistence model, unless a future, separately-approved requirement introduces one.

Anything required for authoritative gameplay correctness or client recovery must already be durable before live delivery is attempted - current RuntimeTurn/Snapshot, Session lifecycle state, SessionInteractions, SessionTimerObligations, semantic presence, terminal state, and fatal runtime diagnostic state where applicable are all already covered by prior accepted decisions. Live delivery communicates durable truth; it does not create that truth.

If live delivery fails, or the process dies after commit, a reconnecting client uses the already-accepted Session resync capability (see Session Runtime Disconnect, Reconnect, and Resynchronization Boundary above) to reconstruct the *current* player-facing truth - not a promise to reproduce every live message that was missed. Worked example: Turn 42 commits and opens interaction Q17; the process dies before Q17 is sent over WebSocket; after reconnect, Q17 is still an `ACTIVE` durable `SessionInteraction` and appears in the player's current resync projection - no generic delivery outbox is required for this to be correct. Client recovery in V1 is "recover current truth," not "replay every event/message since sequence N"; the current RuntimeTurn `sequence` may still identify the version a resync projection represents, but no guaranteed client event log/replay protocol is introduced.

Physical timer scheduling remains Coordinator-owned and ephemeral. If a Turn commits a durable, active SessionTimerObligation but the process dies before the in-memory physical timer is successfully established, the durable obligation remains authoritative; Coordinator recovery/reconciliation may rediscover and physically (re)schedule it under the already-accepted timer-recovery semantics (see Session Runtime Turn And Persistence Model and Session Runtime Process-Agnostic Recovery above). The Turn is never rolled back because physical scheduling failed after commit.

Purely ephemeral/presentation-oriented effects whose loss does not alter authoritative gameplay - animation, sound, confetti, and other presentation-only effects - may be lost if delivery fails, the socket disappears, the Coordinator crashes, or the process dies immediately after commit; V1 does not guarantee their replay after resync.

This best-effort delivery rule covers Coordinator/client/presentation delivery only. It must not silently become the reliability contract for a future Game Language output capable of causing an external irreversible side effect (payment, an external API mutation, a durable notification requiring delivery guarantees, a cross-domain command, or another irreversible external effect); such a capability must explicitly design its own delivery/idempotency/retry semantics as a separate decision.

Rationale and alternatives are recorded in `session/docs/decisions/SESSION-ADR-0019-session-runtime-post-commit-client-delivery-semantics.md`.
