# Session Runtime - Current State

Status: CURRENT IMPLEMENTATION

## Capability Status

| Area | Status | Notes |
| --- | --- | --- |
| Session creation | IMPLEMENTED | `play/session/workflows/sessionlifecycle` (`Manager.CreateSession`): idempotent per user and key, pins the Game's current EXECUTABLE version, creates the Session in LOBBY with a join code. Unit, repository and integration tests (incl. concurrent retries) pass, and `POST /sessions` was tested by hand locally. Flow: `play/docs/FLOWS.md`. |
| Game versions | SCHEMA ONLY | `play_games` / `play_game_versions` exist and are read by Session creation and Start (manifest, backend script and frontend package locators), but nothing creates them yet, so every creation answers `game_unavailable` until they are seeded. |
| Object storage | PARTIAL | `play/session/storage.Open` opens the GCS bucket named by `GCS_PROJECT_ID` / `GCS_BUCKET` (the Google client also honors `STORAGE_EMULATOR_HOST`, so an emulator needs only environment variables); used to load backend scripts and sign frontend package URLs. Optional: without those variables every storage call fails. Outside production, `main` stores the seed script and frontend package when a bucket is configured. Locally, the `gcs` service of `docker-compose` (fake-gcs-server; buckets `playhoot-dev` for the app and `playhoot-test` for tests, created from `local/gcs/`; objects stored as browsable files under `local/gcs-data/`, ignored by git) is selected with `GCS_PROJECT_ID=playhoot-local`, `GCS_BUCKET=playhoot-dev` and `STORAGE_EMULATOR_HOST=http://localhost:4443`; under an emulator, URLs are signed with a throwaway key (the emulator checks no signature) and use http. |
| Live Session Runtime | PARTIAL | One controller per live Session (`play/runtime/workflows/liveconnection`, `play/docs/decisions/SESSION-ADR-0030-the-session-controller-owns-its-live-execution.md`) holds its state, runs admission, SAMPLE ingress, COMMANDs, Start and the running game's ticks, and owns its Sandbox context. From creation until it ends, its main goroutine runs everything that touches the Sandbox or the database (the single mutation lane). The `liveconnection` ControllerResolver only finds or creates controllers (even for a connection then rejected) and stops them on shutdown. The rows below describe each operation. |
| Live Session ownership | PARTIAL | `play/runtime/usecases/ownership` (`LocateOrClaimOwner`) is called by the API before every live upgrade. It claims only live Sessions: it asks the durable Session (`play/session/usecases/checklivesession`, real: LOBBY before its expiry, or RUNNING) and answers `session_unavailable` (404, no controller created) for any other. Every live Session is owned by this instance under epoch 1: there is no registry, release or lease yet (see Placeholders). Design: `play/docs/decisions/SESSION-ADR-0029-live-session-ownership-and-owner-routing.md`. |
| Admin connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachAdmin`) finds or creates the Session's controller, which asks the durable Session whether the caller may join as admin (`play/session/usecases/checkadminjoin`, real: RUNNING, or LOBBY before its expiry, and the caller is the creator), reads its manifest on the first admission and registers the ADMIN connection; several may be attached at once. Tested, and tested by hand from Postman. Lobby updates are real, and so is `StartSession`'s orchestration (see Start Session). `SelectPerspective`, `CancelSession` and the admin's views are not implemented yet: they answer "not implemented" and the API closes the connection. |
| Player connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachPlayer`) finds or creates the Session's controller, which asks the durable Session whether it accepts players (`play/session/usecases/checkplayerjoin`: LOBBY before its expiry; RUNNING is `session_started`), then admits into the lobby: up to the manifest's maximum, the same user's older connection replaced, every change sent to admins and players. Leaving or disconnecting takes the player out at once. Tested, run end to end, and tested by hand. Start moves the controller to running and sends each player `session_started` and a FULL first view; the operations of a running game are not built. |
| Start Session | PARTIAL | `play/runtime/workflows/liveconnection` (`startSession`, behind `AdminConnection.StartSession`, run on the controller's main goroutine while the caller waits): the controller freezes the lobby and numbers it P1..Pn, the durable Session validates, the Sandbox runs `start()` and the first projections (retried once in a fresh context on a script failure), the initial checkpoint is stored before the Session is committed RUNNING, then every connection gets `session_started` (roster and a signed, expiring URL to the game's frontend package, issued by the durable Session) and each player a FULL view. A second script failure aborts the Session (`start_failed`, connections end `session_aborted`); any other failure returns it to its lobby. A start requested while the database already has the Session RUNNING (a lost commit answer, or a controller created after a restart) adopts it: the game runs from the committed roster and latest checkpoint in a restored Sandbox context, answered `already_started`. The durable side is real (`sessionlifecycle`: `CheckStartEligibility`, `CommitStart` in one transaction with roster + checkpoint + RUNNING + join code release, `AbortStart`; `frontendaccess.FrontendAccess`), tested with unit, repository and integration tests against Postgres. Flow: `play/docs/FLOWS.md`. |
| Runtime manifest | PARTIAL | `play_game_versions.manifest` (versioned JSON, `schema_version` 1) holds the player limits, the optional entrypoints (`entrypoints`: only `update` so far), the SAMPLE inputs (`inputs`: boolean, number, vector2, string, enum, with natural zeros or declared defaults; rules in `play/internal/business/inputs`, shared with the Runtime) and the COMMANDs (`commands`: name to `payload` fields declared like inputs; `play/internal/business/commands`); `play/session/internal/business/manifest` validates it and `play/session/usecases/loadruntimemanifest` loads it when a Session's controller admits its first connection. Other manifest facts (entrypoints, capabilities) are not declared yet. |
| Running game (SAMPLEs, COMMANDs, update() and ticks) | PARTIAL | A started game's controller runs a boundary on its main goroutine (`play/runtime/workflows/liveconnection`, `step_boundary.go`) every 100 ms, or when an operation asks for a flush, it executes the SAMPLE transitions the controller accepted (normalized against the manifest, stale sequences ignored, refreshes deduplicated, every distinct transition kept in arrival order across players, stamped with effective Session time), together with the COMMANDs in between and, when the manifest declares `update`, a final `update(state, context)` at the boundary's time on every tick (even with nothing pending; never queued, so a slow game never accumulates missed updates), as one atomic batch in timeline order (adjacent transitions share a `samples(state, transitions, context)` call, each command runs `command(state, cmd, context)`). Every operation runs at its own Session time and `context.elapsed` is the time since the previous operation: a run of transitions ends at its last transition, except when it ends a batch without update, which runs until the boundary's time; a batch without update ending with a command ends at the command. It then commits the new mirror, projects every participant and sends each player connection only the fields that changed plus how far their SAMPLEs were consumed. Failures follow the plan: infrastructure failures retry in a context restored from the mirror, script failures retry once then abort the Session (SCRIPT_FAILURE), and 50 failed boundaries in a row abort it (UNRECOVERABLE_INFRA_FAILURE). A disconnect resets the participant's inputs at once and starts a 3 s transport grace (platform time): within it the same user reattaches through `AttachPlayer` (also a device switch, which ends the older connection as `replaced`), without the game being told, getting `session_started` and a FULL view from the per-participant projection cache, and numbering its SAMPLEs anew on the new connection. When the grace runs out the next boundary runs `playerDisconnected(state, participant, context)` (required in every script) and the participant is disconnected; attaching again is rejected `participant_disconnected` until rejoin exists. A `leave` in a running game is the same disconnection without the grace (`play/docs/decisions/SESSION-ADR-0032-leaving-is-an-immediate-disconnection.md`): inputs reset, `playerDisconnected()` on the timeline, a boundary at once, the connection ended as `left`. Once every participant is disconnected and the game was told, the Session is cancelled durably (`sessionlifecycle.CancelAbandonedSession`: CANCELLED, `ALL_PLAYERS_LEFT`, by the platform; metric `play_session_abandoned_cancelled_total`) and ended live; a failed write is tried again at the next boundary. Metric `play_runtime_participants_disconnected_total{cause}` (`grace_expired`, `left`). Participant presence is not in checkpoints yet. Metrics `play_runtime_player_transports_detached_total` and `play_runtime_player_attach_total{outcome="reattached"}`. There are no platform timers, by decision (`play/docs/decisions/SESSION-ADR-0031-game-time-is-handled-by-update-without-platform-timers.md`): a game keeps its deadlines in its state and checks them in update(). Replay captures are dropped. `play_runtime_update_interval_seconds` measures the wall time between a game's committed updates. Each boundary, a tick or a flush asked by a COMMAND, ends with one update() and sends each player one view of the batch's final state; a COMMAND's response is a separate message sent when that batch commits. Logical errors: `samples()`, `command()` and `update()` may return `errors: [{participant, error}]` next to their state (`error` any JSON but null); once the batch commits, each player's errors travel in that boundary's view (`OwnView.Errors`, sent even when the view did not change) and every error is offered to replay with its participant, Session time and timeline order. They are transient: never kept by the controller nor in checkpoints, not resent on resync, lost with a failed batch. An error to someone who does not play, or a malformed `errors`, is a script failure. Metric `play_runtime_game_errors_total`. Logical events work the same way: the three may return `events: [{event, participants?}]` (broadcast without `participants`); each player receives the ones for them in that boundary's view (`OwnView.Events`), replay gets them with their targets (`replay.Capture.Events`), and they are never kept nor checkpointed. Metric `play_runtime_game_events_total`. Tested, and run end to end (Space Drift keeps drifting without input). |
| COMMANDs | IMPLEMENTED | A player's `command` (token, name, payload) is checked against the manifest before any JavaScript (undeclared name or invalid payload: `invalid`; payload completed with its defaults), its token deduplicated per participant (executed: `already_processed`; the same token while pending is enqueued once and its duplicate answered `already_processed`), then placed on the timeline and a boundary is requested at once. The caller waits until the batch commits and gets `executed` with the game's response (a rejection by the game's rules is a normal response); the token is then processed for the Session's lifetime (kept in the checkpoint document and restored on adoption; only the initial checkpoint is written so far, so the tokens reach checkpoints once periodic checkpoints exist), the response is offered to replay with its participant (dropped by the replay placeholder until the recorder exists), and views are sent. A Session ending while a command is pending answers it `session_not_running`. Metrics `play_runtime_commands_total{outcome}` and `play_runtime_command_duration_seconds{outcome}`. Space Drift has a `teleport` command to test it by hand. Tested (controller, boundary, sandbox) and run end to end. Tested, run end to end, and tested by hand with the Space Drift seed game. |
| Join code resolution | IMPLEMENTED | `play/session/usecases/resolvejoincode` (`ResolveJoinCode`): an unreleased, unexpired join code names its Session (matched case-insensitively); anything else is `not_found`. Called by the API before routing a player who joins by join code. Unit and repository tests. Flow: `play/docs/FLOWS.md`. |
| Sandbox | PARTIAL | `play/runtime/sandbox.Host`: one execution context per running Session, each a long-lived worker process (a re-exec of the binary, `RunAsWorkerIfRequested` first thing in `main`) hosting a QuickJS-on-WebAssembly runtime with the script loaded. No host capability: a patched copy of qjs (`third_party/qjs`, see its `PLAYHOOT_PATCH.md`, which also fixes upstream's use-after-free when serializing results and its leaked C strings) mounts no directory and gives wazero's fake clocks and randomness, so even the `qjs:std`/`qjs:os` modules reach no file, environment, network or real time; the host helpers (`std`, `print`, `setTimeout`...) are removed; the worker process also runs with an empty environment (defense in depth). The script runs in strict mode and, once loaded, every global and builtin is deep-frozen, so no state can live outside what executions return; arguments are deep-frozen, and `Math.random` throws inside `project()`. Limits: 64 MiB memory and 1 MiB stack per context, a 5 s execution budget per call enforced by killing the worker (reported as a script failure), and per instance at most `SANDBOX_MAX_CONTEXTS` contexts (default 32; beyond that Start answers `sandbox_unavailable`) and `SANDBOX_MAX_CONCURRENT_EXECUTIONS` calls at once (default: CPUs). Script contract: `start(participants, context)` returns `{ state }`, `project(state, participant, context)` returns the view; `samples(state, transitions, context)` returns `{ state }` and `command(state, cmd, context)` (cmd `{participant, name, payload, sessionTime}`) returns `{ state, response }`; `update(state, context)` and `playerDisconnected(state, participant, context)` return `{ state }`; these may add `errors: [{participant, error}]` and `events: [{event, participants?}]`, the logical errors and events of that call (at most 256 KiB each); `Date` is the effective Session time (0 at start) and `Math.random` a seeded mulberry32 whose state is exported (4 bytes) for the checkpoint; the context revision is 1 after start. Called by Start; start, restore, execute (a batch of `samples()`, `command()` and `update()` steps) and project exist. Every worker compiles the runtime when it starts, so creating a context costs about half a second of CPU. Capacity and resource metrics (`play_runtime_sandbox_*`: active contexts and limit, capacity rejections, executions in flight and limit, slot waits, execution durations by operation and outcome, worker stops by reason, output sizes, worker memory) are recorded by the sandbox. `play/runtime/sandbox/scriptcheck` statically validates a script for publication (no module or global state, no mutation of inputs, AST-based); nothing calls it yet. |
| Migrations | IMPLEMENTED | One migration creates the tables in `play/docs/DATA_MODEL.md`. |

## Placeholders (wired, but not real behavior)

- No flow registers Games or makes versions executable in `play_games` / `play_game_versions`. Outside production, test-data migrations (`play/session/internal/migrations/seed_*.go`, applied by `main` via `PostgresSeed`) insert a playable Game `11111111-1111-4111-8111-111111111111` (EXECUTABLE current version `11111111-1111-4111-8111-0000000000a1` with a seed backend script and frontend package, stored by `main` through `SeedObjects` when a bucket is configured, plus a newer DRAFT) an unavailable Game `22222222-2222-4222-8222-222222222222` (DRAFT only), and Space Drift `33333333-3333-4333-8333-333333333333` (EXECUTABLE version `33333333-3333-4333-8333-0000000000c1`; inputs `move` vector2 and `boost` boolean, command `teleport`, `update()`, one to eight players): ships flying in a shared arena with drag, wall bounces and a star to collect, for testing SAMPLEs, COMMANDs, update() and replication by hand. Its rules are in the script's opening comment (`seed_20261018000000_space_drift.go`); it integrates its physics up to each operation's time, and `update()` keeps it moving between inputs; anywhere else creation answers `game_unavailable`.

- `play/runtime/usecases/ownership.Service.LocateOrClaimOwner` answers `owned_here` with epoch 1 for every live Session, without a registry. Real behavior: an in-process registry claims and releases ownership; before more than one instance may own Sessions, a shared registry with an owner-renewed lease and heartbeat (SESSION-ADR-0029).
- The admin connection's `SelectPerspective` and `CancelSession` (`play/runtime/workflows/liveconnection`) return "not implemented", and `NextView` never produces a view.
- No object storage is configured by default: without `GCS_PROJECT_ID` / `GCS_BUCKET` every storage call fails (`objectstore.Unconfigured`). Locally the emulator is configured (see Object storage); deployed environments still need their bucket, chosen by environment variables only.
- A started game's Sandbox context is discarded when its Session ends here (aborted) or its controller is retired. Nothing else ends a running game yet, so otherwise the context lives until the process exits.
- During a Start attempt, a player's `Leave` returns "not implemented" (as in a running game).
- A player connection's `Resync` does nothing (`play/runtime/workflows/liveconnection`); before the game runs `Command` answers `session_not_running` and `Sample` is dropped (right), and in a running game `Leave` returns "not implemented".
- The replay recorder (`unwiredReplay` in `unwired.go`) drops every capture a running game offers.
- A running game never stops by itself: its controller's main goroutine keeps ticking until the Session is aborted, its controller is retired or the process stops, even with every player gone (no inactivity, lifetime or finish yet). A game with `update()` executes JavaScript and projects every participant on every tick meanwhile.
- View delivery has no backpressure: a slow connection's queued views grow without bound.
- Session controllers are never destroyed, so they accumulate for the process lifetime. Real behavior: destroyed, and ownership released, when the Session reaches a terminal state.
