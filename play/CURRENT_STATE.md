## Capability Status

| Area | Status | Notes |
| --- | --- | --- |
| Session creation | IMPLEMENTED | `play/session/workflows/sessionlifecycle` (`Manager.CreateSession`): idempotent per user and key, pins the Game's current EXECUTABLE version, creates the Session in LOBBY with a join code. Unit, repository and integration tests (incl. concurrent retries) pass, and `POST /sessions` was tested by hand locally. Flow: `play/docs/FLOWS.md`. |
| Game versions | SCHEMA ONLY | `play_games` / `play_game_versions` exist and are read by Session creation and Start (manifest, backend script and frontend package locators), but nothing creates them yet, so every creation answers `game_unavailable` until they are seeded. |
| Object storage | PARTIAL | `play/session/storage.Open` opens the GCS bucket named by `GCS_PROJECT_ID` / `GCS_BUCKET` (the Google client also honors `STORAGE_EMULATOR_HOST`, so an emulator needs only environment variables); used to load backend scripts and sign frontend package URLs. Locally, the `gcs` service of `docker-compose` (fake-gcs-server; buckets `playhoot-dev` for the app and `playhoot-test` for tests, created from `local/gcs/`; objects stored as browsable files under `local/gcs-data/`, ignored by git) is selected with `GCS_PROJECT_ID=playhoot-local`, `GCS_BUCKET=playhoot-dev` and `STORAGE_EMULATOR_HOST=http://localhost:4443`; under an emulator, URLs are signed with a throwaway key (the emulator checks no signature) and use http. |
| Live Session Runtime | NOT IMPLEMENTED | No controller, live connections, or game execution. The direction is the real-time runtime of `play/docs/decisions/SESSION-ADR-0028-real-time-session-runtime-supersedes-discrete-turn-architecture.md`. |
| Live Session ownership | PLACEHOLDER | `play/runtime/usecases/ownership` (`LocateOrClaimOwner`) is called by the API before every live upgrade, but answers that this instance owns every Session. Design: `play/docs/decisions/SESSION-ADR-0029-live-session-ownership-and-owner-routing.md`. |
| Admin connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachAdmin`) asks the durable Session whether the caller may join as admin (`play/session/usecases/checkadminjoin`, real: RUNNING, or LOBBY before its expiry, and the caller is the creator), finds or creates the Session's controller (`play/runtime/internal/controller`) and registers the ADMIN connection; several may be attached at once. Tested, and tested by hand from Postman. Lobby updates are real, and so is `StartSession`'s orchestration (see Start Session). `SelectPerspective`, `CancelSession` and the admin's views are not implemented yet: they answer "not implemented" and the API closes the connection. |
| Player connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachPlayer`) asks the durable Session whether it accepts players (`play/session/usecases/checkplayerjoin`: LOBBY before its expiry; RUNNING is `session_started`), then the controller admits into the lobby: up to the manifest's maximum, the same user's older connection replaced, every change sent to admins and players. Leaving or disconnecting takes the player out at once. Tested, run end to end, and tested by hand. Start moves the controller to running and sends each player `session_started` and a FULL first view; the operations of a running game are not built. |
| Start Session | PARTIAL | `play/runtime/workflows/liveconnection` (`startSession`, behind `AdminConnection.StartSession`): the controller freezes the lobby and numbers it P1..Pn, the durable Session validates, the Sandbox runs `start()` and the first projections (retried once in a fresh context on a script failure), the initial checkpoint is stored before the Session is committed RUNNING, then every connection gets `session_started` (roster and a signed, expiring URL to the game's frontend package, issued by the durable Session) and each player a FULL view. A second script failure aborts the Session (`start_failed`, connections end `session_aborted`); any other failure returns it to its lobby. A start requested while the database already has the Session RUNNING (a lost commit answer, or a controller created after a restart) adopts it: the game runs from the committed roster and latest checkpoint in a restored Sandbox context, answered `already_started`. The durable side is real (`sessionlifecycle`: `CheckStartEligibility`, `CommitStart` in one transaction with roster + checkpoint + RUNNING + join code release, `AbortStart`; `frontendaccess.FrontendAccess`), tested with unit, repository and integration tests against Postgres. The Sandbox is still a failing stand-in (see Placeholders), so a real start still fails today. Flow: `play/docs/FLOWS.md`. |
| Runtime manifest | PARTIAL | `play_game_versions.manifest` (versioned JSON, `schema_version` 1) holds the player limits; `play/session/internal/business/manifest` validates it and `play/session/usecases/loadruntimemanifest` loads it when a Session's controller is created. Other manifest facts (inputs, commands, entrypoints, capabilities) are not declared yet. |
| Join code resolution | IMPLEMENTED | `play/session/usecases/resolvejoincode` (`ResolveJoinCode`): an unreleased, unexpired join code names its Session (matched case-insensitively); anything else is `not_found`. Called by the API before routing a player who joins by join code. Unit and repository tests. Flow: `play/docs/FLOWS.md`. |
| Sandbox | PARTIAL | `play/runtime/sandbox.Host`: one execution context per running Session, each a long-lived worker process (a re-exec of the binary, `RunAsWorkerIfRequested` first thing in `main`) hosting a QuickJS-on-WebAssembly runtime with the script loaded. No host capability: a patched copy of qjs (`third_party/qjs`, see its `PLAYHOOT_PATCH.md`) mounts no directory and gives wazero's fake clocks and randomness, so even the `qjs:std`/`qjs:os` modules reach no file, environment, network or real time; the host helpers (`std`, `print`, `setTimeout`...) are removed; the worker process also runs with an empty environment (defense in depth). The script runs in strict mode and, once loaded, every global and builtin is deep-frozen, so no state can live outside what executions return; arguments are deep-frozen, and `Math.random` throws inside `project()`. Limits: 64 MiB memory and 1 MiB stack per context, a 5 s execution budget per call enforced by killing the worker (reported as a script failure), and per instance at most `SANDBOX_MAX_CONTEXTS` contexts (default 32; beyond that Start answers `sandbox_unavailable`) and `SANDBOX_MAX_CONCURRENT_EXECUTIONS` calls at once (default: CPUs). Script contract: `start(participants, context)` returns `{ state }`, `project(state, participant, context)` returns the view; `Date` is the effective Session time (0 at start) and `Math.random` a seeded mulberry32 whose state is exported (4 bytes) for the checkpoint; the context revision is 1 after start. Called by Start; only start, restore and project exist. Every worker compiles the runtime when it starts, so creating a context costs about half a second of CPU. Capacity and resource metrics (`play_runtime_sandbox_*`: active contexts and limit, capacity rejections, executions in flight and limit, slot waits, execution durations by operation and outcome, worker stops by reason, output sizes, worker memory) are recorded by the sandbox. `play/runtime/sandbox/scriptcheck` statically validates a script for publication (no module or global state, no mutation of inputs, AST-based); nothing calls it yet. |
| Migrations | IMPLEMENTED | One migration creates the tables in `play/docs/DATA_MODEL.md`. |

## Placeholders (wired, but not real behavior)

- No flow registers Games or makes versions executable in `play_games` / `play_game_versions`. Outside production, test-data migrations (`play/session/internal/migrations/seed_*.go`, applied by `main` via `PostgresSeed`) insert a playable Game `11111111-1111-4111-8111-111111111111` (EXECUTABLE current version `11111111-1111-4111-8111-0000000000a1` with a seed backend script and frontend package, stored by `main` through `SeedObjects` when a bucket is configured, plus a newer DRAFT) and an unavailable Game `22222222-2222-4222-8222-222222222222` (DRAFT only); anywhere else creation answers `game_unavailable`.

- `play/runtime/usecases/ownership.Service.LocateOrClaimOwner` answers `owned_here` with epoch 1 for any Session UUID. Real behavior: only Sessions that exist in LOBBY or RUNNING are owned; an in-process registry claims and releases ownership; before more than one instance may own Sessions, a shared registry with an owner-renewed lease and heartbeat (SESSION-ADR-0029).
- The admin connection's `SelectPerspective` and `CancelSession` (`play/runtime/internal/controller`) return "not implemented", and `NextView` never produces a view.
- No object storage is configured by default: without `GCS_PROJECT_ID` / `GCS_BUCKET` every storage call fails (`objectstore.Unconfigured`). Locally the emulator is configured (see Object storage); deployed environments still need their bucket, chosen by environment variables only.
- Sandbox contexts of started games are never discarded: they live until the process exits (controllers are never destroyed, see below). Real behavior: discarded when the Session ends or its controller is retired.
- During a Start attempt, a player's `Leave` returns "not implemented" (as in a running game).
- A player connection's `Sample` is dropped and `Resync` does nothing (`play/runtime/internal/controller`); before the game runs `Command` answers `session_not_running` (right), and in a running game `Command` and `Leave` return "not implemented". `NextView` only produces the first FULL view of a started game.
- Session controllers are never destroyed, so they accumulate for the process lifetime. Real behavior: destroyed, and ownership released, when the Session reaches a terminal state.
