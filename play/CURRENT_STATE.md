| Live Session ownership | PARTIAL | `play/runtime/usecases/ownership` (`LocateOrClaimOwner`) is called by the API before every live upgrade. | Admin connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachAdmin`) finds or creates the Session's controller, which asks the durable Session whether the caller may join as admin (`play/session/usecases/checkadminjoin`, real: RUNNING, or LOBBY before its expiry, and the caller is the creator), reads its manifest on the first admission and registers the ADMIN connection; several may be attached at once. Admins get the game frontend in `session_started` like players. |
| Player connections | PARTIAL | `play/runtime/workflows/liveconnection` (`AttachPlayer`) finds or creates the Session's controller, which asks the durable Session whether it accepts players (`play/session/usecases/checkplayerjoin`: LOBBY before its expiry; RUNNING is `session_started`), then admits into the lobby: up to the manifest's maximum, the same user's older connection replaced, every change sent to admins and players. Leaving or disconnecting takes the player out at once. Tested, run end to end, and tested by hand. Start moves the controller to running and sends each player `session_started` and a FULL first view; the operations of a running game are not built. Display names and roster (2026-10-20, asked by the human for the frontend): `AttachPlayer` takes a `runtime.Player` (UserUUID and display name, built by the API from what Identity resolved); every lobby update and the started roster carry each player's display name, kept with the participants when the game starts (`play_session_participants.display_name`) so a recovered game still has them. Each player connection of a running game gets the whole roster with every participant's presence (`active`, `reconnecting`, `disconnected`, `left`) right after the start and whenever a presence changes: a transport lost (grace starts), the grace running out, a leave, a rejoin accepted, a reattach. A participant a recovered checkpoint had disconnected shows as `disconnected` (the cause is not checkpointed). Frontend access signed per connection (2026-10-20, asked by the human for the frontend): a player connection attaching to a running game (reattach, rejoin, device switch) and an admin connection attaching to it are told `session_started` with frontend access signed at that moment, not the one signed at the start, which expires after its TTL; signing runs outside the controller lock, and a failure falls back to the start's access (metric `play_runtime_frontend_access_signed_total{outcome}`). |
| Start Session | PARTIAL | `play/runtime/workflows/liveconnection` (`startSession`, behind `AdminConnection.StartSession`, run on the controller's main goroutine while the caller waits): the controller freezes the lobby and numbers it P1..Pn, the durable Session validates, the Sandbox runs `start()` and the first projections (retried once in a fresh context on a script failure), the initial checkpoint is stored before the Session is committed RUNNING, then every connection gets `session_started` (roster and a signed, expiring URL to the game's frontend package, issued by the durable Session) and each player a FULL view. A second script failure aborts the Session (`start_failed`, connections end `session_aborted`); any other failure returns it to its lobby. A start requested while the database already has the Session RUNNING (a lost commit answer, or a controller created after a restart) adopts it: the game runs from the committed roster and latest checkpoint in a restored Sandbox context, answered `already_started`. The durable side is real (`sessionlifecycle`: `CheckStartEligibility`, `CommitStart` in one transaction with roster + checkpoint + RUNNING + join code release, `AbortStart`; `frontendaccess.FrontendAccess`), tested with unit, repository and integration tests against Postgres. Flow: `play/docs/FLOWS.md`. |
| Runtime manifest | PARTIAL | `play_game_versions.manifest` (versioned JSON, `schema_version` 1) holds the player limits, the optional entrypoints (`entrypoints`: `update` and `playerRejoined`), the SAMPLE inputs (`inputs`: boolean, number, vector2, string, enum, with natural zeros or declared defaults; rules in `play/internal/business/inputs`, shared with the Runtime) and the COMMANDs (`commands`: name to `payload` fields declared like inputs; `play/internal/business/commands`); `play/session/internal/business/manifest` validates it and `play/session/usecases/loadruntimemanifest` loads it when a Session's controller admits its first connection. Other manifest facts (entrypoints, capabilities) are not declared yet. |
| Running game (SAMPLEs, COMMANDs, update() and ticks) | PARTIAL | A started game's controller runs a boundary on its main goroutine (`play/runtime/workflows/liveconnection`, `step_boundary.go`) every 100 ms, or when an operation asks for a flush, it executes the SAMPLE transitions the controller accepted (normalized against the manifest, stale sequences ignored, refreshes deduplicated, every distinct transition kept in arrival order across players, stamped with effective Session time), together with the COMMANDs in between and, when the manifest declares `update`, a final `update(state, context)` at the boundary's time on every tick (even with nothing pending; never queued, so a slow game never accumulates missed updates), as one atomic batch in timeline order (adjacent transitions share a `samples(state, transitions, context)` call, each command runs `command(state, cmd, context)`). Every operation runs at its own Session time and `context.elapsed` is the time since the previous operation: a run of transitions ends at its last transition, except when it ends a batch without update, which runs until the boundary's time; a batch without update ending with a command ends at the command. It then commits the new mirror, projects every participant and sends each player connection only the fields that changed plus how far their SAMPLEs were consumed. Each view carries its connection's `revision` (each FULL view or patch is the previous plus one; a view that changes nothing repeats it), so a client that lost a patch notices and sends `resync`, which answers a FULL view from the per-participant projection cache with the current acknowledgement, as a fresh baseline (metric `play_runtime_resyncs_total`). Failures follow the plan: infrastructure failures retry in a context restored from the mirror, script failures retry once then abort the Session (SCRIPT_FAILURE), and 50 failed boundaries in a row abort it (UNRECOVERABLE_INFRA_FAILURE). A disconnect resets the participant's inputs at once and starts a 3 s transport grace (platform time): within it the same user reattaches through `AttachPlayer` (also a device switch, which ends the older connection as `replaced`), without the game being told, getting `session_started` and a FULL view from the per-participant projection cache, and numbering its SAMPLEs anew on the new connection. When the grace runs out the next boundary runs `playerDisconnected(state, participant, context)` (required in every script) and the participant is disconnected; attaching again rejoins: when the manifest declares `playerRejoined`, the attach puts `playerRejoined(state, participant, context)` on the timeline, asks for a boundary and waits for its `{ state, accepted }` (requests of the same participant while one waits share it); accepted, the participant plays again through the reattach path (FULL view of the state the rejoin left, transport grace until a connection attaches); rejected, the attach is rejected `rejoin_rejected`; a game without it rejects `participant_disconnected`. Metric `play_runtime_rejoins_total{outcome}`. A `leave` in a running game is the same disconnection without the grace (`play/docs/decisions/SESSION-ADR-0032-leaving-is-an-immediate-disconnection.md`): inputs reset, `playerDisconnected()` on the timeline, a boundary at once, the connection ended as `left`. Once every participant is disconnected and the game was told, with no rejoin waiting, the Session is cancelled durably, whether the game supports rejoining or not (`sessionlifecycle.CancelAbandonedSession`: CANCELLED, `ALL_PLAYERS_LEFT`, by the platform; metric `play_session_abandoned_cancelled_total`) and ended live; a failed write is tried again at the next boundary. Metric `play_runtime_participants_disconnected_total{cause}` (`grace_expired`, `left`). Participant presence is not in checkpoints yet. Metrics `play_runtime_player_transports_detached_total` and `play_runtime_player_attach_total{outcome="reattached"}`. There are no platform timers, by decision (`play/docs/decisions/SESSION-ADR-0031-game-time-is-handled-by-update-without-platform-timers.md`): a game keeps its deadlines in its state and checks them in update(). Every committed boundary is offered to the Replay Recorder (see Replay recording). `play_runtime_update_interval_seconds` measures the wall time between a game's committed updates. Each boundary, a tick or a flush asked by a COMMAND, ends with one update() and sends each player one view of the batch's final state; a COMMAND's response is a separate message sent when that batch commits. Logical errors: `samples()`, `command()` and `update()` may return `errors: [{participant, error}]` next to their state (`error` any JSON but null); once the batch commits, each player's errors travel in that boundary's view (`OwnView.Errors`, sent even when the view did not change) and every error is offered to replay with its participant, Session time and timeline order. They are transient: never kept by the controller nor in checkpoints, not resent on resync, lost with a failed batch. An error to someone who does not play, or a malformed `errors`, is a script failure. Metric `play_runtime_game_errors_total`. Logical events work the same way: the three may return `events: [{event, participants?}]` (broadcast without `participants`); each player receives the ones for them in that boundary's view (`OwnView.Events`), replay gets them with their targets (`replay.Capture.Events`), and they are never kept nor checkpointed. Metric `play_runtime_game_events_total`. Tested, and run end to end (Space Drift keeps drifting without input). |
| COMMANDs | IMPLEMENTED | A player's `command` (token, name, payload) is checked against the manifest before any JavaScript (undeclared name or invalid payload: `invalid`; payload completed with its defaults), its token deduplicated per participant (executed: `already_processed`; the same token while pending is enqueued once and its duplicate answered `already_processed`), then placed on the timeline and a boundary is requested at once. The caller waits until the batch commits and gets `executed` with the game's response (a rejection by the game's rules is a normal response); the token is then processed for the Session's lifetime (kept in the checkpoint document and restored on adoption; only the initial checkpoint is written so far, so the tokens reach checkpoints once periodic checkpoints exist), the response is recorded in replay with its participant, and views are sent. A Session ending while a command is pending answers it `session_not_running`. Metrics `play_runtime_commands_total{outcome}` and `play_runtime_command_duration_seconds{outcome}`. Space Drift has a `teleport` command to test it by hand. Tested (controller, boundary, sandbox) and run end to end. Tested, run end to end, and tested by hand with the Space Drift seed game. |
| Session termination | IMPLEMENTED | Every end goes through `sessionlifecycle.Manager.EndSession` (one transaction: status, end cause, who caused it, status history, join codes released; a Session the cause does not apply to is reported as it is) and then, on the controller's main goroutine, ends every connection with `ConnectionEnd{SessionStatus, EndCause}`, which the API sends as `lobby_closed` (never started for that client) or `session_ended` (`{type, status, end_cause}`) before closing with 1000. No JavaScript runs, except a game its script finished. Causes: the game finishing (`finished: true` returned by `samples()`, `command()`, `update()`, `playerDisconnected()` or `playerRejoined()`; the batch stops at that operation, later commands answer `session_not_running`; the context is discarded, the final chunk is stored durably by the Replay Recorder's `Finish`, then FINISHED, then players get the final view and events, then connections end; a failure is retried each tick); the creator's `cancel_session` (lobby or running, `HOST_CANCELLED`); the lobby expiring (`LOBBY_EXPIRED`); the maximum lifetime (`play_sessions.expires_at`, creation + 4 h, `MAX_LIFETIME`); 10 minutes without a distinct SAMPLE transition or a COMMAND in a running game (`INACTIVITY_TIMEOUT`; refreshes, resyncs and update() do not count); every participant gone (`ALL_PLAYERS_LEFT`); script or infrastructure failures (ABORTED); and `ControllerResolver.TerminateSession` (`PLATFORM_TERMINATED`, CANCELLED; ready, nothing calls it yet). Deadlines are read once (`play/session/usecases/loadsessionlimits`) and checked every second. An ended controller is dropped from the resolver with its Sandbox context (`play_runtime_controllers_active`). Tested (unit, Postgres integration) and run end to end: lobby and running cancellation. Sessions nothing live ends are ended by the reconciliation job (`play/session/batches/reconcilesessions`, outside the lifecycle workflow, with its own repository; every 5 minutes on every instance, each pass until nothing due is left): expired lobbies, RUNNING Sessions past `expires_at` (`MAX_LIFETIME`) and RUNNING Sessions whose owner lease ran out (`OWNER_LOST`, or `GAME_FINISHED` with a finalized replay), reading only overdue Sessions through one partial index per deadline; a controller whose heartbeat finds its Session ended ends it live. Tested (unit, Postgres integration). |
| Recovery checkpoints | IMPLEMENTED | A running game's controller takes a checkpoint at the first committed boundary at least 5 s after the previous one (state, PRNG, revision, game time, participants, processed COMMAND tokens, participants the game was told disconnected), under its lock right after the commit, and its own writer goroutine stores the latest one through `sessionlifecycle.SaveCheckpoint` (only while RUNNING, never over a higher revision) without blocking the game; a failure waits for the next. Shutting down writes no last checkpoint, by decision: any end of the process counts as abrupt and the game resumes from its last periodic checkpoint. Tested, and checked in a live crash. |
| Session recovery | IMPLEMENTED | Lazy: the first player or admin reconnecting to a Session the database has RUNNING, on an instance whose controller does not run it (after a crash or restart), makes the controller recover it on its main goroutine (concurrent reconnections recover it once): past its lifetime it ends as MAX_LIFETIME instead; otherwise the game is restored from its latest checkpoint (`LoadRunningSession`, restored Sandbox context, projections rebuilt), game time resumes from the checkpoint, inputs at defaults, processed tokens and disconnected participants kept, and whoever was playing has a 30 s recovery window before `playerDisconnected()`. A failure fails the connection (1011) and the next reconnection tries again. Tested, and run live by killing the server mid-game. |
| Join code resolution | IMPLEMENTED | `play/session/usecases/resolvejoincode` (`ResolveJoinCode`): an unreleased, unexpired join code names its Session (matched case-insensitively); anything else is `not_found`. Called by the API before routing a player who joins by join code. Unit and repository tests. Flow: `play/docs/FLOWS.md`. |
| Sandbox | PARTIAL | `play/runtime/sandbox.Host`: one execution context per running Session, each a long-lived worker process (a re-exec of the binary, `RunAsWorkerIfRequested` first thing in `main`) hosting a QuickJS-on-WebAssembly runtime with the script loaded. No host capability: a patched copy of qjs (`third_party/qjs`, see its `PLAYHOOT_PATCH.md`, which also fixes upstream's use-after-free when serializing results and its leaked C strings) mounts no directory and gives wazero's fake clocks and randomness, so even the `qjs:std`/`qjs:os` modules reach no file, environment, network or real time; the host helpers (`std`, `print`, `setTimeout`...) are removed; the worker process also runs with an empty environment (defense in depth). The script runs in strict mode and, once loaded, every global and builtin is deep-frozen, so no state can live outside what executions return; arguments are deep-frozen, and `Math.random` throws inside `project()`. Limits: 64 MiB memory and 1 MiB stack per context, a 5 s execution budget per call enforced by killing the worker (reported as a script failure), and per instance at most `SANDBOX_MAX_CONTEXTS` contexts (default 32; beyond that Start answers `sandbox_unavailable`) and `SANDBOX_MAX_CONCURRENT_EXECUTIONS` calls at once (default: CPUs). Script contract: `start(participants, context)` returns `{ state }`, `project(state, participant, context)` returns the view; `samples(state, transitions, context)` returns `{ state }` and `command(state, cmd, context)` (cmd `{participant, name, payload, sessionTime}`) returns `{ state, response }`; `update(state, context)` and `playerDisconnected(state, participant, context)` return `{ state }`; these may add `errors: [{participant, error}]` and `events: [{event, participants?}]`, the logical errors and events of that call (at most 256 KiB each); `Date` is the effective Session time (0 at start) and `Math.random` a seeded mulberry32 whose state is exported (4 bytes) for the checkpoint; the context revision is 1 after start. Called by Start; start, restore, execute (a batch of `samples()`, `command()` and `update()` steps) and project exist. Every worker compiles the runtime when it starts, so creating a context costs about half a second of CPU. A worker exits as soon as its stdin ends, even in the middle of a call, so it never outlives its host. The controller evicts the context of a running game without update() after 30 s unused and the next execution restores one from the mirror (a game with update() stays hot); evictions and recreations are counted by the controller. Capacity and resource metrics (`play_runtime_sandbox_*`: active contexts and limit, capacity rejections, executions in flight and limit, slot waits, execution durations by operation and outcome, worker stops by reason, output sizes, worker memory) are recorded by the sandbox. `play/runtime/sandbox/scriptcheck` statically validates a script for publication (no module or global state, no mutation of inputs, AST-based); nothing calls it yet. |
| Replay recording | IMPLEMENTED | Complete for the producer side (accepted 2026-10-19); playback, a retention policy for replay objects and metric emission do not exist yet. Producer side only (`play/docs/decisions/SESSION-ADR-0033-replay-recording-produces-immutable-chunks.md`, flow in `play/docs/FLOWS.md`). Each controller run opens a recording (`play/runtime/workflows/replayrecording`) when its game starts, is adopted or recovered, with the starting state as first point, and offers every committed boundary without blocking. Chunks of `REPLAY_CHUNK_DURATION` effective Session time (default `60s`) hold a full base state, JSON Patch deltas of one tick's state in every `REPLAY_STATE_SAMPLE_EVERY_N_TICKS` (default 1) and every event, logical error and COMMAND response with its targets, in timeline order; versioned JSON compressed with zstd. The recorder owns the chunking policy; its internal `chunk` package only builds and encodes chunks (`play/runtime/workflows/replayrecording/internal/chunk`, with `play/runtime/internal/business/jsonpatch`). Sealed chunks are stored in the background by one bounded queue per instance (`REPLAY_MAX_PENDING_CHUNKS`, default 64; oldest dropped when full; 5 attempts each) through `play/session/usecases/storereplaychunk`: object `replays/{session}/{recording}/{index}.rpl` in the private bucket first, then `play_replay_chunks` / `play_replays`. A finished game's final tick closes the last chunk, stored synchronously and finalizing the manifest before FINISHED. Other endings and shutdown store what was held, best effort (shutdown waits up to 10 s). Metrics `play_runtime_replay_captures_total{outcome}`, `play_runtime_replay_chunks_total{outcome}`, `play_runtime_replay_chunk_store_duration_seconds{outcome}`, `play_runtime_replay_chunk_bytes`, `play_runtime_replay_chunk_session_seconds`, `play_runtime_replay_pending_chunks`, `play_runtime_replay_finals_total{outcome}`; dropped chunks are alerted. Unit tests, repository tests against Postgres, and an end-to-end run against the local emulator (a cancelled Space Drift Session and a game that finishes by itself: hashes verified, states rebuilt from the deltas, the final chunk registered before FINISHED). Playback does not exist. |
| Rate limits and resource controls | IMPLEMENTED | The platform chooses every limit; a game cannot ask for more. Limits combine a short and a long window (`utils/ratelimit`). Per instance: at most `RUNTIME_MAX_LIVE_SESSIONS` live Sessions (default 500; a new one is rejected `server_busy`). Per Session (`liveLimits` in `play/runtime/workflows/liveconnection/controller_resolver.go`): 8 admin connections (`too_many_admins`); per participant, 120 distinct input transitions a second and 3600 a minute (beyond them a transition is dropped unacknowledged, and the next SAMPLE carries the state); COMMANDs at 10 a second and 120 a minute per participant, 60 a second and 600 a minute for the whole Session, 4 waiting per participant (beyond any, `rate_limited`, the token unused); at most 128 operations a participant sent and 2048 for the Session waiting in the timeline (the platform's own, disconnections and input resets, are never refused); at most 256 operations per boundary (the rest run in the next one, asked for at once: the partial boundary ends at its last operation without update() and acknowledges only the SAMPLEs it took); at most 25 boundaries a second and 1200 a minute, where ticks always run and count, and a boundary a COMMAND, leave or rejoin asks for beyond them waits for the next tick; 1000 executed COMMAND tokens kept per participant, the oldest forgotten first (a retry comes within seconds; checkpoints keep them oldest first, so each holds at most about 128 KB of tokens per participant); a connection leaving 8 views untaken gets one FULL view of its current view instead, keeping the errors and events they carried. Metrics `play_runtime_limit_rejections_total{limit}`, `play_runtime_boundaries_deferred_total`, `play_runtime_boundaries_split_total`, `play_runtime_views_collapsed_total`, and `rate_limited` in `play_runtime_samples_total` and `play_runtime_commands_total`. No limit ends a Session: `TerminateSession` stays unwired (decided by the human). The API edge's own limits are in `api/README.md`. Unit tests. |

- `play/runtime/usecases/ownership.Service.LocateOrClaimOwner` answers `owned_here` with epoch 1 for every live Session, without a registry. Real behavior: an in-process registry claims and releases ownership; before more than one instance may own Sessions, a shared registry with an owner-renewed lease and heartbeat (SESSION-ADR-0029).
- No object storage is configured by default: without `GCS_PROJECT_ID` / `GCS_BUCKET` every storage call fails (`objectstore.Unconfigured`). Locally the emulator is configured (see Object storage); deployed environments still need their bucket, chosen by environment variables only.
- During a Start attempt, a player's `Leave` returns "not implemented" (as in a running game).
- Before the game runs a player's `Command` answers `session_not_running` and `Sample` is dropped (right), and in a running game `Leave` returns "not implemented".
- `ControllerResolver.TerminateSession` (platform termination) is ready but nothing calls it; a Session owned by another instance would only be ended durably. No rate limit or resource control calls it, by the human's decision (2026-10-19): a misbehaving player is limited, never everyone's game.
- "No live owner" is a durable lease (`play_sessions.owner_lease_expires_at`, 10 min, renewed every 30 s by the controller running the game), not an owner registry: it works with several instances, but the registry (CHECKLIST A1) is still a placeholder. Reconciliation ends Sessions nothing live will end (see `play/docs/FLOWS.md`, Reconciliation).
- `ownership.Service.ReleaseOwner` is called by every controller when it ends, but does nothing: there is no registry to release from. A controller created for a connection that was then rejected lives until its lobby deadline ends it.
