# SESSION-ADR-0031: Game Time Is Handled By update(), Without Platform Timers

Status: ACCEPTED
Created: 2026-10-18
Last status change: 2026-10-18
Supersedes: None
Superseded by: None

## Context

The architecture plan (`plans/session_runtime/...`, §10) gives games platform timers: `scheduleTimer(id, dueAt or delay, data)` and `cancelTimer(id)`, a schedule the Runtime owns and checkpoints, and a `timer(...)` entrypoint the Runtime calls when a timer is due, which can also trigger an early boundary.

By the time timers were due to be built, the Runtime already had periodic processing (§9). A game that declares `update` gets one `update(state, context)` call at the end of every boundary, about every 100 ms, with the effective Session time (`context.sessionTime`) and the time since the previous operation (`context.elapsed`). The plan never promised timers millisecond accuracy either: a due timer would still run at a boundary, so it would be as precise as `update()`.

Game scripts are generated by AI, so every platform mechanism is something the generator has to use correctly.

## Decision

1. **No platform timers.** Playhoot does not offer `scheduleTimer`, `cancelTimer` or a `timer(...)` entrypoint, and the Runtime keeps no timer schedule. Checkpoints hold no pending timers.
2. **Time-driven behavior goes through `update()`.** A game that needs something to happen at a given time stores the deadline in its own state (for example `state.answerDeadline`) and declares `update`. Its `update()` compares `context.sessionTime` with that deadline. The state is the only source of truth for what is pending.
3. **`update()` stays continuous.** A game that declares it runs it at the end of every boundary. The game cannot ask for a specific wake-up time.

## Rationale

- **Same precision.** A timer would fire at a boundary, so it would not be more precise than `update()`.
- **Simpler for generated scripts.** With deadlines in state, nothing has to be cancelled. A classic timer bug cannot happen: a timer set in round 3 firing in round 4 because the script forgot to cancel it, or cancelled the wrong id. `project()` can show a countdown from the same deadline.
- **Recovery for free.** The deadline is in the state, so the checkpoint already holds it. No second piece of state has to stay in sync.
- **The sandbox model stays pure.** `scheduleTimer()` would be a side effect inside entrypoints that today only return values. Expressing it as returned data would add another output contract.

## Alternatives Considered

### Platform timers as in the plan

Explicit and declarative. Rejected: ids, cancellation, timer data and a new entrypoint cost more than they give, given the same precision as `update()` and the stale-timer bugs generated scripts would be likely to make.

### A requested wake-up (`wakeAt`) with on-demand `update()`

Each mutating call would return the next Session time at which the game needs `update()`, and games without continuous simulation would not tick. Rejected by the human: with several pending deadlines, the script would need either a rule like "only the earliest, which then returns the next one" or a list of wake-ups, which is timers again.

## Consequences

- A game that needs any time-driven behavior must declare `update` and runs a JavaScript call, plus a projection per participant, on every boundary while it is RUNNING, even when nothing changes. Its sandbox context stays hot, so the plan's eviction of idle contexts never applies to it.
- Bounding that cost is left to the meaningful-inactivity timeout and the maximum Session lifetime (§25). Skipping `project()` when the state did not change is a possible later optimization. It is not decided.
- Game generation guidance must teach the pattern: deadlines in state, checked in `update()`.

## Canonical Knowledge Impact

- `play/CURRENT_STATE.md`: the running game has no platform timers by decision.
- `docs/projects/active/session-runtime-v1/CHECKLIST.md`: the plan's timer items are out of scope.

## Implementation Impact

None to build. The timer items of the Session Runtime project are closed as out of scope. The ones that also listed other things keep only those.
