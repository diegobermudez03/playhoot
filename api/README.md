# API

API is the external transport/application edge for Playhoot.

- Exposes user-facing transport endpoints.
- Translates transport requests and responses.
- May handle transport-level concerns.
- May perform BFF response shaping for frontend needs.
- May call a single-domain capability.
- May call Composer for cross-domain reads.
- May initiate Orchestrator workflows for cross-domain writes.
- Owns no business state.

BFF response shaping is not the same as cross-domain read composition. If a request requires combining multiple domain reads, that composition belongs to Composer.

This README does not define Identity or authorization ownership.

## Organization: one edge, many route groups

`api` is *the* transport/application edge for the whole system - not one edge per domain. As more workflows/domains are exposed, their endpoints all land in this same package, so it is organized as a set of independent **route groups** rather than one flat list of handlers:

- `api/server.go` - the top-level `Server`/`NewServer()`/`Routes()`. It composes every route group's declared endpoints onto one `http.ServeMux`. A route group that needs a dependency declares its own narrow port for it, and `NewServer` is where its construction is wired.
- `api/<workflow>/` - one subpackage per route group (e.g. `api/play/`), each owning its own handlers, wire DTOs and anything specific to its endpoints. Inside a route group, each endpoint's handler (with its DTOs) has its own file named after the endpoint (`create_session.go`, `admin_join.go`); `handler.go` only declares the `Handler`, its dependencies and its routes. A route group does not need a one-to-one relationship with a single business domain: it may call a single domain capability directly, or a cross-domain coordination layer (Composer/Orchestrator), depending on what its endpoints actually need - but it is still registered, tested, and reasoned about as one independent unit.
- `api/internal/routing/` - the shared `Route`/`Middleware` vocabulary a route group and `Server` both need, without either importing the other (a route group lives *under* `api/`, and `api` composes every route group, so a direct import either way would cycle).
- `api/internal/httpx/` - small HTTP response mechanics (JSON encoding) shared across every route group's handlers; protocol plumbing, not business behavior.
- `api/internal/auth/` - the authorization middleware (see below).

Adding a new workflow's endpoints means adding a new `api/<workflow>/` package with its own `Handler`, and wiring it inside `api.NewServer` from whatever shared infrastructure it needs - not adding more branches to an existing file, and not handing `main.go` the job of assembling each workflow's own dependency chain. `api` is reasoned about as if it were its own deployed service: it owns knowing how to construct or reach every capability it talks to, the same way a real gateway service would own its own downstream-client bootstrap rather than receive that already assembled.

### A route group only declares endpoints; Server registers and wraps them

A route group never touches an `*http.ServeMux` and never starts its own request log. It exposes two methods (an `SSERoutes()` will join them once anything needs Server-Sent Events), each returning a slice of `routing.Route{Pattern, Handler, Middlewares}`:

- `RESTRoutes()` - ordinary request/response endpoints.
- `WebSocketRoutes()` - long-lived connection endpoints.

`Server.NewServer` registers every route from every group onto the shared mux, wrapping each one with the observability behavior its transport shape needs *before* any route-specific middleware the group itself declared (see `docs/engineering/standards/logging.md`'s "Centralized Observability" section for exactly what that behavior is and why REST and WebSocket need different versions of it). This is the whole reason a route group returns declarations rather than registering itself directly: a route group cannot forget to add observability, because it never had the chance to decide whether to - and the same mechanism is where a future cross-cutting concern (metrics, for example) gets added once, for every endpoint, rather than copied into every handler.

A route declares who may call it in `Authorization` (a `routing.Middleware`, set only on routes that need a caller) and, optionally, its own request `Limits`. `Server` chains every route the same way: observability, the route's `Authorization`, request rate limiting, then the route's own `Middlewares` (`[]routing.Middleware`, each `func(http.HandlerFunc) http.HandlerFunc`) in declared order (the first in the list is the outermost), then the handler. `Middlewares` are for concerns specific to that one endpoint; today they are owner routing on live routes and, by join code, its resolution.

### Request rate limiting: every route, after authorization

Every route, REST or a WebSocket handshake, passes through `api/internal/throttle`, applied by `Server` right after the route's authorization, so it runs before any route-specific work (join code resolution, owner claims) and an authorized caller is limited as a user. A caller the route authorized is limited by its `UserUUID`; any other, today only `POST /v1/guests`, by client address. Limits combine a short and a long window (a token bucket per window, `utils/ratelimit`): by default at most 5 requests a second and 30 a minute per user, and 20 a second and 300 a minute per client address, higher because many people may share one (a classroom behind one router). A route may declare its own `routing.RequestLimits`; none does today, since none has a reason to differ. Each route has its own budget. A refused request is answered `429` with code `rate_limited` and a `Retry-After` header in seconds, counted in `api_http_rate_limited_total{key}` (`user` or `client`). The check itself is timed in `api_http_rate_limit_check_duration_seconds{key,swept}`: once per longest window (a minute by default), the check that comes first also forgets that route's keys whose room fully came back, which costs in proportion to the keys it remembers, so those checks are labeled `swept="true"`. The client address is the connection's own unless `TRUSTED_PROXY_HOPS` says how many proxies in front of the server append it to `X-Forwarded-For` (`1` behind Cloud Run alone); entries a client wrote itself are never trusted. Limits are kept in memory per instance, so with several instances a caller gets each instance's budget; a global limit belongs to the infrastructure in front of the service.

The HTTP server bounds each exchange (`main.go`): headers in 10 s and 64 KiB, the request in 15 s, the response in 30 s, idle keep-alive connections 60 s. A connection upgraded to a WebSocket is no longer subject to them: upgrading clears its deadlines.

A WebSocket handler never blocks for the connection's lifetime. Once the connection is admitted, it hands it to `api/internal/live`, which runs each live connection in its own goroutine, and returns. So a WebSocket route's request log is one ordinary line covering the handshake up to admission, and the connection logs its own end (`live connection closed`, with cause and duration) under the same trace. `wsObservability` measures the handshake as an HTTP exchange (`api_websocket_handshakes_total{route,status}`, `101` when upgraded, and its duration); `api/internal/live` measures the connections it runs (`api_live_connections_active`, `api_live_connections_closed_total{close_cause}`, `api_live_connection_duration_seconds`). Whether the Runtime admitted a connection is the Runtime's to count. `Server.Shutdown` tells every live connection to end (closed with `1001`, going away) and waits for them; `main` calls it after the HTTP server stopped accepting requests, because `http.Server.Shutdown` does not track hijacked connections.

## The identity route group

`api/identity` declares `POST /v1/guests`, the only way a client without an account obtains a token. It needs no token. It takes `{display_name, idempotency_key}` and returns `201 {user_uuid, token}`; the client keeps the token and sends it like any other. The idempotency key must be a UUID: with no caller to scope it, it has to be unguessable, since replaying it returns the same guest and token. `400` for an invalid body, a key that is not a UUID, a missing name or one over 64 characters, or a name Identity rejects; `409` when the key was used with another name. Identity owns the rules of a valid display name; the API only bounds its length.

## The play route group

`api/play` is the play domain's route group, and today the only one. It declares `POST /sessions` (create a Session), `GET /sessions/{sessionUUID}/admin` (the creator's live admin connection), and the player's live connection, by Session UUID (`GET /sessions/{sessionUUID}/player`) or by join code (`GET /join/{joinCode}`); the other live endpoints are added as the real-time design is accepted.

`POST /sessions` takes `{game_uuid, idempotency_key}` and returns `201 {session_uuid, join_code, lobby_expires_at}`; `404` when the Game is not playable for the caller, `409` when the idempotency key was used for a different request, `400` for an invalid body. The creator is never part of the request: it is the caller Identity resolves from the bearer token.

`GET /sessions/{sessionUUID}/admin` is a WebSocket. Before the upgrade it authorizes the caller for `JOIN_SESSION_AS_ADMIN` and routes the Session to its owner; the client must offer the `playhoot.v1` subprotocol (`400` otherwise) from an allowed origin (`403` otherwise), and an invalid Session UUID is `400`, a Session that cannot be joined live `404`. After the upgrade the connection is attached to the Runtime, which decides admission: an open WebSocket is not yet an admitted one. A rejected connection receives `{"type":"rejected","reason":...}` and is closed (`1008`). An admitted one gets a `runtime.AdminConnection`: the operations the Runtime offers for this kind of connection, as functions over the Runtime's own types (`SelectPerspective`, `StartSession`, `CancelSession`, `NextLobbyUpdate`, `NextView`, `Ended`, `Disconnect`). The Runtime never sees the socket.

The player endpoints authorize the caller for `JOIN_SESSION_AS_PLAYER` (which Identity allows guests) and route the Session to its owner the same way; by join code, the code is first resolved to its Session (`join_code_routing.go`: `404` when unknown or expired, `400` when longer than any code), after authorization so an unauthorized caller learns nothing. A join code is only an identifier, never authorization. Every live endpoint needs an existing token, a guest's or an account's: a client without one is answered `401` with code `token_required`, and gets a guest token from `POST /v1/guests` first. An admitted player gets a `runtime.PlayerConnection` (`Leave`, `Sample`, `Command`, `Resync`, `NextLobbyUpdate`, `NextView`, `Ended`, `Disconnect`). Admins and players are always separate connections, even for a creator who plays: starting and cancelling the Session are admin messages only.

Each live endpoint owns its wire messages and how it drives its connection's operations. Admin join (`admin_join.go`) and player join (`player_join.go`) each run their loops, built from what they share in `live_connection.go`. One loop reads every client message and hands it to the lane of its type (`api/internal/live/lanes.go`), never waiting for it to be handled; each type has its own lane, a goroutine that handles that type's messages in order and writes each answer, so a slow COMMAND never delays a SAMPLE and vice versa. Handing off never blocks, and every lane is bounded (see Live connection limits below). Closing waits for any answer in progress in every lane. The other loops: one writes every lobby update (`{"type":"lobby_update","members":[{"user_uuid":...,"display_name":...}]}`) and, once the Session starts, `{"type":"lobby_closed"}`, after which no update follows; one writes every view (`{"type":"player_view","participant_id":...,"full":...,"state":<the game's JSON>}`, and `revision`, a counter of the connection's views: each FULL view or patch is the previous plus one, a view that changes nothing repeats it, and a patch that does not follow means the client lost one and should send `resync`; plus `consumed_through_sample_sequence` and, when the game produced them for the player in that boundary, `errors` and `events` (arrays of the game's logical errors and events, as its JSON values, sent once and never repeated) on the player's own connection only); one waits for the Runtime to end the connection and closes the socket with its reason, after every stream and answer in progress was delivered. Admin requests: `{"type":"select_perspective","participant_id":...}`, `{"type":"start_session"}`, `{"type":"cancel_session"}`, answered `select_perspective_result`, `start_session_result`, `cancel_session_result` (`{"type":...,"outcome":...}`). Player requests: `{"type":"sample","sequence":<positive>,"inputs":{...}}` (never answered; its acknowledgement comes with the views), `{"type":"command","token":...,"name":...,"payload":<the game's JSON, optional>}` (answered `{"type":"command_result","token":...,"outcome":...,"response":<the game's JSON, when executed>}`), `{"type":"resync"}` (a FULL view of the current state follows, with the current acknowledgement and the next revision), `{"type":"leave"}` (answered `leave_result`, then closed `1000`). A player connection the same user replaced with a newer one is closed `1000` with reason `replaced`, so the client knows not to reconnect. A player whose connection was lost reconnects to the same endpoint: within the Runtime's transport grace (3 s) they get `session_started` again and a FULL `player_view`, and number their SAMPLEs from 1 again on the new connection; later, or after sending `leave`, coming back is a rejoin the game decides: accepted, the same `session_started` and FULL view follow; rejected, reason `rejoin_rejected`; a game that does not support it, reason `participant_disconnected`. Each endpoint accepts only its own catalog, so a player can never send an admin message nor an admin a SAMPLE or COMMAND. `api/internal/live` holds what every live endpoint shares, knowing no domain: running the loops until one ends the connection, stopping the rest, calling `Disconnect`, shutdown (`1001`), the close log, and reading/writing JSON messages. A frame that is not a valid message ends the connection without reaching the Runtime: binary `1003`, undecodable or missing fields `1007`, unknown type `1008`, over 32 KiB `1009`. `api/internal/wsx` is the domain-free upgrade (subprotocol, origin, size limit).

Display names and the roster (2026-10-20, asked by the human for the frontend): the authorization middleware puts the caller Identity resolved (`identity.User`: UserUUID and display name) in the request context, and the player join builds the Runtime's own `runtime.Player` from it. Every lobby member and every participant of `session_started` (players and admins) carries `display_name`. A player connection also receives, after `session_started`, `{"type":"roster_update","members":[{"participant_id":...,"user_uuid":...,"display_name":...,"status":...}]}`: the whole roster every time a participant's presence changes (the first one right after the start, and again after every reattach), `status` being `active`, `reconnecting` (connection lost, inside the transport grace, or rejoined and not yet attached), `disconnected` (the grace ran out) or `left` (they sent `leave`). Only the latest roster not yet sent is kept.

Every `lobby_update` and `session_started`, for players and admins, carries the routed Session as `session_uuid` (added 2026-10-20 at the human's request for the frontend): a client that joined by join code learns which Session it is in, so it can reconnect through `/v1/play/join/sessions/{sessionUUID}/player` once the Session starts and its code is released. The API only returns identifiers; URLs are the frontend's.

### Live connection limits

Before the upgrade, `api/internal/live` reserves room for the connection: at most `LIVE_MAX_CONNECTIONS` per instance (default 2000; beyond it `503` with code `server_busy`) and 10 per caller (beyond it `429` with code `too_many_connections`), counted in `api_live_connections_refused_total{reason}`; the room is given back when the connection ends or is never served. Once served, everything a client sends is bounded at two levels, all values chosen by the platform and declared by each endpoint (`live_connection.go`, `admin_join.go`, `player_join.go`):

- The connection as a whole: at most 120 messages a second and 6000 a minute, and 256 KiB a second and 4 MiB a minute. Beyond them the connection is closed `1008` with reason `rate limited` (close cause `rate_limited`). Only a misbehaving client reaches them.
- Each message type: a rate and a queue. `sample`: 60 a second and 3600 a minute, 64 waiting; beyond them the SAMPLE is dropped (each is a full snapshot, so the next one carries the state, and sequence gaps are allowed). `command`: 20 a second and 300 a minute, 16 waiting; beyond them it is answered `command_result` with outcome `rate_limited` without reaching the Runtime, so its token stays unused. `resync`: 2 a second and 30 a minute, one waiting; extra ones are dropped, since the waiting one brings the current view. `leave`: one a second, one waiting. Admin `select_perspective`: 5 a second and 60 a minute, 4 waiting; `start_session` and `cancel_session`: 2 a second and 20 a minute, 2 waiting; beyond them the admin connection is closed `1008` `rate limited`. Refusals are counted in `api_live_messages_refused_total{limit}`.

The Runtime adds its own limits per participant and per Session (a COMMAND may still be answered `rate_limited` by it; see `play/CURRENT_STATE.md`) and may reject an admission with reason `too_many_admins` or `server_busy`. A client that does not take a message within 10 s is dropped as too slow (close cause `slow_consumer`), and every connection is pinged every 15 s: one whose pong does not come back within 10 s is closed (close cause `unresponsive`), so a half-open connection is noticed instead of held.

### Live routes are routed to the Session's owner

Every live route declares the route group's owner routing middleware (`owner_routing.go`), which runs after authorization and rate limiting (`play/docs/decisions/SESSION-ADR-0029-live-session-ownership-and-owner-routing.md`). It asks the Runtime for the Session's owner, claiming one when there is none, and lets the request through only when the owner is this instance; the handler reads the routed Session and its ownership epoch from the request context and passes the epoch to the Runtime. It lives in the play route group because it is specific to play Sessions and the Runtime's types. Forwarding to an owner elsewhere is not implemented (answered `503`): with a single instance it cannot happen.

Browser origins other than the server's own are allowed through `WEBSOCKET_ALLOWED_ORIGINS` (comma-separated host patterns, such as `app.example.com` or `*.example.com`; empty allows only the server's own origin).

### Authorization: a per-route middleware backed by Identity

A route that needs an authenticated caller declares `auth.Require(authorizer, operation)` (`api/internal/auth`) as its `Authorization`. The middleware extracts the `Authorization: Bearer <jwt>` token and asks Identity (its own unexported `authorizer` port) for the caller's `UserUUID` and whether that caller may perform the route's named operation (`identity.Operation`); `401` for a missing/invalid token, `403` when Identity forbids the operation. These failures carry a stable `code` next to the `message` (`{"code":...,"message":...}`), which clients branch on: `token_required` (no token was sent: a client without an account creates a guest first), `token_malformed`, `token_invalid` (missing, expired or unknown to Identity), `operation_forbidden`. The handler behind it reads the caller with `auth.UserUUID(ctx)`. The api never interprets the token.

A WebSocket route declares `auth.RequireWebSocket(authorizer, operation)` instead. A browser cannot set headers on a WebSocket handshake, so besides the `Authorization` header (read first), the token may be offered the way the Kubernetes API server accepts it: as the subprotocol `base64url.bearer.authorization.playhoot.<token as unpadded base64url>`, next to `playhoot.v1`. The server only ever selects `playhoot.v1`, so the token is never echoed back. A token subprotocol that cannot be decoded is `401` `malformed bearer token`. Rejections are answered before the upgrade.
